## 1. 引言

### 1.1 业务背景

当前 EmodorRuleExam 已经覆盖培训类别、学员、课程、题库、试卷发布、自动评分、考试记录和统计，但还缺少“人什么时候来、来哪里、占几个名额、是否已付费、企业名单如何进入系统”这一层。

预约域要解决四个现实问题：

1. **个人预约**：学员先支付培训产品费用，再从可用时间段中选择预约场次；当前培训地点固定在海珠区，但不能把海珠区写死在业务代码中。
2. **企业/班组预约**：企业或班组一次预约多人，根据模板上传 Excel 或 TXT 名单，系统逐行预检、确认、创建或匹配学员，并批量分配场次。
3. **有限名额**：每个场次有明确开始时间、结束时间、地点和容量；并发操作不能超卖，取消或退款后名额要按规则释放。
4. **预约与考试衔接**：预约确认不是直接改写考试记录。预约确认后生成考试资格凭证，学员在满足预约、实名、时间窗口等条件后才允许进入对应考试。

### 1.2 设计目标

| 目标 | 定义 |
|---|---|
| 个人闭环 | 产品选择 → 待支付订单 → 支付成功 → 选择场次 → 预约确认 → 到场签到 → 参加考试 |
| 团队闭环 | 企业/班组建单 → 上传 Excel/TXT → 预检与逐行错误 → 确认有效名单 → 分配场次 → 统一支付或财务确认 → 批量预约与通知 |
| 名额可靠 | 服务端以 MySQL 事务和行锁维护容量；Redis 只做短期限流、幂等辅助和可恢复的短期锁，不作为最终库存事实 |
| 账户可复用 | 尽量复用现有 `sys_user`、`training_category`、`learner_identity`、`media_asset`、`import_batch`、`paper_release` 和考试服务，不复制一套学员或试卷体系 |
| 未来可扩展 | 现在只启用海珠区一个地点，数据模型仍支持多个地点、多个产品、多个场次、团队拆分到多个场次和候补名单 |
| 可审计 | 支付回调、名额变更、名单导入、场次分配、取消、退款、签到和考试资格变化都能追溯到操作者、批次或外部事件 |

### 1.3 非目标

本期不建设以下能力：

- 不复制医疗系统的医生、治疗单、就诊卡、治疗师业务模型；培训预约只借鉴“资源—时间段—名额—预约单”的结构。
- 不引入租户平台、加盟分校、复杂营销优惠券、积分、商城购物车或通用电商商品中心。
- 不把支付成功直接当作考试成绩、考试记录或签到事实；支付、预约、签到和考试是四个不同事实。
- 不允许客户端自己计算剩余名额、支付金额、考试资格或预约状态。
- 不在本册内宣称已经接入微信支付、支付宝、短信供应商或生产退款通道；本册只冻结接入契约和状态。

### 1.5 本册的设计取舍

以下是本册直接采用的默认方案；它们不是旧系统事实，后续产品评审可以修改：

1. **个人支付顺序**：个人订单先支付，支付成功后进入“已支付待选场次”；支付成功但尚未选到场次时，不占用具体场次名额。
2. **团队支付顺序**：团队先创建订单并上传名单，预检通过后选择一个或多个场次，系统短时锁定名额，再完成统一支付或线下财务确认。确认支付前的锁定会过期，不形成永久占用。
3. **团队分配方式**：首版允许一个团队订单分配到多个场次，但默认要求一次分配成功；容量不足时整批失败并保留可调整状态，不静默拆散名单。
4. **地点**：首版只初始化一个“海珠区培训点”；预约页面可以展示地点，但当前没有多分校选择。数据库仍按 `venue_id` 关联。
5. **学员账号**：有效名单最终必须关联到现有 `sys_user` 学员。不存在的人员进入待激活流程，不在 Excel/TXT 中携带明文密码。默认情况下，已通过名单预检的待激活成员计入订单人数和场次占用，但在激活前不能签到开考；企业可在预约截止前替换成员。
6. **考试入口**：预约确认生成 `booking_exam_ticket`；考试开始时再校验场次、签到、实名和纸卷发布版本，不提前创建一条假的考试记录。
7. **支付渠道**：使用支付适配器隔离供应商；移动端首选微信支付，但在供应商未确定前不能把微信签名、商户号或回调字段写死到业务服务。

## 2. 角色、数据归属与端划分

### 2.1 角色

预约角色使用现有系统身份加业务权限组合，不修改 `sys_user.role` 的三值兼容枚举。建议新增以下业务角色：

| 角色 | 归属 | 主要职责 |
|---|---|---|
| `super_admin` | 现有系统身份 | 全部预约配置、权限和应急处理 |
| `training_admin` | 业务角色，映射现有 `regulation_admin` 能力 | 创建培训产品、地点、场次和查看预约运营数据 |

## 3. 业务对象与状态机

### 3.1 核心业务对象

| 对象 | 定义 | 是否冻结 |
|---|---|---|
| `booking_product` | 可购买的培训服务，如“安全教育培训 + 考试” | 下单时冻结名称、类别、单价和考试关联 |
| `booking_venue` | 培训地点；当前只有海珠区 | 预约确认时冻结展示快照 |
| `booking_session` | 某产品在某地点、某日期和时间段的一个可预约场次 | 发布后时间、地点和容量不能随意改写 |
| `booking_order` | 一次个人或团队购买/预约意图 | 金额、购买方和产品快照冻结 |
| `booking_participant` | 订单中的一个实际参训人 | 学员、场次、状态和考试资格可追踪 |
| `booking_seat_hold` | 场次名额的短时锁定 | 到期自动释放；不等于已支付或已确认 |
| `booking_exam_ticket` | 预约成员参加某场考试的资格凭证 | 绑定发布版本和场次，不替代 `exam_record` |

### 3.2 订单状态

`booking_order.status` 建议使用字符串，服务端校验，不在客户端自行推断：

```text
draft
  └─> pending_payment ──支付失败/过期──> expired
          │
          └─支付成功─> paid_unbooked
                              │
                              ├─个人选场次 / 团队分配场次
                              │       └─> holding ──锁定过期──> paid_unbooked
                              │                    │
                              │                    └─确认成功─> confirmed
                              │                                    │
                              │                                    ├─取消/退款中─> refunding
                              │                                    │                  └─> refunded
                              │                                    └─完成/关闭─> completed
                              └─无法提供场次─> refunding / paid_unbooked
```

订单状态只描述订单整体；支付状态、成员状态和场次状态单独保存，不能用“订单已支付”推断所有成员已预约。

### 3.3 支付状态

```text
unpaid -> creating -> pending -> paid
                         ├─> failed
                         └─> expired
paid -> refunding -> refunded
```

支付回调必须以供应商签名和服务端金额为准。重复回调只返回已处理结果，不重复记账、不重复增加名额、不重复发放凭证。

### 3.4 成员状态

```text
pending_import
   └─> imported / pending_account
                  └─> assigned
                         └─> confirmed
                                ├─> checked_in
                                │      └─> exam_eligible / completed
                                ├─> absent
                                └─> cancelled / refunded
```

`pending_account` 表示名单有效但尚未绑定现有学员账号，不能生成可开考凭证；`assigned` 只表示已经分配场次，未必已经支付或确认。

### 3.5 场次状态

```text
draft -> published -> open -> full -> closed -> completed
                         └──────────────> cancelled
```

- `published`：已配置但未到开放时间。
- `open`：可以创建锁定名额。
- `full`：剩余名额为 0，但已确认订单仍可查询和签到。
- `closed`：到预约截止时间或管理员主动关闭，不再接受新预约。
- `cancelled`：场次被机构取消，必须进入退款/改签处理。

### 3.6 名额不变量

每个场次必须满足：

```text
remaining_capacity
  = capacity
  - confirmed_participant_count
  - active_hold_quantity
  >= 0
```

`active_hold_quantity` 只计算 `expires_at > now` 且状态为 `active` 的锁定。数据库事务在同一场次行上加写锁后重新计算，任何客户端传入的“剩余名额”只用于展示，不参与判定。

### 4.3 企业/班组预约模块（FR-TEAM）

| 编号 | 需求名称 | 需求描述 | 优先级 | 验收要点 |
|---|---|---|---|---|
| FR-TEAM-01 | 企业与班组 | 维护企业、联系人、班组和组织管理员关系；外部组织与内部 `sys_department` 分离 | P0 | 企业管理员只能访问本组织；组织禁用后不能新建订单，历史记录可读 |
| FR-TEAM-02 | 团队订单 | 企业管理员按产品和预计人数创建团队订单，服务端生成订单号和金额快照 | P0 | 一个订单可包含多成员；订单金额等于有效成员费用汇总，不接受客户端总价 |

| FR-TEAM-07 | 团队分配场次 | 支持整批分配一个场次，也支持按成员/分组分配多个场次 | P0 | 默认原子分配；容量不足时不静默拆分，显示缺口并允许重新分配 |

## 5. 模板与批量名单设计

### 5.1 Excel/TXT 模板 v1

首版模板统一字段，Excel 第一行必须是字段名；TXT 使用 UTF-8（允许 BOM）且默认制表符分隔。不得上传密码、支付账号或与预约无关的敏感字段。

| 字段 | Excel/TXT 列名 | 必填 | 规则 |
|---|---|---:|---|
| 姓名 | `姓名` | 是 | 2—64 个字符；服务端保存时按 PII 规则处理 |
| 手机号 | `手机号` | 是 | 中国大陆手机号格式；用于匹配或短信激活 |
| 工号/学号 | `工号` | 否 | 同一企业内唯一；不能作为跨组织唯一凭证 |
| 证件号 | `证件号` | 否 | 需要实名的考试产品可要求；不在列表页明文展示 |
| 培训类别 | `培训类别` | 是 | 可填稳定 `category_id` 或模板展示名称，服务端解析为 ID |
| 预约场次编码 | `场次编码` | 否 | 为空时由管理员在后台分配；填写后必须匹配当前订单可用场次 |
| 备注 | `备注` | 否 | 仅供组织内部和运营查看，限制长度，不参与资格判定 |

导入逻辑：

1. 文件哈希和订单绑定，形成 `import_batch` 的 `kind = booking_participants` 批次；复用现有导入批次的预检、确认、锁定、重试和审计语义。
2. `import_batch` 增加可空 `booking_order_id`；现有 `students/questions/questions_ai` 批次不改变原语义。
3. `preview` 只写 `normalized_rows`、`valid_rows`、`errors`、`duplicates`，不创建学员、不占用场次、不创建支付单。
4. `commit` 只接受预检通过的行，按 `owner_id + batch_id` 加写锁；重复提交相同有效行返回原结果，提交不同集合返回冲突。
5. 已有学员按手机号、工号和已验证证件 HMAC 顺序匹配；多个账号匹配或字段不一致进入人工处理，不自动合并。
6. 未匹配人员可以创建待激活学员账号，但只保存不可知随机密码哈希并走短信激活；文件中不得出现密码。
7. 只有成员账号、订单、产品和场次都满足要求后，才能生成 `booking_exam_ticket`。

### 5.2 行级错误分类

| 分类 | 示例 | 处理 |
|---|---|---|
| 格式错误 | 文件类型、编码、列名、手机号、字段超长 | 行级拒绝，其他行继续预检 |
| 业务错误 | 培训类别停用、场次不属于产品、企业无权访问 | 行级拒绝或整批阻断 |
| 重复错误 | 文件内手机号重复、订单已有相同成员 | 行级拒绝并给出冲突对象 |
| 绑定待处理 | 手机号对应多个账号、姓名/证件不一致 | 进入待人工处理，不自动生成考试资格 |
| 容量错误 | 指定场次容量不足 | 分配阶段整批拒绝，名单批次仍可重新分配 |

## 6. 核心用例

### UC-RES-01 个人支付并预约

1. 学员登录移动端，选择培训产品。
2. 服务端创建 `pending_payment` 个人订单并冻结价格。
3. 学员完成支付；服务端校验回调后将订单置为 `paid_unbooked`。
4. 客户端查询可用场次，当前地点显示海珠区。
5. 学员选择场次，服务端锁定一个名额并在同一事务内确认成员。
6. 系统生成订单凭证和考试资格凭证（若产品关联纸卷）。
7. 学员按场次到场签到，符合开考条件后进入考试。

异常：支付成功但没有可用场次时，订单保持 `paid_unbooked` 并展示可申请退款/联系运营，不自动伪造预约；支付回调重复不重复生成凭证。

### UC-RES-02 企业上传名单并批量预约

1. `organization_admin` 创建团队订单，选择产品并填写预计人数。
2. 下载模板，上传 Excel/TXT。
3. 服务端预检，返回成功行、错误行、重复行和待激活行。
4. 管理员修正文件并重新预检，或只确认本次通过的行。
5. 服务端在订单锁内提交成员；成员账号未完成绑定的行保持 `pending_account`。
6. 管理员选择一个或多个场次；服务端按场次行锁原子预占名额。
7. 企业完成统一支付或财务确认；订单和成员进入 `confirmed`。
8. 系统向组织管理员和成员发送场次、地点、凭证和注意事项。
9. 现场批量签到；成员分别生成或使用对应考试凭证。

### UC-RES-03 场次容量并发争抢

1. 两个用户同时提交同一场次最后一个名额。
2. 服务端锁定场次行，先完成的请求创建锁定/确认，后到请求重新读取容量。
3. 后到请求收到 `BOOKING_SESSION_FULL`，不创建成员、支付成功状态或考试资格。
4. 测试验证最终 `confirmed + active_hold <= capacity`。

### UC-RES-04 场次取消

1. 运营管理员关闭或取消场次，必须填写原因。
2. 服务端阻止新选场次，查询受影响订单和成员。
3. 已支付未开考成员进入改签或退款队列；已完成考试记录不变。
4. 通知发送失败只记录重试，不回滚场次取消事实。

### UC-RES-05 预约取消与退款

1. 学员或有权限的管理员提交取消。
2. 服务端检查订单状态、成员状态、取消截止时间、是否已经签到/开考。
3. 合法取消将成员置为 `cancelled`，释放名额并创建退款请求（如适用）。
4. 退款回调将支付单置为 `refunded`；失败则进入人工处理，不伪造成功。

## 7. 系统架构与模块设计

### 7.1 总体链路

```text
mobile employee / organization admin / PC operator
                       │
                       ▼
              NestJS reservation APIs
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
  Booking Domain   Payment Adapter   Exam Bridge
       │               │                │
       ▼               ▼                ▼
 MySQL 8.0         Provider/Webhook   paper_release
   + Redis             + Outbox       exam_assignment
```

服务端以预约域为唯一事实源。支付供应商只通过适配器更新支付状态；考试模块只读取预约凭证并在开考时创建/恢复考试记录，不反向修改预约库存。

### 7.2 服务端模块

建议新增 `server/src/modules/reservations/`，内部按职责拆分：

| 子模块 | 职责 | 依赖 |
|---|---|---|
| `catalog` | 产品、价格快照、地点 | `training`, `media`（地点图片如未来需要） |
| `sessions` | 场次、开放窗口、容量、发布/关闭 | `catalog`, `access` |
| `orders` | 个人/团队订单、状态机、成员聚合 | `catalog`, `sessions`, `users` |
| `participants` | 成员绑定、状态、组织数据范围 | `users`, `identity` |
| `imports` | Excel/TXT 预检、批次锁、确认、错误导出 | 现有 `imports`, `media` |
| `payments` | 支付单、供应商回调、退款、对账 | `orders`, `audit` |
| `check-in` | 凭证、签到、缺席、改签 | `sessions`, `participants` |
| `exam-bridge` | 预约考试资格、纸卷版本、开考守卫 | `exams`, `courses`, `identity` |
| `notifications` | 支付、确认、提醒、取消、场次变更事件 | `audit`, 外部通知适配器 |

不把医疗预约的 `ZYBookService`、`ZyBookInfo`、患者治疗单直接移植到 NestJS；可以借鉴其状态和校验，但新系统要使用当前项目的响应信封、DTO Pipe、RBAC、审计、迁移和实体约定。

### 7.3 Web 管理端建议

建议在 `web/src/views/admin/` 增加预约菜单和页面：

```text
Reservations/
├── Products.vue       # 产品和价格
├── Venues.vue         # 地点
├── Sessions.vue       # 场次、容量、发布与关闭
├── Orders.vue         # 订单、支付、退款、取消
├── TeamOrderDetail.vue# 团队名单与场次分配
├── ImportPreview.vue  # Excel/TXT 预检和确认
├── CheckIn.vue        # 签到与异常处理
└── Reports.vue        # 预约、到场、支付、考试资格统计
```

按钮权限必须分别注册，例如 `reservations:read`、`reservations:write`、`reservations:import`、`reservations:allocate`、`reservations:checkin`、`reservations:refund`、`reservations:finance`，不能以一个“预约管理”大权限覆盖所有财务和个人信息操作。

### 7.4 Mobile 建议

移动端只保留本人/本人组织有权的预约数据：

```text
mobile/src/pages/booking/
├── index.vue          # 产品与可用场次入口
├── product.vue        # 产品说明和价格
├── order.vue          # 订单和支付状态
├── sessions.vue       # 选日期、时间段、地点
├── detail.vue         # 预约详情和凭证
└── exam-ticket.vue    # 预约关联的考试入口
```

个人预约和企业团队预约共用订单/场次 API，但客户端不共用登录状态；组织管理员如果首版使用 PC 入口，移动端不需要实现团队上传编辑器。

### 7.5 参考系统到本系统的映射

| 参考系统概念 | 培训系统概念 | 处理原则 |
|---|---|---|
| 患者 | 学员/企业成员 | 复用 `sys_user`，不要新增另一套患者账号 |
| 治疗项目 | 培训产品/培训类别 | 使用 `training_category` 和新的 `booking_product` |
| 资源 | 地点 + 产品 + 日期 | 拆成 `booking_venue`、`booking_product`、`booking_session` |
| 班段/号源 | 时间段/容量 | 用 `booking_session.capacity` 和 `booking_seat_hold` |
| 预约单 | 个人/团队订单及成员 | 用 `booking_order` + `booking_participant` |
| 黑名单 | 取消/风控限制 | 首版不复制医疗黑名单；按订单/账号/组织配置取消和异常规则 |
| 治疗任务 | 签到与考试凭证 | 用 `booking_checkin` 和 `booking_exam_ticket` |
| 微信消息 | 预约通知事件 | 接入现有通知能力或新增适配器，不把消息发送结果当作业务成功 |

## 8. 数据库设计

### 8.1 设计规范

预约域沿用 03 分册：MySQL 8.0、InnoDB、utf8mb4、`DATETIME(3)`、自增 `BIGINT`、数据库不建外键、引用完整性由应用层维护、枚举以 `VARCHAR` 加服务端校验、金额以整数分保存。

本册是增量提案；实施前必须同时更新 migration、`database/init.sql`、entities、03 分册和 README，不能只创建表而不更新迁移注册表或实体。

### 8.2 新增表建议

| 表名 | 一句话职责 | 优先级 |
|---|---|---|
| `booking_product` | 可预约培训产品、类别、考试关联和价格 | P0 |
| `booking_venue` | 培训地点和地址快照来源 | P0 |
| `booking_session` | 产品在地点和时间段的容量库存 | P0 |
| `booking_org` | 外部企业客户 | P0 |
| `booking_team` | 企业下的班组 | P0 |
| `booking_org_member` | 企业/班组与平台账号的关系、组织管理员权限 | P0 |
| `booking_order` | 个人或团队订单、金额和总体状态 | P0 |
| `booking_participant` | 订单成员、账号绑定、场次和成员状态 | P0 |
| `booking_seat_hold` | 场次的短期名额锁定 | P0 |
| `booking_payment_order` | 订单支付意图和渠道状态 | P0 |
| `booking_payment_event` | 支付/退款回调去重和原始摘要 | P0 |
| `booking_checkin` | 成员签到、迟到、缺席和操作人 | P0 |
| `booking_exam_ticket` | 预约成员到考试纸卷的资格桥接 | P0 |
| `booking_event` | 预约领域事件和通知投递状态 | P1 |

现有 `import_batch` 增量：

- `kind` 增加 `booking_participants`；
- 增加可空 `booking_order_id`；
- 保留现有 `students/questions/questions_ai` 的校验和确认语义；
- `normalized_rows` 只保存规范化后的必要字段，不保存上传文件中的密码或无关列；
- 通过 `media_asset` 保存原始 Excel/TXT 的私有引用，不把文件正文放入审计日志。

### 8.3 关键字段与关系

#### 8.3.1 `booking_product`

建议字段：`id`、`category_id`、`name`、`description`、`individual_price_cents`、`team_price_cents`、`paper_release_id`、`course_id`、`requires_checkin`、`requires_identity`、`status`、`effective_from`、`effective_to`、`created_by`、`updated_by`。

产品下线只阻止新订单，不删除历史订单。下单时必须保存产品名称、类别名称、单价和纸卷版本的快照。

#### 8.3.2 `booking_venue`

建议字段：`id`、`name`、`district`、`address`、`contact_name`、`contact_phone`、`status`、`created_by`、`updated_by`。

首发种子为海珠区培训地点；联系人手机号按敏感字段处理。订单和成员凭证保存名称、地址的历史快照，地点后续修改不改变已支付订单的到场信息。

`booking_org_member` 建议保存 `org_id`、`team_id`、`user_id`、`member_type`（`admin/member`）、`status`、`joined_at`、`left_at`。同一用户可以属于多个企业或班组，但每次组织接口请求必须带一个当前组织上下文；`organization_admin` 只能管理自己仍为 active 的组织关系。

#### 8.3.3 `booking_session`

建议字段：`id`、`product_id`、`venue_id`、`session_code`、`start_at`、`end_at`、`booking_open_at`、`booking_close_at`、`capacity`、`held_count`、`confirmed_count`、`status`、`paper_release_id`、`version`、`cancel_reason`。

索引至少包括：`(product_id, status, start_at)`、`(venue_id, start_at, end_at)`、唯一 `(product_id, session_code)`。`held_count` 和 `confirmed_count`是服务端事务聚合字段，任何修复都必须留审计。

#### 8.3.4 `booking_order`

建议字段：`id`、`order_no`、`order_type`（`personal/team`）、`owner_user_id`、`org_id`、`team_id`、`product_id`、`product_name_snapshot`、`category_id_snapshot`、`unit_price_cents`、`participant_count`、`amount_cents`、`paid_amount_cents`、`payment_status`、`status`、`expires_at`、`paid_at`、`confirmed_at`、`idempotency_key`、`source_client`。

唯一约束：`order_no`；同一身份和 `idempotency_key` 唯一；已支付订单的金额和产品快照不可原地改写。

#### 8.3.5 `booking_participant`

建议字段：`id`、`order_id`、`user_id`、`org_id`、`team_id`、`import_batch_id`、`session_id`、`display_name_snapshot`、`phone_last4_snapshot`、`status`、`seat_no`、`checked_in_at`、`cancelled_at`、`cancel_reason`。

姓名、手机号、证件号不应在普通列表直接保存或返回明文；需要实名的场景引用 `learner_identity`，导入匹配使用规范化值和 HMAC，不使用模糊姓名匹配作为唯一依据。

唯一约束：`(order_id, user_id)`；如果 `user_id` 为空，则使用 `order_id + import_batch_id + source_row_no` 防止同一批次重复确认。

#### 8.3.6 支付、锁定、签到和考试凭证

| 表 | 关键字段 | 不变量 |
|---|---|---|
| `booking_seat_hold` | `order_id`、`session_id`、`quantity`、`expires_at`、`status` | 过期锁不计入容量；同一订单同一场次最多一条 active 锁 |
| `booking_payment_order` | `order_id`、`provider`、`provider_order_no`、`amount_cents`、`status`、`expires_at` | 供应商金额必须等于服务端金额；回调幂等 |
| `booking_payment_event` | `provider_event_id`、`payment_order_id`、`event_hash`、`processed_at`、`result` | 同一供应商事件只处理一次 |
| `booking_checkin` | `participant_id`、`session_id`、`status`、`operator_id`、`checked_at` | 同一成员同一场次签到幂等 |
| `booking_exam_ticket` | `participant_id`、`session_id`、`paper_release_id`、`status`、`issued_at`、`used_at` | 只绑定不可变发布版本；取消/退款/撤回后不能新开考 |

### 8.4 数据一致性与事务

1. 创建订单、金额快照和幂等键在一个事务内完成。
2. 支付回调更新支付单、订单状态和领域事件时使用支付事件唯一约束；不直接修改场次计数。
3. 选场次/团队分配时锁定 `booking_session` 行，清理过期锁，重新计算容量，写入锁定和成员分配，再提交。
4. 确认预约时把成员状态、场次 `confirmed_count`、考试凭证和领域事件放在同一事务内；通知异步投递。
5. 取消时把成员状态、锁/确认计数、退款请求和审计事件按业务规则收口；不物理删除订单或成员。
6. `booking_exam_ticket` 只提供资格事实；真正的 `exam_record` 仍由考试模块在开考时按现有冻结规则创建。

任何预约失败都不能消耗考试次数；已创建的历史考试记录不因后续订单取消而删除。

## 10. 安全、隐私与非功能设计

### 10.1 认证、权限与数据范围

- 个人接口按 `user_id` 收口；企业接口按 `org_id` 收口；平台管理员按权限代码和审计边界访问。
- 客户端传入的 `price`、`capacity`、`remaining`、`payment_status`、`exam_eligible` 一律忽略或重新计算。
- 管理员的“补充名额”“人工确认”“改签”“退款确认”必须是独立权限，必须带原因。
- 支付回调、导入确认、场次分配和签到全部幂等；不允许重复请求生成重复成员、支付或资格。

### 10.2 敏感数据

- 姓名、手机号、证件号按现有实名和敏感信息约定处理；列表只显示脱敏值；导入匹配使用规范化值/HMAC。
- Excel/TXT 原文件使用私有媒体存储；短期下载票据必须绑定精确 `media_reference` 和当前组织授权。
- 日志、审计和错误响应不得输出完整手机号、证件号、支付密钥、供应商签名原文或文件正文。
- 企业管理员只能看到本组织必要的成员状态，不默认看到身份证、考试答案、解析或其他企业数据。

### 10.3 文件与导入安全

- 只接受 `.xlsx` 和 UTF-8 `.txt`；校验真实内容类型、大小、最大行数、列数、单元格长度和压缩包展开风险。
- 不接受密码、支付账号、脚本、公式执行或外部链接列；Excel 单元格按纯文本读取，避免公式注入。
- 上传文件先保存私有资产，再生成预检批次；预检和确认分离；失败行不影响其他批次。
- 文件哈希、订单和组织绑定；重复文件不能绕过批次状态和组织权限。

### 10.4 支付与库存安全

- 支付金额由产品和订单快照计算；回调金额与订单金额不一致时进入异常状态。
- 场次库存只在事务内修改；Redis 不作为最后名额事实；数据库锁和唯一约束共同防止超卖。
- 过期锁、支付超时、退款失败、场次取消和回调延迟都必须有补偿任务或人工处理状态。
- 不能以“收到支付回调”直接创建考试记录，只能推进订单和凭证状态。

### 10.5 性能与可靠性目标

以下是设计目标，不是当前已测结果：

| 场景 | 设计目标 |
|---|---|
| 同一场次并发抢最后名额 | 100 个并发请求下不超卖，最终确认数不超过容量 |
| 可用场次查询 | 常规筛选 p95 ≤ 500ms（不含第三方支付） |
| 团队 2,000 行预检 | 返回批次和错误摘要，不在 HTTP 请求内同步创建学员；目标 p95 ≤ 10s |
| 支付回调 | 重复回调和乱序回调不破坏订单终态；单事件可重试 |
| 服务重启 | 订单、支付、锁、成员和考试凭证状态从 MySQL 恢复；Redis 丢失不产生永久库存 |

### 10.6 时间与保留

- 所有服务端时间按 Asia/Shanghai 业务时区展示和判定，数据库仍使用统一 `DATETIME(3)`。
- 订单、支付、退款、导入批次、签到和考试凭证按审计和财务要求保留；不因前端取消而物理删除。
- 过期锁、临时预检文件和通知投递记录按配置清理，但保留事件摘要和失败原因。

## 11. 与现有系统的集成边界

### 11.1 可复用对象

| 现有对象 | 复用方式 |
|---|---|
| `sys_user` | 个人学员和团队成员账号；新增组织管理员用业务角色和组织关系隔离 |
| `training_category` | 产品的培训类别来源；停用类别阻止新产品/订单，不改历史 |
| `learner_identity` | 需要实名的考试产品使用；预约不自行复制身份证加密事实 |
| `import_batch` | 增加 `booking_participants` kind 和 `booking_order_id`，复用预检/确认幂等协议 |
| `media_asset` / `media_reference` | 保存 Excel/TXT 原文件及错误导出 |
| `paper_release` | 场次/产品绑定不可变考试卷发布版本 |
| `exam_assignment` / `exam_record` | 预约只生成资格桥接；开考时按现有考试事务生成或恢复 |
| `sys_role` / `sys_permission` / `audit_log` | 权限和审计沿用现有 RBAC 与审计链 |

### 11.2 不复用的旧医疗事实

以下对象只作为参考，不进入当前培训数据模型：`ZyBookInfo`、治疗单、患者就诊卡、治疗师、科室治疗资源、医疗黑名单、微信患者绑定。培训系统应使用 `booking_*` 命名，避免把医疗语义扩散到课程和考试模块。

### 11.3 考试侧改动边界

预约不得改写现有 `paper_release` 快照、题单、答案或成绩。建议只增加：

1. 产品可选 `paper_release_id`；
2. 新增 `booking_exam_ticket`；
3. `TrainingExamsController.start` 增加预约守卫；
4. 管理端考试记录继续只读投影，增加预约订单/场次筛选，但不把预约状态并入 `exam_record.status`。

### 11.4 推荐实现顺序

```text
G0 业务口径与支付/退款决策
  ↓
G1 产品、地点、场次、容量和个人预约
  ↓
G2 团队组织、Excel/TXT 预检与批量分配
  ↓
G3 支付回调、退款、签到和通知
  ↓
G4 booking_exam_ticket 与考试开考守卫
  ↓
G5 对账、报表、并发压测、浏览器/H5/真实支付验收
```

G1—G4 都是完整预约闭环的必要部分；G5 是交付验收，不得用源码静态检查代替真实支付、并发和移动端验收。

## 12. 验收场景与证据等级

### 12.1 P0 自动化验收

| 场景 | 必须证明 |
|---|---|
| 个人支付后选场次 | 未支付不可选；支付回调幂等；成功后只占一个名额 |
| 最后一个名额并发 | 不超卖；失败请求没有成员、凭证或考试次数副作用 |
| 个人取消/退款 | 状态机正确；名额释放；退款失败可重试；历史订单保留 |
| 团队 Excel/TXT 预检 | 合法/非法/重复/待绑定行正确；预检不创建用户和名额 |
| 团队批次确认 | 只确认通过行；同批重复确认返回同结果；不同集合冲突 |
| 团队多场次分配 | 容量不足整批失败或明确进入调整态，不静默拆分 |
| 支付回调乱序 | 重复、迟到、金额不一致事件不破坏终态 |
| 场次取消 | 已确认成员进入改签/退款；已完成考试记录不变 |
| 考试入口 | 无凭证/未签到/已退款/非时间窗口不能开考；不消耗次数 |
| 组织数据隔离 | 企业 A 不能读企业 B 的订单、名单、支付或成员状态 |

### 12.2 手工和真实验收

- PC 管理端：产品、地点、场次、容量、名单预检、场次分配、签到和报表。
- 学员 H5/小程序：支付页面、支付回调、选场次、预约凭证、取消和考试入口。
- 企业管理员：模板下载、Excel/TXT 上传、错误导出、成员状态和多场次分配。
- 真实支付供应商：签名、金额、超时、退款、重复通知和网络失败。
- 真实设备/浏览器：文件选择、支付跳转、回调返回、二维码/凭证和弱网恢复。

源码、自动化测试、桌面浏览器和本地 Mock 不能扩大为真实支付、真实企业批量导入、真实手机端或生产部署已通过。

### 13.2 需要产品确认的九个口径

本册已经给出推荐默认值；以下选择会改变后续实现范围，应在写 migration/API 前确认。若暂时没有决定，可以先按“推荐默认”实现，并把策略配置化：

1. **首发支付渠道**：推荐个人先接线上微信支付，团队同时支持线上统一支付和线下财务确认；同一订单第一次进入已支付后不允许切换支付渠道。
2. **取消与退款**：推荐个人在场次开始前 24 小时全额退款；团队在预约截止前允许成员级替换/取消，截止后由运营处理；已签到成员不自动退款。
3. **企业开通方式**：推荐由平台管理员创建或邀请企业，组织管理员通过邀请激活；`booking_org_member` 支持一人多组织，但每次请求只有一个 active 组织上下文。
4. **未匹配账号成员**：推荐计入有效名单、订单人数和名额，但必须激活/绑定账号后才可签到和生成考试资格；长期未激活由企业在截止前替换或由运营处理。
5. **多场次与成员变更**：推荐一个团队订单允许多个场次，每名成员同一时间只能有一个 active 场次；支付后增删成员或换场次必须通过运营/组织管理员的受控变更接口，产生补款或退款，不静默改金额。
6. **机构取消场次**：推荐先提供候选场次改签，组织管理员/个人在 48 小时内选择；无法改签或逾期未选择时全额退款，原考试凭证失效并记录原因。
7. **考试准入**：推荐现场考试产品签到为硬门槛，默认允许提前 30 分钟签到、开场后 15 分钟内迟到签到；远程产品通过产品配置关闭签到硬门槛，实名仍在开考前完成。
8. **重复预约与重考**：推荐同一学员不能同时持有同产品重叠场次；已完成或已取消订单可再次购买；一张预约凭证只绑定一个场次，考试重考仍沿用当前试卷的 `max_attempts` 规则。
9. **数据保留**：推荐原始 Excel/TXT 按可配置期限清理，支付事件和审计记录按机构财务/隐私政策保留；开发默认值只用于测试，不代表法律或财务合规期限，正式上线前必须由机构确认。
