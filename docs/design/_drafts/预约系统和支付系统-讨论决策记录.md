## 2 本轮已确认的决定

### D01 培训与考试分开预约 已经 D10 和 D19 澄清

- 状态：历史决定，当前以 D19 的“培训预约自动绑定考试预约、考试可单独改期”为准。
- 确认日期：2026-10-28。
- 用户原话：“培训和考试分别选择时间、分别预约”。
- 适用范围：398 元培训加考试套餐。
- 原需求含义：培训和考试各自选择时间、分别预约。后续 D08 明确要求398元套餐在同一天完成，不能再按任意两天设计。
- 变化原因：用户补充现场运营安排，培训加考试集中在指定工作日，当天完成两项。
- 当前处理：按 D19，初次预约培训时自动绑定考试预约；培训和考试分别记录、关联展示，培训后可单独改考试时间。

### D02 培训与考试独立 不以完成培训为考试条件

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户原话：“两者独立，不以培训完成作为考试条件”。
- 需求含义：考试预约不需要等待培训完成；考试也不因为尚未参加或完成套餐内培训而被阻止。不规定先培训后考试的顺序。
- 取代的设想：必须完成培训后才能预约或参加套餐内考试。
- 边界：这不是取消实名、缴费、预约时间、现场签到等其他条件的授权；这些条件分别讨论。也不据此直接修改现有其他试卷的考前学习配置。
- 后续约束：D08、D10初次按当天安排；D19明确培训后考试可单独改期。当天先后顺序、培训完成是否作为开考校验仍需结合安排核对，不自行恢复学习门槛。
- 待继续明确：此前会议提到“不通过后重新学习再考”，补考是否存在单独要求；不得用这一尚未澄清的片段重新推导首次考试的培训门槛。

### D04 企业联系人自行办理团队报名和预约

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户原话：“企业联系人自己登录上传名单、安排预约”。
- 需求含义：需要面向企业联系人的登录与操作入口，支持上传成员名单、安排培训和考试预约。
- 取代的设想：首期只由机构工作人员接收名单并代办，企业自助后置。
- 设计边界：企业联系人仅能处理获授权企业的报名与预约信息，不获得机构后台的全量学员、财务或题库权限。团队付款已由后续 D05 确认为企业统一付款。
- 待继续明确：联系人变更和班组联系人授权；入口终端按 D12 确认为首期 PC，企业账号开通方式按 D13 已确认。

### D05 团队报名由企业统一付款

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户原话：“肯定是也需要支持企业统一付款，不考虑员工各自付款。”
- 需求含义：企业联系人上传名单、安排团队预约，费用由企业统一支付；团队成员不分别支付对应报名费用。
- 取代的设想：企业仅代报名、员工到现场各自缴费；团队订单同时提供成员分开付款。
- 范围：本决定针对团队报名，不取消个人自行报名、个人付款的既有需求。
- 设计影响：团队订单需要关联成员明细及各人的培训／考试安排；成员端不出现该团队报名的个人待付款入口，也不能重复收取相同费用。
- 待继续明确：成员变更与已使用部分服务的退款规则。企业按未参加成员退款已由 D18 确认；收款方式按 D14，付款先后按 D06，统一付款不自动意味着支持分期或月结。

### D06 企业先提交名单 再统一付费 之后自行预约

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户原话：“按照我提供的模板，先把你公司的那些人，比如手机号码、身份证、人名这些提交完成之后，就可以付费。付费完之后，他自己去预约模块预约就可以了。”
- 明确流程：企业联系人登录 → 按模板上传并提交成员名单 → 企业统一付款 → 进入预约模块安排培训／考试。
- 名单处理：交互参考现有学员管理，模板包含手机号、身份证号、姓名等报名信息；提交名单不等于已付款或已预约，也不等于成员已经完成本人实名认证。
- 取代的设想：先选场次、临时占位再付款确认；团队先预约后现场缴费。
- 范围：本条针对企业团队流程；个人报名已由后续 D09 单独确认同样先付款后预约。
- 待继续明确：企业一次为整批还是选定成员缴费、付款后的增减成员处理；同一批已付款成员可分批预约已按 D11 确认。

### D07 曾提出不限名额 不限名额部分已被 D08 替代

- 状态：历史决定；人数不限的部分已被 D08 明确替代，不能作为当前要求。
- 确认日期：2026-10-28。
- 用户原话：“没有所谓的锁住名额，不需要，不限名额。”
- 当时含义：不设人数上限，不做锁位、余量或满额控制。
- 后续修正：用户在 D08 明确有每日人数及预约时间段限制，并给出60人、100人的配置示例，恢复人数上限和满额判断。
- 仍保留的简化：不采用“付款前先锁名额、超时释放”的购买流程；先付款，后提交预约，提交时检查当前可约人数。候补功能尚未纳入。

### D08 按套餐区分预约场次 配置时间与人数 初次培训绑定当天考试

- 状态：服务分类和人数规则已确认；同日安排经 D19 补充考试改期例外。
- 确认日期：2026-10-28。
- 用户原话要点：“本机构的是购买了398元考试套餐的，套餐包考试和培训，他要在一天之内做完培训和考试。外来的只付了98，只考试。”“现场只容纳60人，是本机构角色的当天名额。”“只报名考试的，可能可以容纳100人。”“这些预约配置都是可以灵活配置的”。
- 两类人员按本次购买服务区分：398元为本机构培训加考试；98元为外来单独考试。此处“角色”是业务分类，不等于企业联系人或机构管理员的操作权限。
- 398元初次预约培训时绑定当天考试；后续 D19 明确，参加培训但有事未考试可以单独改考试时间，不能继续把同一天作为绝对限制。
- 预约有限定日期、时间段和人数上限。后台可配置开放的工作日、具体日期／时段、服务类型、适用人员及人数。
- 用户示例：周一、三、五开放考试场；周二、四开放本机构培训加考试场。98元人员不能选择周二、四这种套餐场。
- 人数示例：培训加考试日为60人，单独考试日可配置为100人。星期安排和人数均为示例，不硬编码为永久规则。
- 按后续 D26，时间段灵活配置，每日总名额不固定均分给各时段；当前不另设每时段人数上限。同日多时段不能把每日60人误放大成每时段各60人，100人的考试日额度也不等于同一时刻坐100人。
- 预约人数按实际成员计数，企业一批多人不能只算一个名额；提交预约需检查当前上限，已经付款不保证任何指定日期必有空位。
- 替代关系：明确替代 D07 的不限名额；收紧 D01 为同一天完成。个人／企业先付款的规则不变，不恢复付款前临时锁位流程。
- 后续确认：当天连续重考按 D24，398元已参加培训后可以选择单独考试场按 D25。已有学员来源字段与本次购买分类如何衔接仍待确定，不直接覆盖历史数据。

### D09 个人报名先付款再预约

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户原话：“个人报名是也统一采用 先付款、再预约”。
- 明确流程：个人选择服务并完成报名资料 → 付款 → 选择符合所购服务的日期和时段 → 提交预约。
- 与企业 D06 保持相同付款顺序；企业多了模板提交名单和统一付费环节。
- 取代的设想：个人先预约后缴费、先保留预约到现场再缴费。现场收款若保留，也必须先确认付款再预约，具体收款方式另行决定。

### D10 398元初次一次操作安排培训考试 后经 D19 澄清为关联预约

- 状态：初次联动安排保留；合并成一条不可拆分预约的理解已被 D19 纠正。
- 确认日期：2026-10-28。
- 确认问题：“398 元学员只预约一次培训考试日，当天的培训和考试由机构统一安排，不再分别预约两次。这样理解对吗？”
- 用户答复：“是的”。
- 当前含义：初次预约培训自动绑定当天考试，操作可以联动，但培训和考试预约分别保留，参加培训后可单独修改考试预约，按 D19 执行。
- 人数口径：一名学员计入当天套餐场的一人名额，不因为包含培训和考试而重复计成两人；企业多人按实际成员数计数。
- 替代关系：替代 D01 的分别预约；明确 D08 的当天完成要求如何体现在预约操作中。
- 边界：只确定同日整套安排，不擅自确定上午培训／下午考试、培训完成校验、缺席或部分使用后的退款政策。

### D11 企业已付款成员可以分批预约不同日期

- 状态：已确认。
- 确认日期：2026-10-28。
- 确认问题：“企业一次为50人付费后，是否允许分批预约，例如30人约周二、20人约周四？”
- 用户答复：“可以”。
- 需求含义：同一批已付款成员可以按人员分批选择不同的适用日期／场次，不要求全体同一天到场。
- 设计影响：企业选择本次安排的成员后提交预约；每位成员分别关联自己的预约，尚未安排者显示为已付款待预约。不能因为部分人已预约，就把全批标成已安排完毕。
- 边界：各批仍遵守服务类型、日期／时段和人数限制；同一笔已付服务不因分批安排而重复收费。分批指不同成员在不同日期参加；同一学员培训后的考试改期另按 D19 执行。

### D12 企业首期使用 PC 三个功能 员工在小程序查看预约

- 状态：已确认。
- 确认日期：2026-10-28。
- 确认方案：“企业入口建议先放在 PC，提供三个功能：成员名单、统一缴费、预约安排；员工在小程序查看自己的预约。”
- 用户答复：“可以”。
- 需求含义：企业联系人在 PC 上传和管理本企业名单、统一缴费、分批安排预约；员工在小程序查看自己的日期、时段和安排，不承担团队费用。
- 范围：首期不建设企业联系人在小程序批量上传和安排团队的功能；个人自行报名、付款、预约仍保留在移动端。
- 边界：此决定确认功能分工，不等于批准整套机构管理端菜单，也不决定独立域名或单独应用。企业只能看到获授权企业的信息；企业账号开通方式由后续 D13 确定。
- 待继续明确：联系人变更与班组授权；员工能否自行修改企业安排的预约。

### D13 企业账号由机构后台开通

- 状态：首期已确认。
- 确认日期：2026-10-28。
- 用户确认：企业账号先由机构后台开通，填写企业名称、联系人和手机号，联系人再登录使用。
- 需求含义：机构工作人员在后台登记上述三项信息并开通对应企业联系人的账号；联系人登录 PC 企业入口后，管理本企业名单、统一缴费和预约。
- 首期范围：不开放企业自行注册，不增加企业注册申请及审核流程。
- 边界：开通企业账号不授予机构管理员权限；具体登录验证方式、联系人更换方式留待后续设计，不在本条中假定密码或验证码方案。

- 微信支付流程：企业在 PC 缴费入口获取微信支付二维码，扫码付款；确认到账后，订单记为已付款，企业可为对应成员预约。
- 对公转账流程：企业按机构提供的对公账户转账，运营人员核实到账并在后台确认付款成功；确认前保持未确认到账，确认后才可预约。
- 后台影响：缴费订单需要区分微信支付和对公转账，提供运营确认到账的操作，并记录确认人、时间、金额和对应订单，便于查询。
- 设计建议：微信支付二维码与具体订单关联，到账结果由系统核实；对公转账记录对应订单和转账依据。二维码生成方式、凭证提交形式在详细设计时确定，不把用户已批准两种方式等同于已确定接口方案。
- 边界：当前明确的是企业付款渠道，不据此自动开放个人对公转账、分期、月结或员工替团队分开付款。两种付款方式均不改变先付款后预约的顺序。

### D23 进行中显示本次序号 最后一次结束才显示次数用尽

### D24 当天未通过可以立即连续考试 不必每次重新预约

- 状态：已确认。
- 确认日期：2026-10-28。
- 确认问题：“学员当天第一次没通过，可以当场再考下一次，还是每次重考都需要重新预约？”
- 用户原话：“可以连续考的，第一次没通过，马上就可以考第二次。”
- 需求含义：当天已安排考试的学员，前一次未通过且仍有剩余次数，可以主动再次开始下一次考试，无须等待其他日期或为每次重考重新预约。
- 衔接规则：沿用原预约；同一人在原预约内连续重考，不按考试次数重复计算当天预约人数。每次正式新开考仍消耗一次机会，生成自己的考试记录并按规则重新抽题；查看结果后不自动替学员开考。
- 替代的备选：每次失败后必须重新预约才能再次开考。
- 边界：未取消实名、剩余次数等条件；连续重考不增加套餐机会。当天营业／开考窗口怎样约束仍需明确，不能解释为可以越过运营时间无限开考。改到其他日期时的场次选择和预约规则另议。

### S04 预约 支付 到场和考试分别记录

缴费、预约、到场和考试结果分别记录。398元按 D19 初次预约培训时自动绑定当天考试，培训和考试分别保留。398元包含1次培训，98元不含培训；两者考试次数按 D22 读取关联试卷配置，当前默认3次。

```text
398 元套餐 → 付款 → 培训预约 → 自动绑定当天考试预约（有名额上限）
    ├── 参加培训 → 保留培训完成记录
    └── 考试预约 → 当天考试，或培训后有事单独改考试时间
                      └── 配置次数用尽且未通过 → 重新购买98元或398元套餐

98 元单独考试（次数取试卷配置，默认3次） → 付款 → 选择单独考试场（有名额上限）
    └── 现场考试 → 现有考试记录

缴费订单负责记录钱；预约记录负责安排时间；考试系统负责答题和成绩。
```

取消或改期不等于退款。D21已确认398元由300元培训费和98元考试费组成，但 D19仍规定参加培训后不退款、可改考试预约；费用可以分项展示，不等于允许分项退费。

### S05 失败记录与下一次考试同屏展示 旧备选 当前推荐见 S06

核对依据：[正在实施的随机考试设计](../../superpowers/specs/2026-10-28-shared-random-exam-design.md)第1、6、7、9节。仅阅读该设计及当前工作区状态，没有把文档状态等同于代码或运行验收完成。

已有设计约定：最多次数由试卷配置；成功开始考试才计次，超时未交卷也计次；进行中恢复不换题、不计新次数；学员明确再次开始才生成新记录并重新抽题；跨次允许重题；同一学员同一试卷首次开考冻结来源、发布版本与规则，撤回重发不重置次数；已及格也可在剩余次数内重考。

此前助手建议供比较；其中双记录展示已不作为当前推荐，其他考试与支付衔接问题仍保留：

1. **一项考试下显示多次记录**：PC仍只配置和发布一项随机考试，不因每次失败新增一张后台试卷。H5在同一考试下同时展示“第1次未通过—查看详情”和“第2次待考试—开始考试／去预约”。更多历史可进入全部考试记录。
2. **先出现入口 点击才抽题**：失败且仍有剩余次数时显示下一次待考入口，不在交卷后自动开始下一场，不提前计次或启动倒计时。点击开始并通过付款、预约、实名等检查后才抽题并保存。此方式与正在实施设计更一致；若坚持失败即预生成题目，需要另设计待开考状态，不能借用已开始考试记录。
3. **重新抽题不等于每道题都不重复**：原设计允许跨次重题。若需要增强差异，可优先抽此前未考过的题，不够时补抽旧题；这是新增建议，尚未确认。若要求跨次完全不重复，需要按题型、难度准备足够题量并明确缺题时怎么办，不能直接承诺一定全新。
4. **查看失败详情保持历史**：展示该次成绩、作答等历史信息，不允许重新提交或覆盖；是否显示完整答案解析继续沿用考试结果查看权限，不在本轮扩大。
5. **下一次入口与预约衔接**：按后续 D24，当天未通过且有次数可以立即再考，不要求每次重考重新预约；另一天考试仍需衔接预约。只保留一个当前待考／进行中入口，刷新和重复点击不生成多个考试。

支付融合还需裁决：

- 建议付费页面读取关联已发布试卷的次数配置，并保存购买时承诺的次数；后续管理员改配置不静默减少已购买机会。现行考试设计在首次开考冻结规则，两者的版本和次数必须统一。这是建议，尚未确定冻结时点。
- 建议重新购买产生新一轮付费考试机会并保留旧记录。但现行设计是同一学员同一试卷累计次数，仅新增支付订单不会解除原上限；必须补充购买与考试轮次的关联，不能通过修改旧次数或复制后台试卷绕过。
- 用户说按套餐区分本机构／外来，正在实施的考试设计按服务端学员来源冻结难度；重新购买98元后的来源、难度和历史归属需明确，不能在付款后直接覆盖旧记录。
- 原设计允许已通过仍继续考试；本轮只讨论失败后的入口，不自动推导为“通过后禁止重考”。

### S06 现有考试卡片显示次数 经考试须知后开考

- 状态：保留单卡片为当前推荐；进行中和次数用尽的具体文案已按 D23 确认；不代表界面已实现。
- 用户提供现有考试Tab截图，建议在时长、题数、满分这一行增加考试机会；每次使用后减少，进入考试须知后，点击开始考试才抽题。
- 展示：一项已发布考试继续对应一张卡片；待开考时显示“剩余N次”，答题中按 D23 显示“第N次考试，共M次”。次数来自试卷配置和本人记录，不写死3次，必要时换行。
- 流程：考试卡片 → 考试须知 → 明确点击开始考试 → 服务端检查条件、抽题并成功建立本次考试 → 使用次数加1、剩余次数减1。进入列表／须知、预约、刷新、开考失败不扣次数。
- 进行中：显示“第N次考试，共M次”和“继续答题”，恢复同一份题目和截止时间，不重抽、不再扣次数。最后一次也可继续当前考试，不以“剩余0次”替代当前考试信息。
- 考试结束：本次失败且仍有次数时，同一张卡片提供“再次考试”及“查看记录”；下一次仍先进入考试须知。次数用尽且无进行中考试时按 D23 显示“考试次数已用完”，保留记录查询。
- 当天重考：按 D24 允许马上再次考试，不额外插入重新预约步骤；通过须知主动开考，仍检查剩余次数并生成新的题单。
- 历史：每次考试各自保留题单、答案和成绩，从“查看记录”进入历史详情，不新增一张待考试卷卡，也不复制PC后台试卷。
- 筛选：不能把一次失败等同于整项考试彻底结束，导致有剩余机会却没有重考入口。已通过后是否继续重考暂沿用正在实施设计，不在此变更。
- 示例：上限3次，未开考显示剩余3次；首次开考显示第1次／共3次，后台剩余新开考机会为2；首次失败后显示剩余2次；第三次进行中显示第3次／共3次并可继续，第三次结束才显示考试次数已用完。
- 与 S05 的关系：用本方案替代双记录卡展示建议；不改变当前设计中“每次新开考随机抽题、进行中恢复不换题”的机制。是否减少跨次重题，以及重新购买如何恢复新一轮机会，继续单独讨论。
