## 2 本轮已确认的决定

### D01 培训与考试分开预约 已经 D10 和 D19 澄清

- 状态：历史决定，当前以 D19 的“培训预约自动绑定考试预约、考试可单独改期”为准。
- 确认日期：2026-10-28。
- 用户原话：“培训和考试分别选择时间、分别预约”。
- 适用范围：398 元培训加考试套餐。
- 原需求含义：培训和考试各自选择时间、分别预约。后续 D08 明确要求398元套餐在同一天完成，不能再按任意两天设计。
- 变化原因：用户补充现场运营安排，培训加考试集中在指定工作日，当天完成两项。
- 当前处理：按 D19，初次预约培训时自动绑定考试预约；培训和考试分别记录、关联展示，培训后可单独改考试时间。

### D02 培训与考试独立 不以完成培训为考试条件

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户原话：“两者独立，不以培训完成作为考试条件”。
- 需求含义：考试预约不需要等待培训完成；考试也不因为尚未参加或完成套餐内培训而被阻止。不规定先培训后考试的顺序。
- 取代的设想：必须完成培训后才能预约或参加套餐内考试。
- 边界：这不是取消实名、缴费、预约时间、现场签到等其他条件的授权；这些条件分别讨论。也不据此直接修改现有其他试卷的考前学习配置。
- 后续约束：D08、D10初次按当天安排；D19明确培训后考试可单独改期。当天先后顺序、培训完成是否作为开考校验仍需结合安排核对，不自行恢复学习门槛。
- 待继续明确：此前会议提到“不通过后重新学习再考”，补考是否存在单独要求；不得用这一尚未澄清的片段重新推导首次考试的培训门槛。

### D04 企业联系人自行办理团队报名和初次预约 经D40确认继续有效

- 状态：已确认；D39的相反理解已经D40纠正。
- 确认日期：2026-10-28。
- 用户原话：“企业联系人自己登录上传名单、安排预约”。
- 当前含义：需要面向企业联系人的登录与操作入口，支持上传成员名单、办理报名、统一付款，并为同批员工批量安排初次培训和考试预约；员工只负责预约成功后的个别改期。
- 取代的设想：首期只由机构工作人员接收名单并代办，企业自助后置。
- 设计边界：企业联系人仅能处理获授权企业的成员、报名、付款和初次预约，不获得机构后台的全量学员、财务或题库权限。团队付款已由后续D05确认为企业统一付款。

### D05 团队报名由企业统一付款

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户原话：“肯定是也需要支持企业统一付款，不考虑员工各自付款。”
- 需求含义：企业联系人上传名单、办理团队报名和初次预约，费用由企业统一支付；团队成员不分别支付对应报名费用。预约成功后的个别改期按D40由员工本人完成。
- 取代的设想：企业仅代报名、员工到现场各自缴费；团队订单同时提供成员分开付款。
- 范围：本决定针对团队报名，不取消个人自行报名、个人付款的既有需求。
- 设计影响：团队订单需要关联成员明细及各人的培训／考试安排；成员端不出现该团队报名的个人待付款入口，也不能重复收取相同费用。
- 后续边界：付款后成员不能换人，按D42执行；新增成员重新报名付款，未使用成员退款按D18。已参加培训后的退款按D19，其他使用情形继续按退款规则讨论。收款方式按D14，付款先后按D06，统一付款不自动意味着支持分期或月结。

### D06 企业先提交名单再统一付费 然后批量初次预约

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户原话：“按照我提供的模板，先把你公司的那些人，比如手机号码、身份证、人名这些提交完成之后，就可以付费。付费完之后，他自己去预约模块预约就可以了。”
- 当前流程：企业联系人登录 → 按模板上传并提交成员名单 → 办理报名并统一付款 → 为选定成员批量安排初次培训／考试预约 → 员工本人到场；个别员工后续改期按D40自行处理。
- 名单处理：交互参考现有学员管理，模板包含手机号、身份证号、姓名等报名信息；提交名单不等于已付款或已预约，也不等于成员已经完成本人实名认证。
- 取代的设想：先选场次、临时占位再付款确认；团队先预约后现场缴费。
- 范围：本条针对企业团队流程；个人报名已由后续 D09 单独确认同样先付款后预约。
- 待继续明确：企业一次为整批还是选定成员缴费、付款后的增减成员处理；企业可以按D11将同批成员分批安排，也可以按D40一次预约到相同时间。

### D08 按套餐区分预约场次 配置时间与人数 初次培训绑定当天考试

- 状态：服务分类和人数规则已确认；同日安排经 D19 补充考试改期例外。
- 确认日期：2026-10-28。
- 用户原话要点：“本机构的是购买了398元考试套餐的，套餐包考试和培训，他要在一天之内做完培训和考试。外来的只付了98，只考试。”“现场只容纳60人，是本机构角色的当天名额。”“只报名考试的，可能可以容纳100人。”“这些预约配置都是可以灵活配置的”。
- 两类人员按本次购买服务区分：398元为本机构培训加考试；98元为外来单独考试。此处“角色”是业务分类，不等于企业联系人或机构管理员的操作权限。
- 398元初次预约培训时绑定当天考试；后续 D19 明确，参加培训但有事未考试可以单独改考试时间，不能继续把同一天作为绝对限制。
- 预约有限定日期、时间段和人数上限。后台可配置开放的工作日、具体日期／时段、服务类型、适用人员及人数。
- 用户示例：周一、三、五开放考试场；周二、四开放本机构培训加考试场。98元人员不能选择周二、四这种套餐场。
- 人数示例：培训加考试日为60人，单独考试日可配置为100人。星期安排和人数均为示例，不硬编码为永久规则。
- 按后续 D26，时间段灵活配置，每日总名额不固定均分给各时段；当前不另设每时段人数上限。同日多时段不能把每日60人误放大成每时段各60人，100人的考试日额度也不等于同一时刻坐100人。
- 预约人数按实际成员计数，企业一批多人不能只算一个名额；提交预约需检查当前上限，已经付款不保证任何指定日期必有空位。
- 替代关系：明确替代 D07 的不限名额；收紧 D01 为同一天完成。个人／企业先付款的规则不变，不恢复付款前临时锁位流程。
- 后续确认：当天连续重考按 D24，398元已参加培训后可以选择单独考试场按 D25。已有学员来源字段与本次购买分类如何衔接仍待确定，不直接覆盖历史数据。

### D09 个人报名先付款再预约

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户原话：“个人报名是也统一采用 先付款、再预约”。
- 明确流程：个人选择服务并完成报名资料 → 付款 → 选择符合所购服务的日期和时段 → 提交预约。
- 与企业 D06 保持相同付款顺序；企业多了模板提交名单和统一付费环节。
- 取代的设想：个人先预约后缴费、先保留预约到现场再缴费。现场收款若保留，也必须先确认付款再预约，具体收款方式另行决定。

### D10 398元初次一次操作安排培训考试 后经 D19 澄清为关联预约

- 状态：初次联动安排保留；合并成一条不可拆分预约的理解已被 D19 纠正。
- 确认日期：2026-10-28。

- 已开始边界：如果培训已经开始或已记录参加，按D19只允许调整尚未开始的考试，不恢复培训机会；如果某次考试已经开始，不允许通过改期逃避该次考试，先按现有交卷、超时和恢复规则结束该次尝试。
- 收费边界：改期不触发退款，也不新增收费；退款仍按D16至D19的独立规则处理。

### D38 已签到后改期不回补原日期名额

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户场景：当天约满60人且60人都已到场，其中2人临时离开并改期；这2人已经占用了当天接待能力，不需要再把当天名额释放出来。
- 简化规则：已签到人员改期时，原日期的已约人数和已到人数作为历史事实保留，不回补可约余量，也不触发候补、补位或重新开放当天预约。
- 当天预约：学员预约页面不提供当天的新预约，只展示下一天及之后的可约日期。因此即使当天有人离开，也不会再有人临时补约当天。
- 新日期：改期只需检查目标日期是否仍有名额；成功后占用目标日期名额，并在目标日期重新签到。
- 结构影响：不需要设计复杂的“签到后释放、重新抢位、候补递补”状态机。当天统计保留原预约数、签到数和实际服务结果即可。
- 范围：本条针对已经签到后再改期；尚未签到且预约日期仍在未来的普通改期，可以按当前有效预约数重新计算余量，不影响本条的简化原则。

### D39 企业付款后全部由员工办理 是一次错误理解

- 状态：已被D40明确替代，不作为当前要求。
- 形成原因：助手把“企业完成报名付款后，员工自己改期”错误扩大成“企业不做初次预约，员工从头自行预约”。
- 保留价值：员工本人负责个别改期、签到、培训和考试仍然成立；企业不替员工签到或答题也仍然成立。
- 被纠正部分：企业付款后仍要为同批员工完成批量初次预约，可以统一预约相同日期和时段；不能再引用本条要求所有员工逐个自行预约。

### D40 企业批量初次预约 员工自行改期

- 状态：已确认，纠正D39并恢复D04、D06、D11、D12中的企业预约职责。
- 确认日期：2026-10-28。
- 用户确认：企业付款成功后，可以给同一批员工预约到相同时间；员工不需要自己完成初次预约，只需按预约到场。预约成功后如需改期，由员工本人操作。
- 企业PC职责：导入成员 → 办理团队报名 → 统一付款 → 选择已付款成员 → 批量选择一个可约日期和时段 → 提交初次预约。一次可以为多人安排相同时间，也可以按D11分批安排。
- 员工移动端职责：查看企业已经安排好的预约；到场后本人完成签到、培训和考试。若个人无法按原日期参加，由本人把自己的预约改到其他可约日期，不需要企业代办。
- 批量预约结果：虽然企业一次提交多人，每位员工仍生成自己的预约记录，便于个人查看、签到和单独改期；不能只生成一条无法拆分的“企业总预约”。
- 改期权限：员工只能修改自己的预约，不能修改同批其他成员；企业初次预约后不负责个别改期。机构运营人员的异常处理能力另行受后台权限控制。
- 付款边界：员工不重复付款；只有企业订单确认已付款的成员才能被企业批量预约。
- 简化后的流程：

```text
企业导入成员、报名并统一付款
  → 企业为同批员工批量安排初次预约
  → 员工查看预约并按时到场
  → 个别员工如有变化，由本人自行改期
  → 员工本人签到、培训和考试
```

### D41 企业负责线下通知 学员端统一查看预约和改期

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户确认：企业预约成功后由企业自己通知员工，不需要系统再设计通知方式；企业导入名单后，该人员已经存在于系统中，可以登录学员端查看预约并改期。
- 通知边界：首期不建设预约成功短信、微信公众号模板消息、小程序订阅消息、App推送或运营电话任务。系统保存并展示预约事实，企业负责把到场安排告知本企业员工。
- 导入衔接：企业名单导入后，为每名成员建立或关联现有学员记录；不能只把姓名保存在企业订单明细中，导致员工登录学员端后找不到自己的服务和预约。
- 企业员工入口：员工登录学员端后查看企业已安排的预约，不需要重复报名或付款；本人可以进入预约详情修改自己的日期，不能查看或修改同批其他成员。
- 个人用户入口：个人参加考试或培训时，仍按D09在学员端自行选择服务、付款、预约；预约成功后也在同一个“我的预约”入口查看和改期。
- 统一模型：无论预约来自个人自己提交还是企业批量提交，最终都形成归属于具体学员的个人预约记录；来源只影响付款人和初次预约操作人，不影响员工本人查看、签到和改期。
- 账号安全：员工登录后只能通过本人账号和实名关系读取自己的学员记录，不能仅凭姓名或手工输入身份证号查看预约；具体登录激活方式沿用学员端账号体系，在实施设计中核对。

### D42 企业成员资格不能换人 只能申请退款

- 状态：已确认。
- 确认日期：2026-10-28。
- 用户确认：企业付款后不能把名额换给其他员工；原成员不参加时，只能由企业自己走退费。
- 禁止换人：不提供“替换成员”“转让名额”“修改身份证后沿用付款”或把甲的预约直接改成乙的功能。服务资格、付款明细和预约始终归属于原订单中的原成员。
- 退款申请人：企业统一付款的订单，只能由企业联系人对指定成员发起部分退款申请；员工本人可以改期，但不能发起企业订单退款，也不能把资格送给其他人。
- 退款条件：继续按D16至D19判断是否可退。尚未使用服务的成员可申请全额退；已经参加培训等不可退款情形不会因为企业提出换人而例外。
- 新员工处理：企业若要增加另一名员工，按新增成员重新报名、确认服务并付款，再为其安排预约；不能用原成员退款中的金额或名额直接顶替。
- 历史保留：退款后原成员、原付款明细、原预约和退款记录继续保留，不通过删除成员来伪装成从未报名。

### S04 预约 支付 到场和考试分别记录

缴费、预约、到场和考试结果分别记录。398元按 D19 初次预约培训时自动绑定当天考试，培训和考试分别保留。398元包含1次培训，98元不含培训；两者考试次数按 D22 读取关联试卷配置，当前默认3次。

```text
398 元套餐 → 付款 → 培训预约 → 自动绑定当天考试预约（有名额上限）
    ├── 参加培训 → 保留培训完成记录
    └── 考试预约 → 当天考试，或培训后有事单独改考试时间
                      └── 配置次数用尽且未通过 → 重新购买98元或398元套餐

98 元单独考试（次数取试卷配置，默认3次） → 付款 → 选择单独考试场（有名额上限）
    └── 现场考试 → 现有考试记录

缴费订单负责记录钱；预约记录负责安排时间；考试系统负责答题和成绩。
```

取消或改期不等于退款。D21已确认398元由300元培训费和98元考试费组成，但 D19仍规定参加培训后不退款、可改考试预约；费用可以分项展示，不等于允许分项退费。

### S05 失败记录与下一次考试同屏展示 旧备选 当前推荐见 S06

核对依据：[正在实施的随机考试设计](../../superpowers/specs/2026-10-28-shared-random-exam-design.md)第1、6、7、9节。仅阅读该设计及当前工作区状态，没有把文档状态等同于代码或运行验收完成。

已有设计约定：最多次数由试卷配置；成功开始考试才计次，超时未交卷也计次；进行中恢复不换题、不计新次数；学员明确再次开始才生成新记录并重新抽题；跨次允许重题；同一学员同一试卷首次开考冻结来源、发布版本与规则，撤回重发不重置次数；已及格也可在剩余次数内重考。

此前助手建议供比较；其中双记录展示已不作为当前推荐，其他考试与支付衔接问题仍保留：

1. **一项考试下显示多次记录**：PC仍只配置和发布一项随机考试，不因每次失败新增一张后台试卷。H5在同一考试下同时展示“第1次未通过—查看详情”和“第2次待考试—开始考试／去预约”。更多历史可进入全部考试记录。
2. **先出现入口 点击才抽题**：失败且仍有剩余次数时显示下一次待考入口，不在交卷后自动开始下一场，不提前计次或启动倒计时。点击开始并通过付款、预约、实名等检查后才抽题并保存。此方式与正在实施设计更一致；若坚持失败即预生成题目，需要另设计待开考状态，不能借用已开始考试记录。
3. **重新抽题不等于每道题都不重复**：原设计允许跨次重题。若需要增强差异，可优先抽此前未考过的题，不够时补抽旧题；这是新增建议，尚未确认。若要求跨次完全不重复，需要按题型、难度准备足够题量并明确缺题时怎么办，不能直接承诺一定全新。
4. **查看失败详情保持历史**：展示该次成绩、作答等历史信息，不允许重新提交或覆盖；是否显示完整答案解析继续沿用考试结果查看权限，不在本轮扩大。
5. **下一次入口与预约衔接**：按后续 D24，当天未通过且有次数可以立即再考，不要求每次重考重新预约；另一天考试仍需衔接预约。只保留一个当前待考／进行中入口，刷新和重复点击不生成多个考试。

支付融合还需裁决：

- 建议付费页面读取关联已发布试卷的次数配置，并保存购买时承诺的次数；后续管理员改配置不静默减少已购买机会。现行考试设计在首次开考冻结规则，两者的版本和次数必须统一。这是建议，尚未确定冻结时点。
- 建议重新购买产生新一轮付费考试机会并保留旧记录。但现行设计是同一学员同一试卷累计次数，仅新增支付订单不会解除原上限；必须补充购买与考试轮次的关联，不能通过修改旧次数或复制后台试卷绕过。
- 用户说按套餐区分本机构／外来，正在实施的考试设计按服务端学员来源冻结难度；重新购买98元后的来源、难度和历史归属需明确，不能在付款后直接覆盖旧记录。
- 原设计允许已通过仍继续考试；本轮只讨论失败后的入口，不自动推导为“通过后禁止重考”。

### S06 现有考试卡片显示次数 经考试须知后开考

- 状态：保留单卡片为当前推荐；进行中和次数用尽的具体文案已按 D23 确认；不代表界面已实现。
- 用户提供现有考试Tab截图，建议在时长、题数、满分这一行增加考试机会；每次使用后减少，进入考试须知后，点击开始考试才抽题。
- 展示：一项已发布考试继续对应一张卡片；待开考时显示“剩余N次”，答题中按 D23 显示“第N次考试，共M次”。次数来自试卷配置和本人记录，不写死3次，必要时换行。
- 流程：考试卡片 → 考试须知 → 明确点击开始考试 → 服务端检查条件、抽题并成功建立本次考试 → 使用次数加1、剩余次数减1。进入列表／须知、预约、刷新、开考失败不扣次数。
- 进行中：显示“第N次考试，共M次”和“继续答题”，恢复同一份题目和截止时间，不重抽、不再扣次数。最后一次也可继续当前考试，不以“剩余0次”替代当前考试信息。
- 考试结束：本次失败且仍有次数时，同一张卡片提供“再次考试”及“查看记录”；下一次仍先进入考试须知。次数用尽且无进行中考试时按 D23 显示“考试次数已用完”，保留记录查询。
- 当天重考：按 D24 允许马上再次考试，不额外插入重新预约步骤；通过须知主动开考，仍检查剩余次数并生成新的题单。
- 历史：每次考试各自保留题单、答案和成绩，从“查看记录”进入历史详情，不新增一张待考试卷卡，也不复制PC后台试卷。
- 筛选：不能把一次失败等同于整项考试彻底结束，导致有剩余机会却没有重考入口。已通过后是否继续重考暂沿用正在实施设计，不在此变更。
- 示例：上限3次，未开考显示剩余3次；首次开考显示第1次／共3次，后台剩余新开考机会为2；首次失败后显示剩余2次；第三次进行中显示第3次／共3次并可继续，第三次结束才显示考试次数已用完。
- 与 S05 的关系：用本方案替代双记录卡展示建议；不改变当前设计中“每次新开考随机抽题、进行中恢复不换题”的机制。是否减少跨次重题，以及重新购买如何恢复新一轮机会，继续单独讨论。

### S08 现场签到与本人核验方案 待选择

目标拆成三个问题，避免一个功能承担所有责任：账号表示谁登录；现场二维码表示此时拿到了现场凭证；本人核验表示当前操作人是否为实名本人。单独定位只能说明手机位置，不能解决代登录。

**方案A 简单人工版 当前首期推荐**

```text
工作人员开启本场签到并展示短时二维码
  → 学员扫码登录
  → 系统核对付款、预约、试卷、签到时间
  → 工作人员核对本人证件／实名信息并确认
  → 签到成功
  → 考试须知 → 学员点击开始 → 抽题
```

- 二维码对应已发布试卷和当前考试安排，但使用短时可验证参数，建议在现场屏幕刷新，避免永久静态码被长期转发；具体刷新时间待设计。
- 复用现有已实名事实，不要求每次重新上传身份证和完成整套实名认证。工作人员只看最少必要的脱敏信息，人工确认需记录操作人和时间。
- 不要求定位，避免室内漂移、授权失败和模拟定位导致正常学员被误拒；可以给少量无法刷脸的人员提供相同人工流程。
- 优点是链路短、成本低、身份确认清楚；代价是现场需要工作人员逐人确认。

**方案B 自动核验版 动态二维码加一次活体核身**

- 扫码后在当日第一次签到时做活体人脸核身，确认当前真人与已实名身份一致；通过后保存当日本场签到，连续考试不重复刷脸。
- 这比现有照片式实名认证更强。当前项目的腾讯 `ImageRecognitionV2` 使用现场正脸照片做身份比对，现有设计没有把它写成活体核验；若选本方案，需要新增腾讯H5／小程序活体流程和真实供应商验收。
- 人脸失败、设备不支持或本人不同意人脸时，必须提供工作人员人工核验的合理替代，不能让人脸成为唯一方式。
- 优点是减少人工、能较好防止借账号；代价是接入、费用、资质、隐私告知和异常处理明显增加。

**方案C 多因子版 动态二维码加活体加定位**

- 在方案B基础上增加机构坐标和50／100米范围判断，定位只作为现场风险信号；需要校验定位精度，不能只比较经纬度。
- 优点是能同时检查本人和手机位置；缺点是定位可被模拟、室内漂移明显，且位置和人脸都是敏感个人信息，会增加权限失败、误判和合规成本。
- 只有实际出现二维码实时转发、远程代签等风险后再考虑，不建议首期直接上。

**助手建议**：首期选A。如果现场人工核验压力确实过大，再升级为B；暂不做C。无论选哪套，扫码／核身／人工确认只完成签到，不扣考试次数、不抽题；学员仍在须知页点击开始后才生成题单。

**视频学习的边界**：已有视频有效学习时长可以证明线上学习进度，不能证明人在培训现场。若业务只要求完成线上培训，则无需额外培训签到；若必须证明参加现场培训，可复用本场一次人工／活体到场确认，不再建设独立复杂的培训签到系统。

**合规提醒**：人脸和精确位置属于敏感个人信息。采用人脸前需要明确必要性、显著告知、单独同意、最短保存、影响评估及替代方式；本讨论记录不替代正式合规评估。

### S09 定位加本人照片比对的首期链路 已按 D31 收敛

**当前项目核查结论**：现有实名认证已经实现“仅相机拍正脸＋身份证正反面OCR＋腾讯 `ImageRecognitionV2` 人证比对”。移动端正脸限定从相机获取；后端向腾讯发送OCR姓名、证件号和正脸图片，相似度低于70拒绝。当前分支定向构建和 `identity-verification.spec.ts` 30项测试通过。

但它是**单张照片人脸核身，不是活体检测**：接口只传 `IdCard/Name/ImageBase64`，没有动作、视频、数字口令或静默活体步骤。相机限定能阻止直接从相册选图，不能证明镜头前一定是真人。既有验收也明确真实腾讯OCR／FaceID、真实材料、微信和手机真机尚未执行，不能把测试Fake Provider通过当成现场核身已验收。

此前建议活体核身，用户因资质和复杂度选择 D31 的照片比对。当前首期链路调整为：

```text
已付款且已预约
  → 预约日期当天打开小程序考试入口
  → 获取本次最新定位
  → 服务端校验机构坐标、配置半径和定位精度
  → 当天首次到场签到时现场拍正脸
  → 后端读取既有实名资料做人证照片比对
  → 服务端记录本人＋预约日期＋培训地点的当天签到
  → 培训和当天全部考试复用该签到
  → 考试须知
  → 点击开始考试后才抽题、计次、下发题目
```

- 培训和当天连续考试沿用同一次有效签到，不重复定位和拍照；跨天改期后重新签到。
- 不需要二维码。试卷由预约和考试Tab确定，定位及照片人证比对承担现场与本人核验。
- 首期按 D31 接受照片比对不是活体检测的风险，产品文案只写“人证比对／身份核验”，不写“活体认证”或“确认真人”。异常时由工作人员人工核对。
- 复用已实名的加密姓名和证件号，不让学员每次重新上传身份证；现场签到只上传本次正脸照片。
- 定位建议只保存签到是否通过、机构、距离／精度的必要审计摘要；是否保存原始经纬度及期限需另作最小化设计。
- 照片核验不能作为唯一不可替代方式。设备不支持、供应商失败或用户不同意人脸时，提供工作人员核对证件的人工签到入口，并记录操作人和原因。

后续确认：D32已确定二维码完全退出签到链，D33已确定默认100米并由培训地点配置维护，D35已确定预约日期当天任意时间可签到，D36已确定培训和当天全部考试复用一次签到。当前签到主链已经收敛。

#### S11.4 服务端：8项新增业务能力

服务端建议按业务边界拆为8项能力，不必机械地等同于8个Nest目录：培训服务、培训地点、场次与容量、预约与改期、企业报名批次、订单与支付、退款与对账、现场签到。它们分别关联现有的用户实名、课程学习、随机考试、权限和审计能力。

#### S11.5 最简业务主链


#### S11.6 明确不建设的模块

首期不建设多地点／分校选择、二维码签到、活体核身、系统通知、候补补位、付款前锁位、当天临时补约、企业成员换人、证书或住建平台对接。上述范围可避免把辅助预约支付流程扩成另一套大型平台。
