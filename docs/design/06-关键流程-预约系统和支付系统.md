#### 12.2.1 企业购买：PC端

前提：机构已在 **PC端 → 预约管理 → 企业报名** 登记企业名称、联系人和手机号，开通企业账号；企业不自行注册。企业联系人使用该账号办理以下流程。

```mermaid
flowchart TB
    C_START([PC端：企业联系人登录企业账号])
    C_START --> C_ENTRY[进入成员报名]
    C_ENTRY --> C_MEMBERS[下载模板并导入成员名单<br/>逐行预检、修正错误，确认本次报名成员]
    C_MEMBERS --> C_SERVICE[本单选择一种服务<br/>398元培训加考试，或98元单独考试]
    C_SERVICE --> C_CONFIRM[确认名单、人数、单价及总额<br/>服务内容、考试次数和退费条款]
    C_CONFIRM --> C_ORDER[提交订单，固定本次购买内容<br/>提交时如有变化，须重新确认后才能创建]
    C_ORDER --> C_PAY[进入PC端：缴费订单<br/>打开本次订单并统一付款]
    C_PAY --> C_METHOD{企业选择付款方式}
    C_METHOD -->|微信扫码| C_WECHAT[PC端展示本订单支付二维码<br/>企业使用微信扫码付款]
    C_METHOD -->|对公转账| C_BANK[企业向机构对公账户转账<br/>按本订单应付金额付款]
    C_WECHAT --> C_WVERIFY[系统核验微信付款结果<br/>核对商户、原订单和金额]
    C_BANK --> C_BVERIFY[财务核对银行实际到账<br/>在PC端登记收款及凭据]
    C_WVERIFY --> C_CHECK{已确认足额收款<br/>且原订单可正常开通？}
    C_BVERIFY --> C_CHECK
    C_CHECK -->|是| C_ACTIVE[订单记为已付款<br/>只开通一次原订单全部成员资格]
    C_ACTIVE --> C_END([企业购买完成：已付款待预约<br/>后续从PC端的预约安排办理批量初次预约])
```

企业需要两种服务时分别下单；同一笔企业订单由企业统一付款，不让员工分别付款。名单存在错误时先修正或重新确认有效成员，不把错误成员带入订单。付款后成员资格不能换人或转让。

#### 12.2.2 个人购买：小程序端

本人使用手机号验证码登录，不选择企业身份，也不使用企业账号。已有企业代付服务的员工无需为该服务再次购买。

#### 购买过程中遇到未付款或异常

以下是两条链路各自适用的处理规则，不在两张图之间连线；详细核实和人工处理见12.8。

| 情况 | 处理与结果 |
| --- | --- |
| 已付款，但本系统尚未确认 | 显示“正在核实付款，请勿重复付款”；核实原交易，不能因为查询失败就当作未付款或另建订单 |
| 确认未付款，原订单未过期 | 从各自的已有订单入口继续付款；不再购买则不产生服务资格 |
| 确认未付款，原订单已过期 | 仍要购买时重新展示并确认当前报价及权益，再创建新订单；保留旧订单，不原地改价；具体过期时长仍未确定 |
| 订单已关闭后发现收款，或金额不符、重复付款 | 先记录真实收款，再按12.8核实；不能直接开通、忽略收款或要求重复付款 |
| 核实后应按原订单提供服务 | 记录收款，只开通一次原订单资格，回到该购买链路的“已付款待预约”结果 |
| 核实后应退回款项 | 按12.8人工退回并登记实际结果；实际退回后该收款问题才算办结，不将办理中写成购买成功 |

微信确认付款成功即可记已付款，不等待微信结算到机构银行卡。企业对公转账须核实银行实际到账；个人或企业的截图都不能代替实际收款核实。两条链路都在提交订单时固定购买内容，到账只激活原订单承诺。

### 12.3 号源建立与日常维护

<a id="flow-schedule"></a>

依据：第4.3节，D26、D44、D45、D48。

```mermaid
flowchart TB
    S_START([PC端：运营进入预约管理 → 场次安排])
    S_START --> S_DATE[选择未来开放日期<br/>培训地点为唯一海珠地点]
    S_DATE --> S_TYPE{开放哪种场次？}
    S_TYPE -->|培训加考试场| S_TRAIN[设置整天时段和当天可接待人数<br/>例如60人，上午培训、下午考试]
    S_TYPE -->|单独考试场| S_EXAM[设置当天可接待总人数及考试时段<br/>例如全天120人，时段由运营设置]
    S_TRAIN --> S_SAVE[保存并开放该日期的预约]
    S_EXAM --> S_SAVE
    S_SAVE --> S_OPEN[号源已开放<br/>只接受明天及以后日期的预约]
    S_OPEN -->|后续需要修改、删除或停止新预约时| M_SELECT[在PC端场次安排中<br/>选择需要维护的日期或时段]
    M_SELECT --> M_BOOKED{该日期或时段是否已有预约记录？}
    M_BOOKED -->|没有| M_ACTION{本次要做什么？}
    M_ACTION -->|修改| M_EDIT[修改日期或时段并保存]
    M_EDIT --> M_UPDATED([修改完成<br/>按新安排接受预约])
    M_ACTION -->|删除| M_DELETE([删除完成<br/>该安排不再提供预约])
    M_BOOKED -->|已有| M_KEEP[不允许直接修改日期、时段或删除<br/>保留原安排和已有预约]
    M_KEEP --> M_STOP{是否停止接受新预约？}
    M_STOP -->|否| M_UNCHANGED([保持原安排<br/>继续按剩余名额接受预约])
    M_STOP -->|是| M_CLOSE[关闭该安排的新预约入口<br/>不取消已有预约、不释放已有名额]
    M_CLOSE --> M_CLOSED([已停止接受新预约<br/>已约学员仍按原安排到场])

    classDef decision fill:#fff2e8,stroke:#c76a32,color:#303b4c;
    classDef result fill:#edf7f0,stroke:#658b72,color:#294537;
    class S_TYPE,M_BOOKED,M_ACTION,M_STOP decision;
    class M_UPDATED,M_DELETE,M_UNCHANGED,M_CLOSED result;
```

同一日期、同一种场次的各时段共用当天总名额，不给每个时段各配一份全天名额。60人、120人和时段数量只是示例。系统不按时段自动均分名额，不另设营业时间或最晚开考时间；现场人员组织接待与连续重考。每天的总人数上限与每次考试已有的截止时间仍然生效。

号源开放后可正常接受预约；只有运营需要维护时才进入下方修改、删除或停止新预约的分支。停止接受新预约不影响已约学员后续签到、培训和考试。提交预约时的余量检查和人数计算见12.4。

### 12.4 个人小程序端：首次购买成功、预约与改期

<a id="flow-booking"></a>

依据：需求分析第3.3、4.1、4.3—4.4、4.7节，UC-AP-01、UC-AP-03；讨论记录D09、D19、D35—D38、D46、D49、D50。

本图从本人首次购买成功开始，按小程序端的实际办理顺序展示预约、查看和改期。购买付款过程见12.2.2；企业批量初次预约不放入本图，已经参加考试后另约一天的流程见12.6。

```mermaid
flowchart TB
    P_PAID([小程序端：首次购买成功<br/>已付款，尚未预约])
    P_PAID --> P_ENTRY[付款成功页：去预约<br/>选择本次已购买的服务]
    P_ENTRY --> P_SERVICE[打开预约页面，按所购套餐展示可约场次<br/>398元：培训加考试场，例如周二、周四工作日<br/>98元：单独考试场，例如周一、周三、周五工作日]
```

#### 一、页面入口

1. 付款成功后，点击“去预约”。
2. 当时未预约的，从“小程序端 → 我的 → 我的订单／服务 → 本次已购服务”继续预约。
3. 预约成功后，从“我的 → 我的预约”或首页近期安排查看详情。
4. 需要换时间时，在预约详情点击“改期”，重新打开预约页面，不必重新购买。

#### 二、可选日期和时段

1. **398元未培训**：只显示培训加考试场，例如周二、周四工作日。
2. **98元**：只显示单独考试场，例如周一、周三、周五工作日。
3. **398元已培训**：只改未参加的考试，显示单独考试场。
4. 页面按套餐和培训参加情况提供可选项，学员只需选时间。
5. 上述星期是排期示例，实际由运营配置。
6. 只能选择明天及以后、已开放且有剩余名额的日期和时段。

#### 三、首次预约规则

1. 付款成功不等于预约成功，不保证指定日期有名额。
2. 提交预约时，系统再次检查本人资格、日期是否开放及剩余名额。
3. 398元一起安排当天培训和考试，1人只占1个名额。
4. 保存失败不产生预约，也不占名额。
5. 暂不预约时保留已购资格；未使用服务的退款按12.7办理。

#### 四、改期条件

1. 过去日期未到场、未签到的预约，仍可改到未来可约日期。
2. 已签到，但培训和考试都尚未开始的，仍可改期。
3. 398元尚未参加的培训和关联考试，必须一起改期。
4. 398元已参加培训的，只改未参加的考试，保留本轮培训事实。
5. 退款处理中等服务暂停状态，不能改期。
6. 有进行中的考试时，不能通过改期取消或逃避本次考试。

#### 五、改期结果

1. 新安排、原预约变更和名额处理全部成功，才算改期成功。
2. 改期失败，保留原预约、原名额及原签到适用关系，新日期不占位。
3. 改期成功后，未签到且原日期在未来的名额可以释放。
4. 已签到的原日期名额不回补；原签到只保留历史，新日期须重新签到。
5. 改期不额外收费、不自动退款，也不消耗或重置考试次数。

#### 六、与其他操作的区别

1. 已参加过考试、用剩余次数另一天再来，按12.6“预约下次考试”办理，不修改已使用的历史预约。
2. 首期不提供“单独取消预约但保留待约资格”的操作。

#### 签到与开考规则

1. 考试二维码进入考试Tab，培训二维码进入课程Tab；也可自行打开小程序。二维码只负责跳转页面，不证明到场。

9. 签到完成后不自动开始考试；本人仍须在考试须知页明确点击“开始考试”，服务端再次检查全部条件。
10. 同一天、同一地点签到一次，培训和当天全部考试共用；换一天参加须有新日期有效预约并重新签到，不能补记过去日期的签到。
11. 进入课程Tab、观看视频、签到成功，都不等于已经参加现场培训；已有进行中的考试按12.6恢复，不重新走新开考流程。

```mermaid
        FAILED --> RETRY{已确认不会继续出款<br/>且问题已解决？}
        RETRY -->|否| FAILED
        RETRY -->|是| CHECK
    end
    REGISTER --> END([结束实际退款成员的本轮资格<br/>保留逐人金额和结果<br/>其他正常成员不受影响])

    classDef decision fill:#fff2e8,stroke:#c76a32,color:#303b4c;
    classDef result fill:#edf7f0,stroke:#658b72,color:#294537;
    classDef wait fill:#fff8e8,stroke:#a68a50,color:#55482f;
    class WHO,EXIST,UNUSED,AMOUNT,APPROVE,CHANNEL,SAFE,RESULT,RETRY decision;
    class EXISTEND,USED,REJECT,END result;
    class SPECIAL,UNKNOWN,FAILED wait;
```

受理、审核、交人办理和录入结果时都要重新检查可退金额，同一申请各阶段只计算一次。退款申请与培训确认／新开考不能同时成功；审核通过不等于已退钱。更换办理人先查原办理记录；结果录错时保留更正记录并复核资格和金额，不能删除原记录重填。人工失败或结果不明不自动恢复服务。

### 12.8 异常收款与多收款退回

<a id="flow-payment-exception"></a>

依据：第4.6.1节，UC-AP-07，D51—D54。每笔异常有处理人、处理经过和下一步动作；只有收款与资格核对一致，或应退的钱实际退回，才标记办结。

异常收款分成以下三张图，分别处理付款核实、登记纠错和实际退钱，避免把不同问题挤在同一张图里。

#### 12.8.1 付款未显示、少付多付和关闭订单后收款

```mermaid
flowchart TB
    A([发现收款异常<br/>保留记录并指定处理人]) --> TYPE{遇到哪类问题？}
    TYPE -->|微信已扣款，本地仍未付款| QUERY[系统查询原微信订单<br/>查不清时财务在商户平台核实]
    QUERY --> Q{查询结果？}
    Q -->|未查清| PENDING[保持待核实，提示不要重复付款<br/>不能把查询失败当未付款]
    PENDING --> QUERY
    Q -->|明确未付款| UNPAID([返回12.2按未付款处理<br/>不开通资格])
    Q -->|付款成功| ORDER
    TYPE -->|订单关闭后收款／少付／多付／重复付款| ORDER
    TYPE -->|不知道谁付或对应哪单| FIND[保留收款待核对<br/>财务查明原付款方和订单]
    FIND --> FOUND{是否查明？}
    FOUND -->|没有| FIND
    FOUND -->|属于某订单| ORDER
    FOUND -->|确认是误转款| RETURN
    ORDER[核对原订单、真实收款及原退款记录<br/>不因补记付款重新开通已取消或已退服务]
    ORDER --> CAN{原服务能否继续提供<br/>且无取消／服务退款冲突？}
    CAN -->|不能履行，或有取消／退款处理中／已退款等冲突| REFUND[核实并沿用原退款处理<br/>服务退款继续12.7，不重新开通资格]
    REFUND -->|还有需要退回的真实款项| RETURN
    REFUND -->|应退款已全部退回且记录一致| DONE
    CAN -->|能| MONEY{仍用于本单的可用收款<br/>与原应付金额相比？}
    MONEY -->|不足| SHORT[展示已收和差额<br/>不开通部分成员资格]
    SHORT --> WANT{企业是否继续购买？}
    WANT -->|继续| TOPUP[补款仍登记到原订单]
    TOPUP --> ORDER
    WANT -->|放弃| RETURN
    MONEY -->|正好足额| ACTIVATE[按原承诺只开通一次资格<br/>仅解除本次收款纠错造成的暂停]
    MONEY -->|多付或两笔重复付款| EXTRA[每笔收款分别留痕，资格只开通一次<br/>多收部分列待退，不增加次数]
    EXTRA -->|只退多收部分，正常资格保留| RETURN
    RETURN[进入12.8.3核实并人工退回<br/>已有办理记录先查原退款]
    RETURN -->|应退款实际退回且资格核对一致| DONE([本次异常处理完成<br/>保留完整收付款记录])
    ACTIVATE --> DONE
```

“可用收款”只算仍用于本订单、未退回且未进入退款处理的金额。所有开通或恢复资格的路径都先检查取消和服务退款记录；不能借补记付款解除服务退款的暂停。仅因未付款关闭的订单，确认足额付款且原服务仍可提供时，沿用原购买承诺办理。

#### 12.8.2 银行流水重复登记与收款记错订单

```mermaid
flowchart TB
    A([发现登记问题]) --> TYPE{问题类型？}
    TYPE -->|同一银行流水重复认领| DUP[拒绝再次登记到本单或另一订单<br/>提示原收款关联位置]
    DUP --> WRONG{原登记是否错误？}

    WRONG -->|是| FIX
    TYPE -->|误确认收款或记错订单| FIX[财务新增更正记录<br/>保留原登记、原因、凭据和处理人]
```

一笔真实银行收款只登记一次、只归属一个订单。没有真实收款时不能凭错误登记退款；错误原订单后续补足时，仍回到12.8.1核对全部条件，只解除收款纠错造成的暂停。纠错办结表示登记和资格已恢复一致，不表示未付款的订单可以继续使用服务。

#### 12.8.3 多收、重复收到或误转款的人工退回

```mermaid
flowchart TB
    A([确认有需要退回的款项]) --> CHECK[财务核实原付款方、原付款<br/>应退金额和已有退款记录]
    CHECK --> PAID{本次应退金额<br/>是否已全部实际退回？}
    PAID -->|是| END([核对退款记录，异常款项处理完成<br/>正常已购服务不受影响])
    PAID -->|否| RUNNING{是否已有办理中<br/>或结果不明的退款？}
    RUNNING -->|有| QUERY[办理人先查原退款<br/>不另退一次，也不同时换渠道退]
    RUNNING -->|没有| ASSIGN[确认尚未退回且未被其他退款占用的金额<br/>指定一名办理人]
    ASSIGN --> CHANNEL{原渠道能否办理？}
    CHANNEL -->|能| PAY[工作人员在微信商户平台／银行办理<br/>款项退回原付款方]
    CHANNEL -->|受限| SPECIAL[记录原因，财务核实替代方式<br/>先确认原退款不会出款]
    SPECIAL --> SAFE{已核实原付款方和收款账户<br/>且可安全办理？}
    SAFE -->|否| SPECIAL
    SAFE -->|是| PAY
    PAY --> RESULT
    QUERY --> RESULT{实际退款结果？}
    RESULT -->|成功| RECORD[运营凭实际凭据登记金额、时间和经办人<br/>正常资格不因退多收款而暂停或终止]
    RECORD --> CHECK
    RESULT -->|处理中或不明| WAIT[保持待处理和金额占用]
    WAIT --> QUERY
    RESULT -->|明确失败| FAIL[登记原因并核实原退款不会继续出款<br/>问题解决后再办理，保留原记录]
    FAIL --> CHECK

    classDef decision fill:#fff2e8,stroke:#c76a32,color:#303b4c;
    classDef result fill:#edf7f0,stroke:#658b72,color:#294537;
    classDef wait fill:#fff8e8,stroke:#a68a50,color:#55482f;
    class PAID,RUNNING,CHANNEL,SAFE,RESULT decision;
    class END result;
    class SPECIAL,WAIT,FAIL wait;
```

上述退回只纠正收款，不受“已培训不退服务费”限制，也不增加考试次数或转成下一单余额。取消服务、关闭订单不能履行或少付后放弃购买所产生的款项退回，也复用这条人工办理和结果登记链路，但其资格状态仍按原处理原因或12.7执行，不能用本图恢复已取消或已退款资格。款项核对、退款金额保护和凭据要求同样适用，不能另起一笔重复退钱。

本节未替尚未确定的事项作决定：具体付款过期时长、自动关闭安排、多个有效资格的选择顺序、跨次重题及退款法律例外，仍按讨论记录继续确认；不在图中填入假定天数、自动退款或自动换人规则。
