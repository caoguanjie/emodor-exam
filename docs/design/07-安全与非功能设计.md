## 1. 引言

### 1.0 schema3与作者原稿安全增量（2026-10-23）

schema2原白名单和复杂度不变；schema3独立校验受控富文，允许有限marks、段落/标题/引用/列表/代码/表格/受控图片及有限排版属性。只允许SimSun/SimHei/Microsoft YaHei/FangSong/KaiTi、9—36pt、受控色值/行高/对齐/缩进；每字段2,000节点/100,000字符/16层，表格跨度与网格一致性校验。任意URL、HTML、CSS字符串、事件、未知属性及原型键均拒绝。作者链接/控件只静态转换可见文本，学员端不执行它们；作者元数据、答案/解析/checked/correct不得进入在考投影。

作者提交只允许现有管理角色与questions权限；精确版本锁、来源不可伪造、媒体精确引用继续生效。作者文档最多100题/20,000节点/32层/2MiB，超限41301；整个批次、原稿、媒体引用和持久回执同事务，失败整体回滚。request_id与owner唯一，无短期回执TTL；未知响应先查询原回执。纸张布局仅管理端展示，不扩大考试媒体范围。受控图片仍按exam_record_question精确owner签票，URL不得包含JWT。

### 1.3 设计原则

1. **客户端不可信**：一切与判定、计分、时长有关的规则只在服务端生效；客户端（浏览器）只负责采集与展示。C-01（学习时长以服务端累计为准）是该原则在学习域的直接约束，本册将其推广到考试域（判分参数全部服务端读取，见 3.2.5）。
2. **纵深防御**：单点防线必然被绕过（如位图可被脚本伪造、心跳可被模拟），多层防线叠加使作弊成本显著高于认真学习的成本（`required_minutes` 默认 10 分钟）。
3. **最小权限**：数据库账号、文件目录、接口角色均按最小必要授权。
4. **默认安全**：安全配置（HTTPS、哈希、校验、审计）随部署默认开启，不需要运维逐项手工开启。
5. **诚实边界**：明确声明技术手段的能力边界（见 3.3），不承诺"绝对防作弊"，把物理作弊的兜底交给组织手段。

## 2. 认证与授权设计

### 2.1 JWT 设计

#### 2.1.1 令牌结构与有效期

采用双令牌机制（对应技术栈定稿 JWT + RBAC，架构决策 AD-05）：

| 令牌 | 有效期 | 载荷 | 传输方式 |
|---|---|---|---|
| Access Token | 2 小时（环境变量 `JWT_EXPIRES_IN=2h`） | `sub`（sys_user.id）、`username`、`role`、`auth_version`、`sid`（认证会话 id）、`client`、`auth_method`、`type: "access"`、`jti`、`iat`、`exp` | `Authorization: Bearer <token>` 请求头 |
| Refresh Token | 7 天（`JWT_REFRESH_EXPIRES_DAYS` 可配），滑动续期（每次刷新重签发并废弃前一枚） | 同上，`type: "refresh"` | 按客户端隔离的 HttpOnly + SameSite=Strict Cookie，生产环境 Secure；见下表 |

| 客户端 | 认证方式 | Refresh Cookie | Cookie Path / 刷新入口 |
|---|---|---|---|
| PC | `client=pc`、`auth_method=password` | `ruleexam_refresh` | `/api/v1/auth` / `POST /api/v1/auth/refresh` |
| 学员 H5 | `client=mobile`、`auth_method=sms/debug` | `ruleexam_mobile_refresh` | `/api/v1/mobile/auth` / `POST /api/v1/mobile/auth/refresh` |

载荷设计约束：**不携带** `password_hash`、完整 `phone`、`email` 等敏感字段；`role` 来自 `sys_user.role` 三值枚举（super_admin / regulation_admin / employee）。新签发令牌的 sid/client/auth_method 必须与数据库会话用户、客户端及认证方式一致；mobile 不允许缺失 sid。仅历史 PC 令牌可将缺失 client/auth_method 视为 pc/password，无 sid 时继续按旧 jti/用户封禁规则兼容。mobile access 只保存在 Pinia 内存，不写 uni storage、localStorage、sessionStorage、URL 或 Cookie；refresh 不进入响应体或可读前端存储。

选择 2 小时的依据：学习会话与考试会话均以分钟计（`required_minutes` 默认 10 分钟、`duration_minutes` 默认 30 分钟），2 小时覆盖一次完整学习 / 考试会话不中断；同时将令牌泄露后的滥用窗口收敛在 2 小时内。

#### 2.1.2 无感刷新策略

前端在 Access Token 剩余有效期 < 10 分钟时（或收到 401 后）静默调用刷新接口：Refresh Token 有效则重签发双令牌并重放原请求，用户无感知；Refresh Token 过期则跳转登录页。学习页 30 秒心跳与考试页作答暂存均不受刷新影响（刷新只更换凭据，不触碰业务状态）。Redis 中断网恢复后的重连（UC-04 A1）同样先走刷新链路。

学员 H5 启动时用自身 HttpOnly Cookie 尝试恢复会话；业务请求 401 时，同一时刻共用一个刷新 Promise，每个原请求最多重放一次，刷新/登录/发码本身不进入递归刷新。服务端每次刷新复核账号状态、认证世代、用户封禁、jti 及持久会话身份，mobile 还重新查询普通学员身份与有效管理权限。旧 refresh jti 一次性消费，轮换后不可重放；刷新只延续本端会话和 Cookie，不替换另一端 Cookie。

#### 2.1.3 密钥管理

- 签名密钥 `JWT_SECRET`：**仅存于环境变量**（`.env.production`，文件权限 600，加入版本忽略清单），不落 MySQL、不进代码仓库、不打进镜像；由 `openssl rand -base64 48` 生成（≥ 32 字符随机串）。
- 签名算法 HS256（对称）；内网单体部署无多方验签诉求，不引入 RS256 的密钥分发复杂度。
- **密钥轮换**（建议周期 90 天，或疑似泄露时立即执行）：过渡期同时配置 `JWT_SECRET`（新钥，签发与验证）与 `JWT_SECRET_PRIOR`（旧钥，仅验证），一个有效期（2 小时）后所有旧令牌自然过期，删除旧钥；轮换纳入运维变更记录与审计日志（NFR-10）。
- **乱序密钥 `EXAM_SHUFFLE_SECRET` 独立管理**（3.2.1）：与 `JWT_SECRET` 相互独立、**不参与 90 天轮换**——乱序映射的可重算性依赖密钥恒定，若随 `JWT_SECRET` 轮换，轮换瞬间在考记录的还原映射错位、判分错误；仅**确认泄露且无 `in_progress` 考试记录**时才更换（更换前置条件见 3.2.1）。

#### 2.1.4 登出与令牌吊销（Redis 黑名单方案）

**问题**：JWT 是无状态令牌，签发后服务端默认"认签不认人"——登出、改密、禁用账号后，已签发的令牌在到期前依然有效（最长 2 小时窗口）。

**三候选方案对比**：

| 方案 | 做法 | 取舍 |
|---|---|---|
| a. 纯无状态（不吊销） | 登出仅删除前端本地令牌 | 令牌泄露后无法止损；改密 / 禁用后旧令牌仍可用——**不可接受** |
| b. 全量会话表 | 每次签发入库存令牌，每请求查库比对 | JWT 退化为自建 session，丧失无状态优势（AD-05）；高频心跳（约 17 QPS）每请求多一次库查询——**代价过高** |
| c. **黑名单（定稿）** | 默认放行；仅被吊销的令牌进入 Redis 黑名单，每请求一次 Redis 查询 | 空间只与"登出 / 封禁事件数"成正比（条目 = 活跃被吊销 jti 数，量级极小）；查询为 O(1)；保留无状态主体 |

**定稿实现**：

1. **单端登出与会话吊销**：PC 登出校验 access，将对应 jti 写入 `auth:blacklist:{jti}`（TTL 为剩余有效期），吊销该 sid 并清理 PC Cookie。mobile `POST /mobile/auth/logout` 是公开的 Cookie 驱动幂等入口，不依赖 access 有效性；只验证自身 refresh Cookie 的签名、type=refresh、client=mobile、sms/debug、sub/jti/sid，再撤销对应 refresh jti 和匹配的持久会话。无 Cookie、无效 Cookie 或 PC Cookie 不授权任何撤销，仍清理 mobile Cookie；不会清理 PC Cookie。即使 mobile access 已过期，退出后刷新也不能恢复该会话。认证守卫同时检查 Redis 撤销缓存与数据库会话撤销/到期事实，避免 Redis 重启使已撤销 sid 复活。
2. **用户级封禁（踢全部设备）**：改密成功、管理员重置密码、管理员禁用账号（`sys_user.status` 置 0）时，写入 `auth:block:{user_id}`，**值为封禁时刻时间戳（秒级）**，**TTL = refresh 剩余有效期（最长 7 天）**——比 Access 最大剩余寿命（2 小时）更长，可同时封死旧 refresh token 的轮换路径（防止封禁 2 小时后旧 refresh 仍换取新 access）。认证守卫判定：命中该键且 **`token.iat < 封禁时间戳` 才拒绝**（错误码 40107，HTTP 401）——封禁之前签发的全部存量令牌（access 与 refresh）一律失效，封禁之后**新签发**的令牌（`iat` ≥ 封禁时刻）天然放行，无需任何显式解封操作即实现「踢全部设备、新登录不受影响」的原意。由此实现：FR-ORG-06 验收②「修改成功后旧密码立即失效」、FR-ORG-03 验收②「禁用账号即刻无法登录且不参与应学人数统计」。
3. **降级取舍**：Redis 不可用时，jti 黑名单和用户封禁键的即时保障可能短暂下降；数据库的账号 status、auth_version 与持久会话撤销/到期检查仍生效。带 sid 的新 PC/mobile 会话不能因缓存丢失重新生效；历史无 sid PC 令牌的单 jti 吊销仍受 Redis 可用性影响，最长不超过 access 剩余有效期。不能把这一兼容降级描述为停用账号或 mobile 持久会话仍可通行。

### 2.2 密码安全

#### 2.2.1 哈希算法与参数

- **bcrypt，cost = 12**（2^12 轮）：单次哈希 / 校验约 200~300ms，登录非高频路径可接受；cost 每提高 1 耗时翻倍，12 在"防离线爆破"与"登录体验"间平衡（OWASP 建议 ≥ 10）。
- 哈希存 `sys_user.password_hash`（VARCHAR(255)，60 字符 bcrypt 串；长度预留 255 兼容未来迁移 argon2id——见 03 册 3.1.2）。
- **明文永不出现在任何路径**：接口返回用户信息一律排除 `password_hash` 列（任何查询不 SELECT 该列）；日志、审计、错误消息中禁止打印密码与哈希。
- 比对在应用层完成（不依赖排序规则，03 册 1.2）；登录失败与用户不存在返回同一模糊错误（FR-ORG-01 验收②：不泄露「用户不存在 / 密码错误」的区别）。

#### 2.2.2 强度策略与防爆破

| 策略 | 规则 |
|---|---|
| 密码强度 | 长度 ≥ 8 位（建议 10 位）；须同时包含字母与数字；不得包含 `username` / `employee_no` / `real_name` 的 ≥ 3 字符子串；命中常见弱密码字典（top 1000）拒绝 |
| 前后端双重校验 | 前端 `el-form` rules 即时提示 + 后端 Pipe（class-validator）强制校验（02 册 4.2 协同口径） |
| 登录防爆破（双计数） | `username` 维度：连续失败 5 次 → 锁定 10 分钟（Redis `auth:fail:{username}` 计数，TTL 10 分钟滑动窗口），锁定期内正确密码也拒绝，返回错误码 40106（HTTP 429，响应含剩余秒数）；叠加 `source_ip` 维度 10 次/分钟限流（与 04 册 §5 限流约定逐字一致）。Redis 故障降级：锁定计数退化为**仅 IP 维度进程内计数** + 登录接口 `sys_user.status` 校验兜底（`status = 0` 拒绝登录），恢复后计数回 Redis |
| 修改密码 | 须校验原密码（FR-ORG-06 验收①）；成功后写 `auth:block:{user_id}`（值为封禁时刻时间戳，`token.iat < 封禁时刻` 的全部旧令牌失效，见 2.1.4），须用新密码重新登录 |

#### 2.2.3 初始密码与首次登录强制改密

初始密码仅用于管理员（03 册第 7 章初始化口径）：① 部署时超级管理员账号（`admin`，初始化脚本 bcrypt 哈希后写入）；② 管理员原子创建与授权重置密码。管理员入口共用密码强度、哈希和强制改密策略。纯学员仅通过 H5 手机验证码登录；学员新建、导入不接受密码，也没有学员重置密码接口。为兼容 `sys_user.password_hash` 非空列，创建时保存不可知随机值的 bcrypt 哈希并设 `force_password_change=0`。

**强制改密与登录统计分离**：`sys_user.force_password_change` 是当前口令是否必须修改的权威状态，不再用登录统计推断；`login_count` 只累计真实密码登录，`last_login_at/last_login_ip` 记录密码、短信或显式调试入口最近一次成功登录。refresh 不更新上述统计；短信/调试登录不清除 PC 强制改密状态。

1. 管理员初始创建：`force_password_change = 1`，统计从零开始；学员创建/导入不进入强制改密流程；
2. 有维护管理员权限者重置密码：置 `force_password_change = 1`，保留历史登录时间、IP、次数，避免伪造统计；超级管理员目标仍受下文保护；
3. 密码校验成功（包括首次 pending 登录）：递增 `login_count`，更新 `last_login_at` 与 `last_login_ip`；若 `force_password_change = 1`，签发受限 Access Token（`pwd_pending=true`），仅放行本人改密；
4. `PUT /auth/password` 成功：在同一事务内置 `force_password_change = 0`、递增 `auth_version`、吊销旧 durable sessions 并创建新会话，再签发完整令牌；refresh 不更新登录统计。

管理员必须通过独立创建入口设置初始密码，复用本节强度策略并置首次强制改密；不提供把既有学员账号提升为管理员的角色配置入口，也不静默生成不可知管理员密码。已有管理员通过修改接口调整业务角色，角色调整不重设密码，状态和有效权限分类由服务端判定。

管理员管理的重置密码入口要求 `administrators:reset_password`；非超级管理员不可重置超级管理员，不能重置本人（走本人改密）。仅写入 bcrypt 哈希、`force_password_change=1` 和新的认证世代，保留登录统计。资料/角色/状态更新、重置和删除在用户行锁内复核目标分类并吊销旧会话，提交后写 Redis 快速封禁/吊销及清理权限缓存。任何超级管理员与本人均不可被禁用/删除。删除仅写 `deleted_at/status=0`，保留角色、账号唯一标识和历史引用，不提供恢复或学员接口改写入口；密码和哈希均不进入审计 detail。

#### 2.2.4 管理员验证码

PC 密码登录仅接受管理员，必须携带 captcha_id/captcha_code；纯学员使用 H5 手机验证码登录。验证码写入 Redis，TTL 120 秒，校验使用一次性消费；/auth/captcha 按来源 IP 限流，响应只返回图片与 captcha_id，不返回答案。测试夹具只能从本次运行隔离 Redis 前缀读取答案，生产不提供绕过端点。

#### 2.2.5 学员移动短信认证与调试入口

手机号是认证标识：去除空白/连字符后必须匹配 `^1[3-9][0-9]{9}$`，非空值由 `uk_sys_user_phone` 唯一约束。本人 `PATCH /me/profile` 不接受 phone；后台受控入口改号须递增 auth_version 并吊销旧会话，不能把改号当作普通展示资料更新。

短信挑战使用随机 48 位小写十六进制 challenge_id，Redis 只保存以服务端 JWT 密钥计算的手机号 HMAC 关联、当前挑战、次数及过期时间；手机号/IP 限流键同样使用 HMAC。挑战存储不保存验证码或完整手机号，验证码由供应商生成并通过供应商 verifycode 校验。默认约束如下，环境变量只允许服务端配置：

| 约束 | 默认值 | 环境变量 |
|---|---|---|
| 同手机号重发间隔 | 60 秒 | `YUNXIN_SMS_LOGIN_RESEND_SECONDS` |
| 挑战有效期 | 300 秒 | `YUNXIN_SMS_LOGIN_VERIFY_TTL_SECONDS` |
| 每挑战验码次数 | 5 次 | `YUNXIN_SMS_LOGIN_MAX_VERIFY_ATTEMPTS` |
| 手机号/IP 发码上限 | 86400 秒计数窗口内 10/100 次 | `YUNXIN_SMS_LOGIN_PHONE_DAILY_LIMIT` / `YUNXIN_SMS_LOGIN_IP_DAILY_LIMIT` |

同一手机号新发码后旧挑战失效，验码前核对手机号 HMAC 与当前挑战，供应商校验通过后原子消费；重复消费不再签发会话。DTO 固定验证码为 6 位数字。供应商请求只在服务端发出，禁止记录请求体、验证码、完整手机号、签名原文、供应商原始消息或密钥；对外错误只返回受控业务码和脱敏提示。

`SMS_PROVIDER` 默认 `disabled`（发码/验码返回服务不可用），可选 `yunxin`；非法 provider 启动失败。启用 yunxin 必须通过环境变量同时提供 `YUNXIN_SMS_APP_KEY`、`YUNXIN_SMS_APP_SECRET`、`YUNXIN_SMS_LOGIN_CODE_TEMPLATE_ID`，缺项启动失败；默认服务地址 `https://sms.yunxinapi.com`、超时 5 秒（`YUNXIN_SMS_BASE_URL`、`YUNXIN_SMS_TIMEOUT_SECONDS` 可配），禁跟随重定向。密钥不能进入 H5 构建产物、示例值、日志或仓库。

`SERVER_DEBUG_LOGIN_ENABLED` 默认 false，只允许 test/development 显式开启；production 开启时配置加载即失败，其他非 test/development 环境也不得启用。`POST /mobile/auth/debug-login` 只跳过短信供应商校验，仍共用手机号规范化、账号关联/创建、普通学员检查与 `SessionIssuerService`，不自行伪造 JWT，不绕过停用、角色、管理权限、实名或业务守卫。新建调试学员仍为 unverified，H5 不提供调试按钮或固定验证码。

当前实现与自动测试不构成真实短信收码/验码验收；真实手机号及验证码由用户手工验证。调试入口的成功也不代表实名认证、真实供应商或微信真机验证通过。

#### 2.2.6 学员三图实名与供应商隔离（Gate G 自动化与独立代码审查已通过）

`IDENTITY_PROVIDER` 运行时只允许 `disabled|tencent`，非法值启动失败；disabled 可读取既有权威实名，但新图片处理/会话核验返回服务不可用。tencent 必须同时启用 `TENCENT_ID_CARD_OCR_ENABLED` 和 `TENCENT_FACEID_ENABLED`，两组 SecretId/SecretKey 完整；端点只接受对应腾讯官方 HTTPS 主机，不跟随重定向，超时默认 10 秒。FaceID 固定 `ImageRecognitionV2`、版本 2018-03-01，请求只有 OCR 得到的 IdCard/Name 与现场正脸 ImageBase64，阈值 70；不使用旧 ImageRecognition，不声称交互式活体。

三图上传/会话仅限当前 mobile 普通学员本人。服务端复核每项资产 ready、owner、uploaded_by、purpose 及未删除，不能靠客户端 scan_status、MIME 或“已认证”字段通过。创建锁用户行，同材料复用、不同材料不并行；外部调用前提交数据库 claim/lease，超时/未知不自动重调腾讯、不冒充材料拒绝。成功受控结果先加密保存 provider_verified 后再本地绑定；超过普通 TTL 仍恢复绑定，迟到旧结果不能改写既有实名。无成功结果的 lease/会话过期语义见 05 册 2.4.4。

不存在运行时 mock Provider、固定通过码或 test-pass 路由。自动化仅通过 Nest TestingModule override IdentityProvider，使用不含真实身份/人脸的合成图片，仍经过上传、归属、会话、轮询、结果持久化与绑定事务；生产入口和产物不加载该测试 bootstrap。Gate G 自动验证、真实腾讯核验、H5 相机权限和微信真机是不同验收证据，当前文档同步不代表任何真实供应商/设备已通过。

### 2.3 RBAC：业务角色权限与接口守卫链

#### 2.3.1 系统身份兼容与业务角色模型

`sys_user.role` 的 `super_admin / regulation_admin / employee` 单值枚举继续作为 legacy 系统身份兼容层；现行管理权限由 `sys_user_role` 的多选业务角色与服务端注册权限白名单决定。新建管理员通过 `POST /admin/administrators` 在同一事务创建账号和角色关系，`role_ids` 至少一项且只能引用启用的非系统业务角色；失败不得留下半成品账号。super_admin 天然拥有全部注册权限且不可清空保护权限。管理员页面不显示“我的学习”，但共享账号、认证、视频和 legacy 学员能力不因菜单隔离而删除。

036将本次三个模块拆为真实按钮权限：administrators:create/update/delete/reset_password、roles:create/update/delete/permissions、menus:read/create/update/delete。资料PUT与授权字段分别核验，新角色创建附带授权必须额外有roles:permissions；新增权限、修改权限、删除权限不能互换。菜单与其它系统配置不再共享维护入口授权；仅system_settings:write的新授权账号不获得menus权限。两个旧聚合项只兼容旧API输入，UI与新独立授权目录不展示。旧角色在一次性迁移保留原对应能力；回放迁移不会覆盖之后人工撤销。038前向删除已退役的 `administrators:assign_roles` 权限、菜单按钮与角色授权，以后继检查接管036相应不变量，既有学员不能通过管理接口提升为管理员。API权限缓存使用v2命名空间，旧前端缓存的兼容映射不会改变服务端授权事实。


#### 2.3.2 接口守卫链（认证 → 角色 → 资源归属三级校验）

全部受保护的 `/api/v1` 接口经过下列守卫与资源归属校验，任一级失败立即拒绝并返回 40xxx 段错误码（错误码明细见 04-API设计.md）。显式公开的登录、短信发码、Cookie 刷新/移动退出、公共配置与健康检查等入口按各自契约校验，不以业务 Bearer 作为前置条件：

| 级 | 守卫 | 校验内容 | 失败响应 |
|---|---|---|---|
| 第一级：认证 | 全局 JwtAuthGuard | JWT 验签（`JWT_SECRET` / 过渡期双密钥）→ `exp` 未过期 → `jti` 不在黑名单 → 当前 `status`、`auth_version`、`sid` 与用户级封禁均通过（NFR-06） | 401 类（token 过期 / 伪造 / 已吊销） |
| 第二级：权限代码 | 全局 PermissionsGuard（Permissions 装饰器或旧路由映射） | 服务端权限白名单与当前显式业务角色关系；未注册/未映射的 privileged 路由拒绝 | 403 类权限错误 |
| 第三级：兼容角色 | RolesGuard（`@Roles(...)` 声明式装饰器） | 使用当前数据库 `sys_user.role` 保留超级管理员保护与 legacy 学员边界；已删除的员工、部门、制度管理路由不能通过旧角色重新开放 | 403 类权限错误 |
| 第四级：资源归属 | 业务 OwnershipGuard（随各模块业务逻辑） | 数据级归属校验，见 2.3.3 | 403 / 404 类 |

mobile JWT 每次受保护请求都以数据库当前值复核 `status=1`、`role=employee`，并绕过权限缓存重新计算有效管理权限，必须为空；不能只信令牌 role。JWT 的 client/auth_method 与 sid 对应持久会话必须匹配；mobile 凭据禁止访问 `/admin/*`、PC `/auth/*`，PC 凭据禁止访问受保护 `/mobile/*`。路径边界按大小写无关路由语义统一检查。短信/调试登录与刷新采用相同普通学员条件；PC 强制改密仍只约束 PC 密码会话。

#### 2.3.3 数据权限边界（第三级守卫的校验规则）

| 主体 | 边界规则 | 典型校验 |
|---|---|---|
| 学员（legacy `employee` 身份） | **仅本人**：学习与考试数据一律 `user_id = 当前用户`；课程可见性要求账号启用、来源/类别匹配且课程 published；legacy 制度阅读仍按历史发布范围 | 课程与考试列表不接受客户端指定 user/category；跨类别详情返回 40302 |
| 业务管理员 | 仅按业务角色权限访问培训类别、学员、课程、题库、试卷、记录、统计或系统设置；资料读写复用 `ai:read / ai:write` | 题库资料、题目与试卷均做权限和资源归属校验；学员来源不是授权条件 |
| super_admin | 全部注册权限 + 管理员与系统设置；超级管理员保护不可被普通角色绕过 | 已取消的制度、员工、部门 CRUD 即使是 super_admin 也没有管理路由 |

B1 注册 `courses:read / courses:write / courses:publish` 三个权限。课程 category-options 是 `courses:write` 下的最窄包装，强制 `status=1` 且只返回 `id/name`；它不开放类别管理列表，也不把 `PermissionsGuard` 改成 OR 语义。非头像媒体上传仍独立要求 `media:write`。出题资料列表/详情/状态使用 `ai:read`，创建/上传/重试使用 `ai:write`，不新建一套资料角色。

B4 `/admin/questions/import-*` 全部要求 `questions:write`。`owner_id` 只能取当前令牌，客户端不能提交；questions 入口先核对批次 kind 与 owner，跨 owner/kind 统一返回 40302 且响应不携带批次内容。旧 `/admin/students/import-batches/{id}/commit` 在服务端固定只查询当前 owner 的 students 批次，题库批次沿用 students 原有 404 隐藏语义，不能因操作者仍有 `students:write` 而转调 questions 适配器。导入不授予题库读取、审核或其他管理权限。

C6 `/statistics/training/options|summary|ranking` 明确要求 `statistics:read`，导出只接受 `statistics:export`；窄 options 不借用 `papers:read` 或 `training_categories:read`，避免统计角色为填筛选器被迫取得源模块权限。`/admin/dashboard` 仅提供认证后的容器，`TrainingStatisticsService` 再按当前有效权限逐项决定是否返回学员/题目/试卷/趋势键；无权限键直接省略而非返回 0，前端隐藏不代替该服务端裁剪。学员来源/类别仍是考试范围事实，不是授权条件；兼任业务管理员不会从应考集合中消失。

数据边界由**后端查询条件强制收窄**（如 employee 的所有学习域查询强制带 `user_id`），而非仅靠前端路由拦截——前端 Vue Router 守卫只负责体验（拦截非法跳转），后端守卫负责安全（02 册 3.1 选型理由 3 的双层防线口径）。

## 3. 防作弊体系

本章是本册核心。学习侧与考试侧分别构筑防线，全部判定规则**只在服务端生效**。

### 3.1 学习侧四道防线（NFR-08）

四道防线依 01 册 1.2 节定序：**心跳上报（30 秒/次）→ 失焦暂停计时 → 时长容差校验（单次心跳最大计入 45 秒）→ 滚动分段位图（底部段必须覆盖）**；另加多设备 / 多开风控作为补充防线（3.1.4）。

#### 3.1.1 防线一：心跳保活与失焦暂停（服务端信任模型）

**前端采集**（信任信号，非判定依据）：

- 进入阅读页即启动 30 秒心跳定时器（`setInterval`，30 秒/次），每次心跳携带：当前最大滚动百分比、本周期内已确认停留 ≥ 10 秒的段集合（见 3.1.3）；
- 页面失焦（`visibilitychange` → `document.hidden`，辅以 `window blur` 兜底，NFR-13 四浏览器一致）→ **立即调用 `POST /learning/heartbeat/pause`**（服务端按 45 秒封顶结算当前区间并置 `state = paused`），随后停止心跳定时器；恢复聚焦 → **立即调用 `POST /learning/heartbeat/resume`**（服务端仅重置 `last_beat_at` 锚点、计 0 秒），随后恢复 30 秒节奏；
- 失焦 / 关闭页面时的段位 flush：`visibilitychange → hidden` 与 `pagehide` 时以 `navigator.sendBeacon('/api/v1/learning/heartbeat/pause', payload)` 携带未上报的 `dwell_segments` 与 `scroll_percent` 完成投递（见 3.1.3）；
- 失焦期间同样停止滚动采样（不发心跳即无采样，见 3.1.3）。

**服务端信任模型（为什么以服务端为准，C-01）**：

有效学习时长的唯一来源是**服务端相邻两次心跳到达时刻的间隔**（服务端时钟，`DATETIME(3)` 毫秒精度，03 册 1.3——不信任客户端上报的任何时间戳）。该模型下：

1. **改本地时间无效**：客户端时间戳不参与计算，服务端只用自身时钟差值；
2. **失焦语义服务端结算**：失焦由前端调用 pause 端点声明，服务端收到后按「当前时刻 − `last_beat_at`」以 45 秒封顶结算并置 `state = paused`；paused 期间到达的心跳不计费、不更新锚点（见 3.1.2）。即使攻击者篡改前端令失焦照发心跳，时长仍按服务端实测间隔计算，无法虚增（FR-LRN-03 验收②「失焦期间不产生有效时长累计」）；
3. **恢复聚焦不补记**：resume 端点只重置 `last_beat_at` 基准、计 0 秒（FR-LRN-03 验收③「长时间失焦后返回不一次性计入大额时长」）。由于 pause / resume 只会减少计入、不会增加计入，该参考信号被伪造也无法虚增时长，符合 C-01「客户端上报仅供参考」；
4. **断网恢复**：网络中断导致心跳丢失 → 恢复后从当前时刻继续累计，丢失区间不计（UC-04 A1，以服务端已收到心跳的累计为准）。

**会话状态与收口**（与 03 册 6.3 写入点 1 的 Redis 策略一致）：

- 开读创建 `learning_session` 行（`started_at` 落库）并建 Redis 会话键 `learn:session:{session_id}`（Hash：`duration_ms` / `state` / `segments` / `max_scroll_percent` / `last_beat_at`；TTL 6 小时兜底过期）；
- 会话收口三触发（任一）：① 正常退出上报 `ended_at`；② 心跳中断超 90 秒判定离线，按最后一次心跳 + 45 秒封顶截止（UC-04 A2）；③ 兜底定时任务（每 5 分钟扫描超时未收口会话，走 `idx_started_at`，02 册 2.2 定时任务②）。**失焦会话的两条边界**：① `state = paused` 的会话**豁免 90 秒离线收口**（失焦停发心跳属正常语义而非离线），由 Redis 会话键 6 小时 TTL 与 5 分钟兜底任务收口；② **已收口会话**收到的 pause / resume / 心跳请求一律返回 40906（语义扩展为「会话已结束，请重新开始学习」）；
- 落库事务：一次事务内 UPDATE `learning_session`（`ended_at` / `duration_seconds`）+ UPDATE `learning_record`（`total_seconds` 累加、`scroll_coverage` 按位 OR、`max_scroll_percent` 取 max、`last_learn_at`、`is_valid` 幂等判定）。

#### 3.1.2 防线二：45 秒容差校验算法（防加速挂机）

服务端对每次心跳执行的时长校验算法（伪码）：

```
输入：now = 服务端当前时刻（毫秒）
状态：last_beat_at = Redis learn:session:{session_id} 中的上次心跳到达时刻
      state = 会话当前状态（active / paused，3.1.1）
规则：
  若 state = paused：                # 失焦期间到达的心跳（含异常补发）
      不计费、不更新锚点；仅合并 dwell_segments 与 max_scroll_percent；返回
  delta_ms = now - last_beat_at
  若 delta_ms <= 0：丢弃本心跳（乱序 / 重放），返回
  credit_ms = min(delta_ms, 45000)   # 单次心跳最大计入 45 秒（毫秒封顶）
  HINCRBY duration_ms credit_ms
  HSET last_beat_at = now
输出：total_seconds = FLOOR(duration_ms / 1000)   # 判定与响应用
落库：learning_session.duration_seconds 统一取整口径（单会话最多损失 1 秒）
```

**各场景通过性分析**（攻击者视角验证）：

| 场景 | 心跳间隔 | 每次计入 | 结论 |
|---|---|---|---|
| 正常学习 | 30 秒 | 30 秒 | 时长 = 真实阅读时间 |
| 高频上报（篡改前端每秒 1 次，FR-LRN-02 验收②） | ≈ 1 秒 | ≈ 1 秒 | 总时长仍 = 真实经过时间，**无法虚增** |
| 低频上报（60 秒 1 次省流量） | 60 秒 | 45 秒（封顶） | 反而每轮亏 15 秒，**不鼓励** |
| 失焦 10 分钟后返回（pause → resume） | — | 0 秒 | pause 已按 45 秒封顶结算，失焦区间不计入（FR-LRN-03） |
| 断网 5 分钟后恢复 | 300+30 秒 | 45 秒 | 丢失区间不计（UC-04 A1） |
| 直接关闭浏览器 | — | 收口时 +45 秒封顶 | 会话按最后心跳封 45 秒截止（UC-04 A2） |

该算法使"时长"与"服务端观测到的真实在线阅读时间"严格一致，是 C-01 的算法化表达；Redis `HINCRBY` 单命令原子累计，无并发竞态。

#### 3.1.3 防线三：10 段滚动覆盖位图（防直接拖到底）

**问题**：`scroll_coverage` 位图（10 段，结构见 03 册 4.4：`total_segments` / `covered_count` / `segments`）若按「滚动经过某段即置位」的字面实现（FR-LRN-04 验收①），攻击者打开页面后**一次拖动跳到底部** → 途经段 0~9 全部置位 → `covered_count = 10`、底部段覆盖 → 判定条件②瞬间满足。位图更新规则必须专门设计。

**两个候选方案**：

| 方案 | 规则 | 评估 |
|---|---|---|
| A. 途经段标记 + 停留时间加权 | 一次滚动跳段时把途经段全部标记为"部分覆盖"，按停留时间加权累计，权重达阈值才计满 | 需在前端维护逐段计时与加权计算；滚动事件（`dispatchEvent` 合成 scroll）极易被脚本批量伪造；加权语义复杂、难以审计 |
| B. **只计停留 ≥ N 秒的段（定稿）** | 段被置位当且仅当该段被**静止停留** ≥ N 秒且经心跳通道上报确认 | 规则简单可审计（每段置位都有停留证据链）；信任面收敛到心跳单一通道；与 30 秒心跳机制天然契合 |

**定稿规则（方案 B，N = 10 秒）**：

1. **前端采样**（每 5 秒一次）：滚动静止 ≥ 1 秒后，将当前视口底缘映射的段位（按阅读容器滚动高度 → 0~100% → 除段取整，03 册 4.4）记入本地"段 → 连续停留秒数"缓冲；滚动位置变化即重置对应计时；**确认停留 ≥ 10 秒的段立即加入待上报队列**（不等下一拍心跳边界、计时不受心跳边界重置）；
2. **心跳上报**：30 秒心跳携带「待上报队列中的段集合」（confirmed segments）与当前 `max_scroll_percent`；**失焦 / 关闭页面 flush**：`visibilitychange → hidden` 与 `pagehide` 时以 `navigator.sendBeacon('/api/v1/learning/heartbeat/pause', payload)` 携带未上报的 `dwell_segments` 与 `scroll_percent` 完成 flush——beacon 在页面卸载时可靠投递且与 pause 端点「结算 + 置 paused」语义契合，避免本地缓冲中已确认的段位（尤其底部段）因停止心跳而永久丢失；
3. **服务端合并**：Redis 会话位图与上报段集合按位 OR；落库时与 `learning_record.scroll_coverage` 按位 OR 写回——**覆盖只增不减、合并幂等、回滚不取消已置位段落**（FR-LRN-04 验收②）；
4. **快速跳段的语义**：从段 2 直接拖到底部段（段 10）→ 途经段 3~9 因从未静止停留 ≥ 10 秒而**不置位**（"途经不算读过"）；底部段若真实停留 ≥ 10 秒 → 正常置位（用户确实读到了底部）；
5. **判定条件②**：`segments[total_segments - 1] === 1`（底部段覆盖，C-02 双条件缺一不可）；`is_valid` 一旦置 1 永不回退（03 册 3.3.2 设计说明 1）。

**N = 10 秒的取值依据**：① 与 5 秒采样配合，两次采样即可确认一段；② 顺序读完全部 10 段的最少停留 ≈ 100 秒，显著低于 `required_minutes × 60`（默认 600 秒），使覆盖条件独立于时长条件发挥信号作用而非重复计时；③ 10 秒 / 段（约全文十分之一内容）低于正常中文阅读速度（约 300~500 字/分钟），真实读者的误伤可忽略。

**方案 B 的取舍声明**：代价是 < 10 秒的快速扫读不计入覆盖——制度学习场景下可接受；换来的是规则可解释、可审计（会话流水 + 心跳上报构成证据链），且**不存在"途经即置位"这条可被脚本利用的捷径**。

#### 3.1.4 补充防线：跨阅读/视频单活动风控

**风险**：同一账号在多台设备、多个制度或阅读/视频两种协议上并行累计，会把真实时间重复计入多个学习事实。

**规则（同一用户跨全部学习类型单活动）**：

- 所有 reading/video start 每轮以短事务悲观锁同一 `sys_user` 行并做合法目标/账号与活动 reading 的权威重查；发现旧 reading 时立即释放事务连接，随后才在事务外等待原 session mutex 并调用唯一的 reading flush 算法，最多竞争重试 3 次，避免小连接池互等；reading 仍保留 `learn:active:{user_id}:{regulation_id}` 作为当前制度指针，video 另以 `active_user_id` 可空唯一索引兜底；
- 最终无活动 reading 的短事务关闭旧 video，完成后才取得新会话 `started_at/last_heartbeat_at`，因此旧 reading 在途心跳即使晚完成也不会与新视频计时重叠。后开者胜出，旧 reading 的已确认 Redis 累计正常落库，旧 video 不补记未上报区间；
- 心跳始终先检查 DB 会话未结束与当前所有权。Redis activeKey 不是活动权威，不能复活已被另一路 start 标记 ended 的 reading。

**取舍**（后开者胜 vs 拒绝新会话）：拒绝新会话虽更严格，但会把“换设备继续学 / 浏览器崩溃后重开”的学员锁死在死会话上（须等 90 秒离线判定或 5 分钟兜底任务），体验代价过高；后开者胜方案下旧会话数据不丢（已累计时长全部落库）、风控目标（禁止并行累计）不受损，故选后者。

**边界说明**：不同制度和视频的进度事实仍分别累计、互不挪用；“单活动”只禁止同一真实时间并行计费，不合并各自判定规则。切换到另一学习对象时，前一会话先收口，之后可继续接力学习。

#### 3.1.5 学习侧残余风险与兜底

- **脚本模拟**（Puppeteer / CDP 自动化）可伪造"每段停留 10 秒"的采样与 30 秒心跳——位图与心跳对脚本不可区分；
- 但兜底仍在：时长条件要求服务端真实经历 `required_minutes × 60` 的心跳时间（无法压缩）；"人在页面上发呆"（不切走、不阅读）技术上不可区分，这是「时长 + 覆盖」双条件模型的固有边界（见 3.3）；
- 防作弊审计支撑：`learning_session`（`idx_user_regulation_started`）保存逐会话起止流水，时长判定有争议时可下钻对账（03 册 3.3.1 设计说明 1）。

#### 3.1.6 B2 视频位置与覆盖防线

视频心跳不复用制度滚动位图。Task 12 Video Contract v1要求 `/me`视频接口只接受当前mobile employee本人；start与播放票据须复核账号启用、实名事实、published课程、video课时current version正时长、ready/purpose=video资产及精确版本引用。external/institution同学习资格，缺类别或跨类别不额外阻断；浏览目录/本人已有进度不自动start，不因未实名封锁只读入口。Gate H1 自动化与独立代码审查已通过；真实播放器解码、断网、全屏、微信开发者工具和真机仍未验。

服务端持久保存 `seq`、上次到达时刻、播放位置与状态；初始paused且位置取confirmed_position_ms，实际play首拍playing只建立锚点。心跳默认30秒，接受严格递增序号，重复或乱序只返回现有进度。有效区间要求前一状态为playing、当前为playing/ended，并先满足 `forward_ms ≤ max(server_elapsed_ms,0)+2000`；通过跳播判断后，确认时长再取服务端间隔、45秒和真实前进量的最小值。暂停、缓冲、后台、反向跳转和过大前向跳播均不计，前端只报告位置/状态，不提交累计时长或完成标志。

`credited_ms`与 `coverage_ms`分离：前者允许重复观看累积，后者由合并后的不重叠区间求和，完成只看 `coverage_ms / duration_ms ≥ 95%`。learner课程进度分母为当前published课程required video lessons当前版本，零分母null；来源/类别不改变该学习资格或分母，C6管理统计仍按既有筛选。位置合法性不能证明用户注意力，服务器也无法识别摄像、他人代看等物理作弊。下架、换版、引用失效、账号停用或当前播放资格失效时先关闭活动所有权再拒绝心跳；close与90秒回收都不补记未上报时间。

移动端onHide暂停播放器、立即报background并停周期心跳，不close；前台恢复保持暂停，须主动再播放，onUnload尽力close。waiting自然恢复后，在前台且仍有播放意图时，首个确认位置前进的timeupdate只发送一次playing重建锚点，其余timeupdate不逐次请求；error只作UI态，尽力发非播放状态截断锚点后提供简单重试。断网沿用原生buffering/loading，无离线缓存、补时队列或旧心跳重放。start/close串行、心跳同seq不并发，session/revision/登录epoch阻止旧课时或旧账号回包生效；start超时结果未知不自动并发重发。

### 3.2 考试侧防线（NFR-09）

考试侧防线依次为：**实名/资格、冻结乱序、受限题面/稳定ID、服务端期限、主动整卷与终态幂等；到期纯timeout**；legacy 固定卷另有考试资格校验。系统不采集切屏、连接状态或设备摘要。

#### 3.2.0 legacy 资格校验前置

**旧制度固定卷**发起考试（创建 `exam_record` 前）由服务端校验该学员在该制度上的 `learning_record.is_valid = 1`。未达标拒绝并返回剩余有效时长与底部段覆盖差距；同时校验试卷 published、作答次数与并发 `in_progress`。这是 legacy 执行兼容，不提供制度发布或学习要求管理入口。

现行新培训考试默认不要求课程或制度阅读完成，改为服务端校验mobile身份/实名、发布场次、类别/来源范围、权限、次数、账号状态和deadline；课程视频协议与制度阅读协议继续分别执行。来源标识不能替代权限角色，不能为绕过新门槛而减少答案/解析隔离、服务端计时或令牌吊销。

#### 3.2.0.1 C1 发布快照与答案隔离

1. 发布事务先锁培训类别、再写锁试卷；冻结规则和全部候选内容成功后才把试卷置为 published。不存在“状态已发布但快照缺行”的可见中间态。
2. `paper_release_question.snapshot_json` 是服务端权威历史，含答案/解析；普通 `GET /admin/papers/{id}/preview` 必须白名单投影并剔除这两项。答案版另需 `papers:export` 或题库读/导出权限，且不作为学员开考 payload。
3. 随机预览只是规则、两池容量和一次样例，必须显示“非所有考生同卷”。真实个人题单由 C2 在开考事务中生成；C1 不把预览样例写成个人历史。
4. 培训新流程为 draft → published → draft（撤回后可修改再发布新版本）；归档及 legacy 状态写入口继续退场。撤回草稿与历史 withdrawn/archived 记录继续阻止新开考并保留 release/assignment；编辑当前草稿与重新发布不得覆盖历史冻结数据；C2 与 C1 继续共用 `exam_paper` 行锁序列化开考、发布与撤回，不用 Redis 替代 MySQL 权威状态。

#### 3.2.1 稳定ID、冻结乱序与受限题面

创建record时用HMAC-SHA256(EXAM_SHUFFLE_SECRET, record_id)派生seed，以确定性Fisher-Yates洗牌并持久化题序/选项序；恢复不重算当前题库。v2 option ID在同一question version内唯一且重排不变，学员提交稳定ID，服务端直接比较冻结answer_option_ids，不转显示下标。legacy数字答案只以当时冻结options原始下标/key及display_to_original适配；缺失/重复/非法key整题报错，禁止随机补ID、当前题库替换或历史回写。

021仅新增question/question_version的content_schema_version/content_json及exam_answer.selected_option_ids兼容列，旧内容、checksum、release/record快照、答案与成绩不回写。AI/文件导题、PC legacy输入统一规范成新v2版本；PC checked只表示标准答案编辑状态，与学员所选option_ids独立。

在考递归重建受限Tiptap投影，仅item_id/type/score/stem/options[{id,content}]；能力3额外增加content_schema_version。schema2节点只允许doc/paragraph/text/hardBreak/image，图片attrs仅十进制字符串asset_id；禁止marks、任意src、HTML、链接、样式、事件或未知字段。schema2单文档上限2000节点、100000文本字符、深度4；schema3按本册1.0独立白名单，非法内容整题拒绝。任何层级与错误响应都不能泄漏checked/correct/answer/correct_answer/analysis/rubric及管理元数据；终态attempt的questions=[]。

#### 3.2.2 不采集页面焦点或设备状态

考试不注册监考用visibilitychange/blur上报，不采集切屏、连接状态、设备摘要或实时监控轮询。页面焦点不暂停服务端期限。onHide/onUnload只补存本地答案草稿，返回/退出尽可能强确认；浏览器强关/系统回收不能绝对拦截。学习侧失焦暂停仍用于结算学习时长，与考试无关。

PC /my/exams及/my/exams/:paperId菜单与深链接均关闭，PC管理题库、预览、组卷、exam_records:read只读记录保留。新/me考试只接受启用mobile employee，不用PC会话或管理权限旁路；未实名可浏览列表，新开/恢复进行中题面/主动交卷须权威实名，Debug Login不绕过。终态查询不再要求实名。

#### 3.2.3 绝对期限与纯timeout

deadline_at只在创建时由冻结规则计算，此后不变。客户端以server_now校准offset并显示deadline-(Date.now()+offset)；短时断网、切后台、刷新、重新进入或试卷调整都不延长期限。归零只锁编辑并查询record，不调用submit。

服务端在本人record悲观锁后取唯一accepted_at；只有accepted_at < deadline_at的主动提交有效，相等或更晚均timeout，不能使用前端点击、请求发出、到达队列时刻作为成功。状态读取/恢复、定时扫描、legacy Redis事件及过期submit统一纯timeout，不能取MySQL旧草稿或Redis答案评分。

纯timeout原子写status=timeout、score=0、grading_state=not_submitted，submission_method/submitted_at/graded_at/active_assignment_id=NULL，draft_revision=0且其他draft元数据NULL；不调用评分、不创建exam_answer、不生成逐题得分。升级前同record的非终态草稿答案只清理，历史终态不改。结果score=0/passed=false/correct_rate=null/items=[]，显示“超时未交卷”，无解析/题图/错题，排除finalized成绩与排名分母但保留历史列表。

#### 3.2.4 主动整卷、严格校验与终态幂等

答案由学员客户端产生，评分规则/标准答案/分值/期限与最终汇总只由服务端冻结事实产生。新body只能{record_id,answers:[{item_id,option_ids}]}，path/body记录相同；每题恰一次、未答[]，选项属于本题且唯一，single/judgment最多一项；未知字段、旧selected/revision/asset_ids、数字ID、缺题/重复/跨题均40001。

固定处理顺序为认证mobile→本人记录→事务悲观锁→状态/期限仲裁→仅active首次有效提交校验body。passed/failed重复请求忽略新答案返回首次结果；历史submitted返回待确认，不重试评分；timeout返回冻结超时，不能改为主动提交。不增加submission_id。两份不同答案并发、submit/timeout竞争与回滚重试只产生一个终态及一组副作用。

主动受理在同一事务写完整稳定selected_option_ids、逐题得分、总分、manual/finalized与passed/failed，submitted_at使用唯一accepted_at；失败整体回滚。新/me不提供服务端draft/heartbeat，也不能从读取、恢复、倒计时或清扫自动交卷。

草稿仅以ruleexam:mobile:<userId>:exam-draft:<recordId>在本地保存answers/currentIndex/savedAt，不存题面、标准答案、解析、deadline或token；每次变化完整克隆、同key串行，落盘成功才显示已保存。用户index与generation/tombstone阻止清理后的迟到写复活。主动登出/确认终态清理，普通401保留所属草稿，换号不读旧key。重进先联网取原attempt/题面再整份校验，任一未知ID或损坏整份不用，空答继续同record，不重抽/延时；离线刷新不能仅凭草稿显示题面。

主动确认后冻结payload，submitting禁止改答；结果不明先查record，仅仍active且未截止最多重试一次完全相同payload，再不明保留草稿/冻结payload继续查证。不得直接冒报成功/失败或换答案重试。

#### 3.2.5 自动评分、历史与题图授权

仅主动受理后的single/multiple/judgment在同事务按冻结answer_option_ids与规则评分：单选/判断全等满分；多选全对满分、错选0、非空漏选按partial_credit_ratio部分分；未答0且is_correct=NULL。主动结果才有稳定selected_option_ids/correct_option_ids、逐题得分与受限解析，无人工改分、答案附件、评语或阅卷版本。

历史已评分timeout（finalized且score/submitted_at已知）保持原分数/明细、timeout交卷方式及冻结结果图片只读权限，结果按历史事实投影passed/failed；历史submitted返回score/passed/correct_rate=null、items=[]的LegacySubmittedResult，显示“历史结果待确认”，不伪造新终态。legacy由schema/快照与历史事实判断，不能以submission_method为空推断。新纯timeout不进错题，旧finalized历史timeout按原事实保留。

题图以exam_record_question/item_id精确引用，短票签发/续签及 proxy 内容读取均重查 media_reference、账号启用/role/权限、记录归属和阶段：in_progress须实名/未截止，仅prompt；passed/failed及历史已评分timeout按冻结结果允许题干/选项/解析图；仅新纯timeout拒绝题图。PC exam_records:read Bearer管理预览独立，不可签learner票据；URL不含JWT。公开短票内容入口以claims.user重查原学员资格，同浏览器切号本身不保证即时吊销TTL内旧URL，客户端必须清旧URL/迟到结果，不能把旧资产纳入新账号状态。

### 3.3 防作弊能力边界声明（诚实声明）

**技术手段无法防范的物理作弊**（浏览器沙箱无法感知物理环境，本系统为内网部署、无摄像头 / 机房监考条件）：

| 作弊方式 | 说明 | 技术上为何防不住 |
|---|---|---|
| 拍照外传 / 拍照搜题 | 用第二部手机拍摄屏幕发给他人或识别软件 | 第二设备不在浏览器沙箱内 |
| 真人代考 | 把凭据交给他人或认证后由他人答题 | 三图核验不是考试全程在场证明，系统不采集持续摄像 |
| 线下协作 | 多人约同场次考试，线下互传答案 | 乱序提高了对答案的成本（题目选项位置对不上）但不归零 |
| 第二设备 AI 辅助 | 用另一台设备查询题目 | 同"拍照外传" |
| 页面内挂机发呆 | 学习时人在页面但不阅读 | "在页面上停留"与"在阅读"技术上不可区分 |
| 失焦事件漏报（前端未调用 pause / 事件被浏览器节流） | 单次最多计入 45 秒 | 浏览器事件不可强制送达，服务端只能按心跳间隔推断 |

**建议的组织手段补充**（技术的边界由管理补位）：

1. **错峰多批次开考**：按培训类别或业务安排分批开考，缩小同场次题面交集与协作面；
2. **缩短考试窗口**：`duration_minutes` 贴合作答所需时长（如 20 题 20 分钟），压缩外查答案的时间余量；
3. **题库轮换**：同一制度组多张试卷（`exam_paper` 可多卷并存）+ 乱序 + 补考换卷，使拍屏分享的边际价值趋零；
4. **结果抽查机制**：可按短时长高分、重复异常分布等服务端已有考试事实进行线下抽查；不以页面焦点、连接状态或设备摘要推断作弊；
5. **重点制度线下考试**：安全类等高合规要求制度，采用系统出题 + 线下集中监考的组织形式；
6. **账号实名与弱挂钩**：考试成绩与考核弱挂钩，降低作弊动机本身。

**设计立场**：本系统的技术防线目标是**把作弊成本抬高到显著高于认真学习的成本**（`required_minutes` 默认 10 分钟 + 一场限时考试），配合全程留痕的威慑与事后审计，达到企业内部系统的合理安全水位；「绝对防作弊」不是本系统的设计目标。

## 4. 数据安全

### 4.1 传输安全

| 层面 | 设计 |
|---|---|
| 浏览器 → nginx | 生产环境全程 HTTPS（NFR-10）：nginx TLS 终止，协议 TLS 1.2+（推荐 1.3），证书由企业内部 CA 签发（或自签证书 + 内部分发信任）；80 端口 308 永久跳转 443；启用 HSTS（`max-age=31536000`） |
| 安全响应头 | `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Content-Security-Policy`（见 4.4.2）、`Referrer-Policy: strict-origin-when-cross-origin` |
| 容器网络内部 | nginx → api（3000）、api → mysql（3306）、api → redis（6379）全部走 Compose 自定义桥接网络，**mysql / redis / api 端口不映射宿主机**（02 册 5.1 拓扑：仅 nginx 暴露 80/443），杜绝内网直连绕过应用层鉴权 |
| api → 第三方 AI | OpenAI 兼容端点（`base_url`）全程 HTTPS 调用（02 册 2.1） |

### 4.2 存储安全

#### 4.2.1 密码与哈希

`sys_user.password_hash` 存 bcrypt 哈希（参数与策略见 2.2）；任何查询不 SELECT 该列、任何接口不返回该字段、日志不打印（03 册 3.1.2 设计说明 2）。

#### 4.2.2 敏感配置的分层管理（api_key 为核心场景）

AI 服务参数（`base_url` / `api_key` / `model`）有两条配置路径，优先级为「界面配置 > 环境变量兜底」：

| 层 | 载体 | 说明 |
|---|---|---|
| 部署级兜底 | 环境变量 `AI_BASE_URL` / `AI_API_KEY` / `AI_MODEL`（02 册 5.3 清单） | 部署时注入，`.env` 权限 600、不入代码仓库；适用于未做界面配置的初始部署 |
| 业务级配置（**权威副本**） | 具备 `ai_config:write` 的管理端界面录入（FR-AIQ-01、NFR-15：调整无需改代码停机）→ **AES-256-GCM 加密后存应用数据目录下的加密配置文件**（与 05 册 §4.4.1 载体口径一致；文件随数据卷参与 4.2.3 每日备份，30 天保留） | 加密密钥为环境变量 `APP_ENCRYPTION_KEY`（32 字节，`openssl rand -base64 32` 生成，仅运维持有）；**不落 MySQL 业务表**（02 册 5.3「不落业务库」基准口径；不因培训增量改变敏感值边界）；界面只回显掩码（如 `sk-****xxxx`，FR-AIQ-01 验收②） |
| 读缓存 | Redis `ai:config:cache`（TTL 10 分钟） | 解密后配置的**读缓存**，仅用于 AI 网关调用路径减少文件解密读取；**缓存可再生、丢失由权威文件随时重建**，与 AD-04「Redis 只存可再生临时态」一致（6.2.2） |

**`api_key` 全生命周期约束**：明文仅在内存中出现于「界面保存瞬间（请求体）→ 加密落配置文件」与「AI 网关调用瞬间（解密 → 构造请求头）」两处；不入任何日志（含 AI 调用失败日志——错误信息脱敏为不含鉴权头的摘要）、不回显、不进入前端；配置变更写入审计日志（4.5）。

#### 4.2.2.1 实名数据加密与最小披露

`learner_identity.identity_encrypted` 与 `identity_verification_session.provider_result_encrypted` 只保存绑定所需受控数据，以独立 `IDENTITY_DATA_ENCRYPTION_KEY` 做 AES-256-GCM：随机 12 字节 nonce、16 字节 tag、版本化密文和固定 AAD；证件号规范化后用独立 `IDENTITY_FINGERPRINT_SECRET` 做 HMAC-SHA256 查重，不使用可离线穷举的裸哈希代替。两密钥均为严格 Base64 编码 32 字节值，production 或任一环境启用 `IDENTITY_PROVIDER=tencent` 时必须稳定注入，不复用 JWT/AI 密钥；不得以进程随机值写入可持久化真实实名事实。

本人权威视图可返回解密姓名、脱敏证件号与验证时间；不返回完整证件号、原始 Provider 响应、原图、签名、Secret 或 Token。原始材料私有存储，表与备份均按敏感业务数据权限管理。普通 PC/mobile 资料入口不得改已实名姓名；实名不改变账号 ID、手机号、来源、类别或历史记录，证件冲突不静默合并账号。

身份密钥不能直接替换而使历史密文不可读；轮换须在受控变更窗口以内存解密/重加密迁移校验后切换，指纹密钥变更须重新计算并保持唯一约束，不写明文临时文件。Provider 返回与落库之间崩溃只能保留 unknown，不声称外部 exactly-once。数据库唯一绑定事实和 `bound_event_id/bound_at` 同事务，文件审计提交后 best-effort，日志仅含内部 ID、受控状态与事件 ID。

### 4.3 文件安全

#### 4.3.1 上传校验链（四步，全部服务端执行）

| 步骤 | 规则（出题资料 PDF / DOCX） | 规则（学员导入 xlsx） | 拦截目标 |
|---|---|---|---|
| ① 扩展名白名单 | 仅 `.pdf` / `.docx`（外部资料版本 `file_type` 枚举 pdf / docx；内部可复用 legacy 列） | 仅 `.xlsx` | 伪装扩展名 |
| ② Content-Type 校验 | `application/pdf` / `application/vnd.openxmlformats-officedocument.wordprocessingml.document` | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` | 简单改后缀 |
| ③ 魔法数校验 | 读文件头：PDF 为 `%PDF-`；docx 为 ZIP 头 `PK\x03\x04` 且包含 `[Content_Types].xml` | ZIP 头 `PK\x03\x04` 且包含 `xl/workbook.xml`（与 docx 同族 ZIP、按内部结构区分） | 构造伪造文件 |
| ④ 大小上限 | 单文件 ≤ 50MB（环境变量 `MAX_UPLOAD_SIZE`，nginx 同步 `client_max_body_size`） | 单文件 ≤ 5MB；**解压后总大小上限 50MB**（防 zip bomb 高压缩比耗尽资源） | 超大文件耗尽磁盘（T5） |

**说明**：50MB 为上传硬上限；NFR-04 的「≤ 20MB 常规资料解析 ≤ 60 秒」是解析时效承诺（20MB 为常规文件基准），20MB ~ 50MB 的大文件解析走异步队列不受 60 秒承诺约束、不阻塞其他操作。学员导入的**业务级 1000 行上限在上述文件级校验之后**执行（文件级校验先于解析，阻断解析阶段的资源耗尽）。

**file_hash 双用途**：上传完成即计算 SHA-256（CHAR(64)）落库——① 同资料重复 hash 时提示已存在但不阻断；② 读取与审计场景做完整性比对。资料与版本对外 ID 均字符串化，不能因 JavaScript 数字精度导致越权读错对象。

#### 4.3.2 存储与路径安全

- **存储路径由服务端生成**：内部仍可复用 `{UPLOAD_DIR}/regulations/{material_id}/{version_no}_{file_hash 前 8 位}.{file_type}` 这一 legacy 存储键；目录名不构成对外“制度管理”语义。客户端原始文件名只作为展示元数据、**不参与任何路径拼接**——路径穿越（`../../etc/passwd` 类攻击）在结构上不可能；
- **存储目录不可执行**：`upload_files` 卷独立挂载，目录权限 750；nginx 对该目录仅配置只读静态映射且**不解析任何服务端脚本**（无 PHP / CGI / SSI 扩展关联）；
- **读取走 API 鉴权**：文件本体不经任意静态 URL 直供。出题资料列表/详情/解析状态要求 `ai:read`，创建/上传/重试要求 `ai:write`，版本归属必须匹配；legacy 学员文件读取仍按本人历史可见范围。nginx 仅以 internal 转发已授权文件，真实路径不暴露给客户端；
- **解析产物 XSS 净化**：mammoth 产出的 `content_html` 在写入 `regulation_version` 前做服务端白名单净化——仅保留语义标签（`p` / `h1`~`h6` / `ul` / `ol` / `li` / `table` / `thead` / `tbody` / `tr` / `td` / `th` / `strong` / `em` / `a[href^="http"]` / `img[src^="data:image/"]`），剥离 `script` / `iframe` / `style` / `on*` 事件属性 / `javascript:` 协议；**内嵌图片**（组织架构图 / 流程图等，mammoth 以 `data:` URI 内联输出）以 `img[src^="data:image/"]` 放行并**限制单图 base64 长度 ≤ 2MB、全文图片总数 ≤ 50**（防 MEDIUMTEXT 撑爆与浏览器内存放大）——与 4.4.2 CSP 的 `img-src 'self' data:` 对齐（白名单放行 `img` 与 CSP 允许 `data:` 图片二者缺一即图表被静默剥离）；**所有保留的 `<a>` 强制注入 `rel="noopener noreferrer"` 并移除 `target` 属性**（防新窗口打开时 `window.opener` 反向操纵阅读页）；内网部署（A-04）下正文外链仅展示为纯文本不可点击——外链多半不可达，避免员工点击后误判系统故障；PDF 渲染走 pdfjs-dist canvas，无 `v-html` 注入面。

#### 4.3.3 受控媒体上传与读取（A4）

- **用途白名单**：通用媒体只接受 `avatar`、`course_cover`、`video`、`question`、`branding`；公开 DTO 与内部业务均不接受图片答案用途。未注册 `owner_type` 的业务引用默认拒绝读取。
- **大小与落盘**：视频默认上限 512 MiB（显式配置范围 1—536870912 bytes），图片默认 10 MiB（范围 1—104857600 bytes）；Multer 磁盘流上限动态取两者较大值，nginx `client_max_body_size` 必须唯一且精确等于 `max(video,image) + 1048576` bytes，默认 513 MiB。禁止把大视频汇总为内存 buffer；存储键由服务端生成并做 root containment 校验，原始文件名仅作元数据。Multer 与媒体业务层的超限都统一返回 42202/HTTP 422；DTO、用途或权限在落盘后拒绝时也必须清理该精确临时文件，崩溃遗留仅由受控 TTL 清理扫描回收。
- **内容探测**：JPEG/PNG/WebP 由无 shell 的 `ffmpeg` 子进程实际解码，设置 `max_pixels`（默认 2500 万，配置范围 1—1 亿）、`max_alloc`、超时与 256KiB 输出上限，不以扩展名或单一 magic number 通过。视频由无 shell 的 `ffprobe` 读取结构化 metadata，`major_brand` 仅允许 `isom/iso2/iso3/iso4/iso5/iso6/avc1/mp41/mp42/m4v/dash/cmfc/cmfs`；必须恰好一条 H.264 视频轨，可包含零条或多条音轨，但每条音轨都必须是 AAC。字幕、数据等辅助轨道不会仅因存在而被拒绝；首条视频流仍由 `ffmpeg` 实际解码首帧。`ffprobe`/`ffmpeg` 仅允许 `file,pipe` 协议与 `mov` 容器，并保留 `max_alloc`、`max_pixels`、超时与 256KiB 输出上限。探测超时默认 30000ms，范围 1000—120000ms。内容不合规落 `failed` 与脱敏摘要；探测工具缺失或不可执行属于部署依赖不可用，返回 50004/HTTP 503，不能伪装成用户文件 400 错误。两类失败资源都不能被引用或读取。
- **所有权与引用**：资源 `owner_id` 与上传操作者分离；本人头像在 `PATCH /me/profile` 内绑定，管理端头像在 `lockManagedStudent` 最终事务检查内绑定。常规内容读取使用 owner/已注册 authorizer，越权统一 40302；删除前锁定资源并检查 `media_reference`，已引用返回 40913。无引用资源先把既有 `VARCHAR(16)` status 置为内部 `deleting`，再删除物理文件；失败保留数据库行供后续重试并返回 50004，只有物理删除成功或文件本就不存在才删行。bind 仅允许 `ready`，故不能与新引用竞态；常规 metadata/content 对 `deleting` 返回 40401，不暴露内部墓碑状态。孤儿延迟清理遵循相同状态机，计数只包含实际删除成功项。
- **题图最小授权**：`question_version` owner policy 的 asset-specific 检查只使用受控 `data-media-id` 提取。上传者与 `questions:read` 行为不变；`papers:read` 只能桥接真实 fixed draft、`paper_release_question` 快照，或 random draft 依完整规则重算出的当前合法候选精确版本。题干/选项可读，解析还要求 `papers:export` 或 `questions:export`；单独 `questions:export` 不放开试卷或全库媒体。发布后修订不改变旧 release 的题图读取，因为字段归属取冻结 `snapshot_json`。错误类别、资料来源、难度、状态、current version、题型、草稿或字段均拒绝；普通题图保留不等于图片答案能力保留。
- **B1 课程 owner policy**：`training_course_cover`只允许course_cover，owner为course ID；`lesson_version_video`只允许video，owner为不可变lesson_version ID。通用Bearer读取保留PC `courses:read`受控预览，普通学员读取须启用、实名及published/current version；video不能以 `asset.owner_id===actor_id` 上传者短路授权，所有读取均核对精确版本引用。视频短票另用learner-only authorizer，签发/续签及 proxy 内容读取都重查启用 employee、无有效管理权限、实名、published/current、ready资产及引用，不接受管理预览旁路。换版新增引用不解绑旧版本，故历史视频不能被媒体删除接口回收，但新签/续签及旧代理票据立即失去 current 授权，已发 COS 链接至到期有效。
- **A5 公开品牌窄桥接**：匿名端只能从 `GET /site-config` 读取 `logo_asset_id/banners`，且内容端点必须同时满足“ID 仍在当前两键白名单”、“存在 `owner_type=site_config` 引用”、“资源为 ready branding image”。不提供匿名 metadata 列表、不接受任意 media id 公开读取；任一条件不满足统一 40401。
- **流式 Range**：私有媒体流与上述公开品牌窄桥接在各自校验通过后按 Range 返回 206/`Content-Range`，不暴露真实存储路径；无效、多段或不可满足的 Range 返回 41601/HTTP 416；processing/failed/deleting 资源不返回本体。

#### 4.3.3.1 实名私有图片与短期媒体票据（Gate G 自动化与独立代码审查已通过）

实名三种 purpose `identity_id_portrait/identity_id_emblem/identity_face` 只能通过本人专用上传接口，通用 `/media/upload` 不能接收。JPEG/PNG 原图 ≤10 MiB、至少 320×320；证件源图 ≤20M 像素、face ≤60M，解码后降采样、修正 EXIF、重编码去元数据，最终长边 ≤1600、JPEG Base64 ≤约 2.8M。证件面还须 OCR 裁剪/清洗；声明格式、扩展名和客户端压缩成功不能替代服务端探测。三图不能跨账号拼接。

上传即建立 `identity_verification_user + user ID` 精确引用。取消/替换/离页可 best-effort DELETE，但服务端只释放本人、对应 identity purpose 且没有 session/实名事实使用的临时资产。仅临时引用且超过 24 小时未提交的材料由清理任务解除引用后按媒体 deleting 状态机删除；活动 session 与绑定证据保留。客户端释放 Object URL/临时文件并使旧请求失效，不把实名输入、原图或临时预览持久化到 Pinia storage。

签票须先验证精确 `media_reference(asset_id,owner_type,owner_id)`和当前owner policy，不以课程可见性代替任意封面绑定。已冻结owner为identity_verification_user/user_avatar/training_course_cover、lesson_version_video + version ID及exam_record_question + item ID；视频须使用上文独立learner-only授权，不能沿用PC管理读取旁路。proxy 票据用独立 `MEDIA_TICKET_SECRET` 做 HMAC，绑定版本、asset、actor、purpose、owner type、owner ID与expiry，默认300秒；URL不含access/refresh JWT、真实文件名、磁盘路径或供应商凭据。

proxy 内容入口即使票据签名正确，也重查同一引用、当前业务权限、purpose和资源ready/未删除；引用/权限撤销、角色变化或账号停用后拒绝旧票据，视频还须检查published/current，题图还须检查record阶段。无效/过期票据返回40302，单段Range依既有规则返回206或41601，响应 `Cache-Control: private, no-store`和 `X-Content-Type-Options: nosniff`。短期票据本身仍是可用凭据，不写业务日志、分析埋点或公开缓存。start签票失败须先关闭本次新session，不返回半成品；临期重签只换媒体src并恢复位置，不重建session或补时。Task12视频与Task13/14题图分别已完成Gate H1/H2自动验证；真实后端浏览器全链、供应商、真实弱网与设备边界不因本册同步放宽。

H5 的 proxy/local/实名内容使用同源相对 content_url，COS 普通媒体接受精确配置 origin/prefix 下的签名 URL；MP-WEIXIN适配层可通过公开构建配置 `VITE_API_ORIGIN` 转为HTTPS完整URL，缺失配置须给可辨别错误，禁止写Token、凭据或私有路径。微信合法域名白名单、Range/签名URL、原生拖动及全屏还须开发者工具/真机验证；首期MP编译兼容不替代这些验收。

**MP-WEIXIN 原生通信增量（2026-10-27）**：普通API、头像/实名上传及同源票据共用公开HTTPS origin配置，API路径不得转向任意站点；COS签名URL严格限定正式媒体origin/prefix，不依赖浏览器URL全局。小程序不自动维护Cookie，因此只在原生传输层内存维护精确API origin、mobile auth Path及 `ruleexam_mobile_refresh` Cookie，限refresh/logout发送；不持久化、不放入Pinia/URL/body，不接收PC Cookie。服务端仍校验现有client/auth_method/sid及吊销信息。H5继续使用浏览器HttpOnly Cookie；原生内存不具备浏览器HttpOnly隔离性质，冷启动重新短信登录，不能以本适配宣称具备持久免登录。账号切换/失效/退出清理并丢弃迟到Cookie更新。

#### 4.3.4 题库文件导入（B4）

- 仅接受显式 `format=xlsx|txt`：xlsx 校验 ZIP/OOXML 并由 ExcelJS 读取；TXT 必须是 UTF-8 中文标签分块或兼容的旧 TSV，支持 BOM/CRLF；中文选项按`${内容},${内容}`精确解析，旧 TSV 不能任意更换分隔符。
- 文件最大5MB、数据行最多1000。普通中文表头五列（试题内容、试题类型、选项内容、答案、难度），兼容旧四列；空难度默认easy，只接受简单／困难。普通入口必填有效category_id并覆盖整批类别。兼容英文七列category,type,difficulty,stem,options,answer,analysis；兼容旧九列及仅少concept或仅少score的两种八列，按表头映射防字段错位。旧concept非空固定行错误“考点组已取消，请清空后重试”；旧score任何值及公式仅忽略，不执行、不校验分数、不进入draft／指纹／题库／试卷赋分，warnings一次提示“旧模板分值已忽略，请在组卷时设置”。旧TSV列数须与识别表头一致；中文TXT校验标签、必填字段及选项包装；Excel按真实列索引拒绝超列数据／公式，业务列公式按行错误，真正空可选格不误判。
- 中文格式先把选项包装语法、答案字母及对／错规范化为内部数组；旧英文 `options/answer` 只接受 JSON 数组。每行随后进入 B3 `QuestionValidator`，因此 script/on*、javascript URL、外链图片与不属于操作者的受控媒体均无法借导入绕过。
- 预检只保存无概念／无分值draft、SHA-256重复指纹、行号、错误摘要及固定question_import_meta转换元数据到import_batch，不保存原文件。确认事务在排序类别锁后用锁定当前读复核重复指纹，媒体可用性查询沿用同一事务 manager；任一失败时题目、版本、媒体引用和批次结果整批回滚。前端把传输失败、502/504 与不可验证信封视为结果未知，只查询原批次且禁止另开预览；异步回包绑定 batch ID 和页面代次，离页后不得导航。

#### 4.3.5 一次性 AI 参考题的留存与来源边界

- 参考模板通过purpose=ai兼容参数下载，与普通导入统一为中文五列xlsx／标签TXT；页面选择并提交整批category_id。继续兼容旧英文七列、旧九列及仅少concept或仅少score的两种八列（旧客户端可沿用文件类别，旧concept非空拒绝，旧score仅warnings），≤5MB、≤50 参考行，先完成格式、类别及行校验再调用 AI。原文件和参考题正文只允许存在于当前任务内存；不写磁盘、MySQL、Redis、资料表、媒体表、审计详情或日志，成功、失败、超时后释放。错误只返回脱敏摘要，不回显参考题或供应商原始响应。
- Redis 只保存不含参考正文的任务状态与计数，TTL 24 小时；重启遗留未完成任务返回 failed，要求重新上传。`questions_ai` 批次只保存生成题及校验结果，未确认批次自创建起 24 小时有效，已确认回执继续保留。引用内容作为模型输入属于数据，不授予执行指令的能力。
- 类别、题型和目标easy／hard难度由服务端从已校验参考行和生成目标固定；生成题不带分值，丢弃模型伪造的来源、状态、审核人和制度版本。所有生成题经过统一客观题与富文本/媒体校验，异常行不能确认。生成阶段 `question/question_version` 零写入，只有选行确认事务创建启用的source=ai题目、revision1和enabled:true回执；兼容status=approved但审核元数据NULL，不伪造审核事实。
- 本功能明确允许 `source=ai` 且无 `regulation_id/version_id`，因为参考文件按产品要求不保留；不能把不存在的制度来源或审核事实填入快照。该例外只由 `questions_ai` 的服务端写入路径授予，人工DTO与普通questions导入仍不能伪造AI或资料来源；旧资料AI来源只读保留，其直接生成写路由已退场。
- 发起任务、修改生成行与单行重生成要求 `ai:write`；任务/批次读取、下载要求 `ai:read`；选行确认要求 `questions:write`。所有操作校验 owner，批次固定 `kind=questions_ai`；普通questions/students路径不得确认questions_ai批次。确认在同一事务锁定批次、复核合法行并写题目/revision/回执；同集合重试幂等，不同集合拒绝。确认后直接启用，不进入二次审核；当前候选仍须精确版本、启用身份、类别／难度／来源和媒体授权全部通过。

#### 4.3.6 题库启停、修订与历史保护

- questions:write负责人工保存、修订、文件／AI确认和启停；027只移除questions:review及其角色／菜单关联。旧review、concept CRUD、资料直接generate-questions和历史题直接regenerate写入口不注册，AI配置及旧任务／结果读取保留，不能绕过导入预览确认。
- 修订必须显式携带expected_version_id（真正legacy为null）和布尔expected_enabled，在锁定同一identity的事务内同时比较；不一致40940，零新版本、不恢复启用。停用题只有刷新并明确基于停用态提交才创建新版本并启用。启停本身带目标enabled及版本令牌，同目标幂等；恢复先锁内重验结构、类别、启用难度、来源和媒体。
- 旧未提交批次只读投影去concept／score，实际修改或确认仍重跑校验；已提交旧回执不改写、不重复建题。未知响应先GET原batch或原request回执，owner／kind隔离不放宽。
- 新候选／新发布按question_id去重，新release不写concept；发布锁内重验仍启用且仍指向选定current version。既有随机release显式historical-concept模式保持冻结concept分组，无concept回退question_id，预览和开考一致。后续修订／停用不改变旧release、assignment、attempt或成绩。
- 新题与新revision的概念、分值和审核元数据NULL，status=approved仅兼容，不表示真实审核发生；旧值与历史作者原稿保持原样。分值只由卷内关联／规则提供，禁止从历史question分数回退。

### 4.4 注入与 Web 通用防护

#### 4.4.1 SQL 注入防护

- 全部数据访问经 TypeORM **参数化查询**（占位符绑定），禁止任何字符串拼接 SQL（02 册 4.2 协同口径）；JSON 字段（`scroll_coverage` / `options` / `answer` / `selected`）的读写均为整存整取，无 SQL 层 JSON 路径拼接；
- 入参经 class-validator DTO 白名单校验（类型 / 范围 / 枚举合法性，03 册 1.7），非法值在写入前拦截；
- **数据库账号最小权限**：应用账号仅授予当前业务表及已审阅培训增量表所需的 SELECT / INSERT / UPDATE / DELETE，无 DDL / DROP / GRANT 权限；迁移执行器使用单独受控凭据，不能把 schema 变更权限混给日常 API——即使注入成立，破坏半径也被收敛。

#### 4.4.2 XSS 与 CSRF 防护

- **XSS**：Vue 默认插值转义；`v-html` 白名单仅限净化后的 `content_html`（4.3.2）；CSP 响应头保留 `default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'self'`；PC/H5 为 Vue、Element Plus、Wot 的运行时样式显式配置 `style-src 'self' 'unsafe-inline'`，不放开脚本内联或 eval。`img-src` 放行同源/data/blob、`media-src` 放行同源/blob、`connect-src` 放行同源；COS 启用时三者只额外允许经严格校验的标准 HTTPS 桶 origin，不使用域名通配或协议通配。Docker 构建从公开桶/地域/正式目录派生 Vite 配置并烘焙公开定位文件，Nginx 启动从同一文件生成 CSP，仅替换白名单模板变量；COS 凭据仍仅注入 API。配置改变须重建前端镜像，不能仅重启或混用运行期 origin；
- **CSRF**：业务 API 鉴权走 `Authorization: Bearer`，浏览器不会像 Cookie 一样自动为跨站请求附带 access。PC/mobile 的两个 refresh Cookie 均为 HttpOnly、SameSite=Strict，生产环境 Secure，分别限制在 `/api/v1/auth` 与 `/api/v1/mobile/auth`；刷新和登出只读取所属 Cookie，并校验令牌 client/auth_method/sid。公开 mobile 退出可凭 Cookie 执行，所以 Cookie 认证入口仍有 CSRF 防护需求，不能宣称攻击面不存在。当前同源部署依赖 SameSite=Strict 与既有 CORS 来源白名单；Cookie Path 用于减少自动携带范围，不替代服务端客户端身份校验，也不等于同源隔离。若未来采用跨站部署并放宽 SameSite，须先重新设计 Cookie 入口的 CSRF 防护。

| 数据导出 | legacy 未完成人员清单（现行前端无入口）及培训明确难度排名 Excel 导出；记录完整筛选与分页，不记录工作簿内容。当前培训统计只有原因人数聚合，不提供人员明细 |

**载体与格式**：结构化 JSON 文件日志（`audit` 日志通道，字段：`ts`、`actor_id`、`actor_name`、`action`、`object_type`、`object_id`、`detail`、`result`、`source_ip`），随日志卷持久化、logrotate 按天切割、**保留 ≥ 180 天**。

**管理端呈现**：导航与页面使用业务名称“操作记录”。默认只查询人工管理操作；登录与安全、考试事件、学员行为、系统事件及全部记录通过“记录范围”筛选查看，范围与结果过滤均在分页前完成。列表只展示时间、真实操作人、业务模块、中文操作、业务对象和结果；来源 IP、原始 actor/action/object 标识与 JSON detail 收进详情。菜单和角色的新写入记录名称快照及实际变化的 `before/after`，已有旧记录不追溯改写；缺少名称快照时以对象类型和 ID 兜底。人工角色维护、角色分配及强制下线必须传递当前认证账号和来源 IP，不得再伪装成 `system`；管理员强制下线记录 `auth.session.force_revoke`，普通会话吊销继续使用 `auth.session.revoke`。无人工身份的内部事件才显示为“系统任务”；失败登录若账号不存在，仍以“未认证账号”保留尝试账号。旧记录若名称为 `system` 但仍有 actor_id，页面显示“用户 #ID（历史记录）”，不把无法复原的姓名伪造成当前账号。

**中央脱敏与查询边界（A5）**：审计写入前递归遍历对象/数组，对 password/pwd/secret/token/authorization/cookie/api_key/credential 等敏感键置为 `[REDACTED]`。字符串值若是可解析 JSON，则解析后递归执行同一敏感键规则并重新序列化；非 JSON 文本会脱敏 Bearer 令牌及常见 `key=value`/`key:value` 的完整值（含引号内空格），而不是只遮住第一个单词。正常 JSONL 写入和文件系统失败后的 stderr fallback 使用同一处理，不为了诊断降级而输出明文。`GET /admin/audit-logs` 只读 `LOG_DIR/audit` 中符合 `audit-YYYY-MM-DD.log` 的普通文件，以 no-follow 方式拒绝符号链接，忽略损坏行，并在响应前再执行一次脱敏。首次尚无审计目录时返回空页；已经观察到的目录或目标日志若不可读、类型不符、读取中消失或发生其他 I/O 错误，则返回安全的 50004/HTTP 503，不得用空结果或部分结果掩盖故障。管理端没有“一键清空审计”或任何删除路由。

**载体取舍说明**：当前审计日志使用结构化 JSON 文件，不把审计写入业务表。新增资料或考试事实须通过同步 migration/init/entity/设计/API 落地并保留最小权限，不能只改某一层，也不能在文档中预设未实现字段。A5 通过受限目录的结构化查询 API 提供管理端查询，保留期仍由外部 logrotate 负责。

### 5.2 心跳高频写入的性能设计（17 QPS）

**压力估算**（03 册 6.3 写入点 1 口径）：500 人同时学习、心跳 30 秒/次 → 心跳请求 ≈ 500 ÷ 30 ≈ **17 QPS**；若每次心跳直写 MySQL（UPDATE `learning_session` + UPDATE `learning_record`）≈ 34 QPS 写入，且同一用户的 `learning_record` 行被高频独占更新，与统计读相互加锁。

**制度阅读：Redis 缓冲 + 批量落库策略**：

1. **心跳处理全部落在 Redis**：`learn:session:{session_id}` Hash 的 `HINCRBY duration_ms <本轮计入毫秒数>`（封顶 45000，见 3.1.2）+ 位图 OR 合并 + `last_beat_at` 更新——单命令 O(1)，17 QPS 对 Redis 单实例（512MB 级配置）余量超过两个数量级（02 册 3.5 理由 5）；
2. **落库批量收敛**：仅会话收口三触发（正常退出 / 90 秒无心跳判离线 / 5 分钟兜底任务，见 3.1.1）时一次性落库——数据库写频率从 ~34 QPS 降至**每会话一次**（≈ 500 人 ÷ 20 分钟平均会话 ≈ 0.4 QPS + 兜底批次），降两个数量级；
3. **Redis 故障降级（仅单实例部署适用）**（可用性优先，NFR-11 不丢已落库数据）：Redis 不可用时心跳路径退化为**直写 MySQL**——`learning_session` 行级增量 UPDATE（17 QPS 分散于不同行，InnoDB 行锁无热点冲突）+ 位图在应用内存合并、随收口任务写 `learning_record`；**该内存合并降级仅在单实例部署（5.6 阶段 0）下成立**——多实例阶段（5.6 阶段 1 起）Redis 故障时学习心跳直接返回 503 + 前端本地暂存重放，不做内存合并降级（实例本地态无法跨实例共享，见 5.6）；收口互斥以数据库乐观锁保证：`UPDATE learning_session SET ended_at = ? WHERE id = ? AND ended_at IS NULL`——影响行数为 0 即已被处理（与 3.2.4 交卷乐观锁同型），杜绝定时任务与用户主动收口并发导致的丢更新；恢复后切回 Redis 缓冲（与 02 册 AD-04「降级查库兜底」一致）。

**视频学习：逐拍 MySQL 持久化策略**：B2 为跨进程恢复 `last_seq`、位置锚点和去重区间，每个有效新序号心跳在单事务内锁定一条 `video_learning_session`，再锁定一条 `video_learning_record` 并各写一次。500 人全为视频时约 17 个短事务/秒、34 次分散行 UPDATE/秒；不存在同一用户多活动热点，索引均为主键/唯一键点查。这里不借 Redis 暂存，也不把重启前锚点丢给客户端重放。若实测 P95 超过目标，再在保持 DB 权威与 session→record 锁顺序前提下评估批量化，不能用累计时长替代覆盖区间。

### 5.3 统计查询性能

- **索引支撑**（03 册 6.4 已逐项设计，本册不重复）：应学人数（`uk_regulation_department` + `sys_user.idx_department_status`）、学习完成率（`learning_record.idx_regulation_valid`）、参考人数 / 通过率 / 平均分（`exam_record.idx_paper_status` / `idx_regulation_status`）、取最高分（`uk_paper_user_attempt` 前缀）、题目正确率（`exam_answer.idx_question`）；
- **题目正确率 / 得分率口径**（分母固化，FR-STT-04 题目质量分析输入）：`题目正确率 = SUM(is_correct = 1) / COUNT(*)`（NULL——主动提交中的未作答——计入分母、不计入分子；多选部分分is_correct=0，新纯timeout无答案行）；`题目得分率 = SUM(gained_score) / (COUNT(*) × paper_question.score)`（覆盖漏选部分分，用于难度分析）；
- **缓存叠加（键含维度与主体标识）**：制度维度缓存键 `stat:reg:{regulation_id}`（TTL 5 分钟）、部门维度 `stat:dept:{regulation_id}:{department_id}`；**个人维度一律不缓存**（数据主体唯一、命中率低、越权风险高——不同主体复用同键将造成跨用户数据泄露，违反 2.3.3「employee 仅本人」边界）；失效按 `stat:` 前缀 `SCAN`（非 `KEYS`，避免阻塞）匹配 `regulation_id` 批量主动失效 + TTL 兜底——统计低频变更（考试结束后才变），命中率天然高；
- **C6 实时查询边界**：培训 summary/ranking/dashboard 当前不缓存，直接按 `paper_id`、最新 release、冻结规则/难度与当前人员/课程版本读取；因此学员变更、视频换版或自动评分完成无需新增缓存失效链。legacy 制度缓存保持兼容。看板新趋势支持7/30日，先按UTC `started_at` 半开区间过滤，再按 `Asia/Shanghai` 自然日及学员取首条冻结来源；旧7日记录趋势兼容保留，不能依赖数据库会话时区或浏览器本地时区；
- **大表聚合评估**：最大表 `exam_answer` 三年累计约 300 万行（03 册 6.2），在 `idx_question` / 唯一键支撑下单制度聚合为毫秒~百毫秒级，**当前量级直接查库即达标，无需预聚合表**；预聚合的引入触发条件与 A-05 边界：单表 > 1,000 万行或统计 P95 持续 > 3 秒时再评估——届时预聚合结构须先修订 README（与 NFR-16 的表变更约束一致），预聚合结果本身可先落 Redis（不引入新表）过渡。

**运营看板实测边界（2026-10-27）**：五卡逐项权限裁剪，四个独立统计接口显式要求 `statistics:read`，跳转记录另查 `exam_records:read`；前端整体替换metrics，403/会话吊销清除旧数据。无统计缓存、轮询或推送。隔离MySQL8.0.46上1万账号/10万考试、5次预热后50样本P95：30日趋势294.0ms、学时15.4ms、最近考试654.4ms；实际EXPLAIN不读答案表，本样本无需新增索引。Kimi真实浏览器验证权限收回、错误/重试与ECharts尺寸/缓存生命周期；这些结果不替代生产容量或部署验证，见[验收记录](../../review/2026-10-27-admin-operations-dashboard-acceptance.md)。

### 5.4 AI 调用与文件解析的异步化

两项长耗时操作均不阻塞主请求线程（NestJS 事件循环 + 异步任务，02 册 3.3 选型理由 2；架构决策 AD-03）：

| 操作 | 异步设计 |
|---|---|
| 文件解析 | 上传接口校验四步（4.3.1）通过即返回字符串版本 ID 与 `pending`；解析任务进队列（内部可复用 legacy 版本表索引 + Redis 队列加速），由独立 worker 执行；完成后写 `content_html` / `text_content` 并流转 `parsed / failed`。≤ 20MB 文件 60 秒内完成，20~50MB 大文件排队执行不阻塞其他操作；失败版本可显式重试 |
| AI出题 | 当前参考题AI发起后返回task_id，最多50参考行、每行最多easy/hard两题；后台超时和失败只给脱敏计数，参考正文仅内存。模型输入按数据处理、可信类别／题型／目标难度及source由服务端固定，统一结构与媒体校验并拒绝完整参考片段／选项集合复用；生成、修改与行重生成只写预览批次，选行确认才原子创建启用题。旧资料生成写入口退场，AI配置／旧任务读取继续保留。 |
| AI 参考题生成 | 独立导入页发起后只返回任务状态；参考文件在内存解析，每题最多生成一对 easy/hard。完成后只创建生成题预览批次，管理员确认才原子创建启用题与兼容 approved、审核元数据 NULL 的版本。任务轮询失活/离页即停止，晚到回包不覆盖页面。参考文件不落盘、不随任务状态持久化，重启后的未完成任务读取为 failed，不自动重放 |

## 6. 可用性与可维护性

### 6.1 Docker Compose 健康检查与重启策略

| 服务 | 健康检查（healthcheck） | 重启策略 | 依赖顺序 |
|---|---|---|---|
| mysql | `mysqladmin ping`（间隔 10s，超时 5s，失败 5 次判 unhealthy） | `restart: unless-stopped` | 无 |
| redis | `redis-cli -a $REDIS_PASSWORD ping`（间隔 10s） | `restart: unless-stopped` | 无 |
| api | HTTP `GET /api/v1/health`（探活 MySQL 连接池 + Redis PING + 磁盘余量，间隔 15s） | `restart: unless-stopped`（`on-failure` 不适用——进程退出多为发布重建） | `depends_on: mysql(service_healthy) + redis(service_healthy)` |
| nginx | 无独立健康检查（无状态反代） | `restart: unless-stopped` | `depends_on: api(service_healthy)` |

单点故障语义（NFR-11：可用性 ≥ 99.5%，单点故障不丢已落库数据）：mysql / redis / api 任一故障时各自重启策略拉起；Redis 故障期间降级矩阵见 6.2.2 与 5.2——**已落库的 `learning_record` / `exam_record` 数据零丢失**，仅临时态（暂存答案、倒计时键）受短暂影响。

### 6.2 MySQL / Redis 数据持久化与备份

#### 6.2.1 MySQL

- 崩溃恢复由 InnoDB redo log 保证（已提交事务不丢失，03 册 1.2 理由 3）；
- 备份策略见 4.2.3（每日 `mysqldump --single-transaction` + binlog ROW 增量，30 天滚动保留）。

#### 6.2.2 Redis（RDB / AOF 取舍）

**定稿：AOF（`appendfsync everysec`）+ RDB 快照混合持久化**（Redis 7 `aof-use-rdb-preamble`）。

| 方案 | 取舍 |
|---|---|
| 仅 RDB | 恢复快，但快照间隔内的数据全丢（学习累计、考试暂存答案可能丢 15 分钟以上）——不可接受 |
| 仅 AOF everysec | 最多丢 1 秒，但重启恢复慢（重放全量命令） |
| **混合（定稿）** | AOF 文件前段为 RDB 全量快照 + 后段增量命令：恢复速度接近 RDB、丢失窗口 1 秒 |

丢失窗口的语义评估：Redis 中只存**可再生临时态**（AD-04）——学习会话累计（最多丢 1 秒心跳累计值）、考试暂存答案（最多丢 1 秒内的暂存写入，下一次对齐暂存即补回）、倒计时键（可由 `exam_record.deadline_at` 快照重算，3.2.3）。**任何情况下已落库的学习与考试数据不受影响**（NFR-11 验收口径）。

内存策略：`maxmemory` 规划 512MB + `maxmemory-policy noeviction`（**除配置读缓存 `ai:config:cache`（TTL 10 分钟、可再生，4.2.2）外，业务键均带 TTL 自然过期**——见本册各键定义；`exam:answer` 的 TTL = `duration_minutes × 60 + 24 小时`、交卷后主动 DEL，见 3.2.4；内存不足时告警扩容而非静默淘汰业务键，02 册 3.5 风险 R3）。

### 6.3 日志与监控

**结构化日志**（02 册 5.2 口径：生产 info 级）：JSON 格式（pino），字段含 `ts` / `level` / `request_id` / `user_id` / `module` / `action` / `duration_ms` / `status`；随容器日志卷持久化 + logrotate 按天切割保留 30 天；审计日志独立通道（4.5，保留 180 天）。关键链路（解析、AI 调用、交卷评分）日志可排查（NFR-16）。

**关键业务指标监控项**（内网环境以轻量 exporter / 日志聚合实现，不引入额外重型组件）：

| 指标 | 采集口径 | 告警示例 |
|---|---|---|
| 心跳 QPS | 心跳接口请求速率 | 骤降 > 50%（大面积离线 / 前端异常）；持续 > 25（超并发预估） |
| 心跳落库延迟 | 收口任务批处理耗时 | P95 > 5 秒 |
| AI 调用成功率 / 延迟 | AI 网关出口指标 | 成功率 < 90%（10 分钟窗口）；超时率 > 10% |
| 资料解析队列积压 | 出题资料版本中 `parse_status = pending` 的数量与最老任务年龄 | 最老 pending > 5 分钟 |
| 交卷判分耗时 | 交卷接口耗时 | P95 > 3 秒（NFR-02 红线） |

## COS访问与容量补充约束（033）

沿用gooodwork私有COS短链；两个后端共用原SecretId/SecretKey，但RuleExam数据库独立，adapter拒绝自己的prefix外定位。SecretKey仅后端环境注入，前端只获受限上传临时授权或GET签名URL；完整签名不记录日志、不入业务数据。URL中的q-ak仅签名身份标识，不等于SecretKey。

申请/续签重新检查当前状态、权限和精确引用；已签URL在默认300秒或配置期限内仍可能有效（上限3600秒）。这是用户选择gooodwork模式后的显式边界，替换COS分支的即时撤权要求；local/实名代理继续每请求授权。纯timeout/在考解析/错owner不签新链接，identity/staging不进入普通GET签名范围。

PC/H5精确HTTPS桶域名与正式目录/query白名单、账号epoch、单飞续期和有界重试分别验证；COS版本未开启时用后端唯一不可覆写正式key，开启或暂停版本时按供应商实际VersionId准确读取，不强制修改共桶版本设置。

容量按媒体、签票、登录/开考/交卷突发、30秒心跳分别测500/1000/3000阶梯。默认 `tests/performance/media-capacity.mjs` 只估算，明确测试场景加--run才发请求。记录压测机与服务端指标、真实达到并发；四项工具单测不等于真实数千并发通过。
