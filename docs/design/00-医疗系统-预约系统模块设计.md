### 1.6 已找到的真实业务链路

```text

```

**保存预约**：`Business/ZYBookService.cs:189—345`。

1. :199—208 找治疗单；:210—220 APP 黑名单检查。
2. :222—239 查同人同班段重复、可配置预约次数不得超过治疗次数。
3. :241—255 查班段、停诊及线上/现场余量；:256—261 查同人时间重叠。
4. :262—267 查患者；:269—305 写带项目/时段/患者快照的待报到预约。
5. :306—343 写扩展明细、更新已约计数、写流转日志。

实际接口为 `POST zyBookInfo/saveBookInfo`，并非支付订单创建接口。“加号”与普通线上/现场预约分支不同，不建议培训系统用加号绕过总容量。

**取消预约**：`Business/ZYBookService.cs:642—762`。

- :648—674 读截止配置、检查预约存在且是 ToReport；截止规则只限制 APP。

**记录查询**：`Business/ZYBookService.cs:76—182` 为本人列表/详情，`:769—1020` 为管理、患者、周维度列表。

**周期复制**：`Business/ZYBookService.cs:353—636` 读取源日期和目标日期范围，结合治疗师预约、其他治疗师和高压氧安排做复制检查；这属于医疗排程复用，不是企业多人预约，更不是“付款后批量占位”。培训项目如需重复安排，应重新检查每次资格/容量，不能盲目复制旧预约。

### 1.8 参考内容的采用方式

| 可借鉴的源码模型 | 本系统需要新增或改造的设计 |
|---|---|
| 班次、周规则、日期资源、班段余量 | 固定海珠场地、统一场地容量、项目适用范围 |
| 个人预约、取消、流水和历史 | 先付款取得资格、改期、退款及幂等补偿 |
| 本人列表和管理查询 | 企业/班组档案、成员预检、统一付款、逐人预约 |
| 黑名单、取消通知与任务 | 预约限制有效期/解除、成功与提醒、核销及真实统计 |

线上/现场名额是**预约渠道**，个人/团队是**报名组织方式**，两者不能直接一一替换。建议个人和团队共享场地总容量；是否预留团队额度须另作配置，不能把团队人数加在总容量之外。

## 2. 培训预约需求与功能模块（新设计建议）

### 2.1 业务目标与范围

让个人和企业清楚知道“买什么、多少钱、何时有位、预约是否成功、到场怎么办、取消后钱和名额怎么办”。机构能统一排班、限制容量、处理批量名单，并把到场记录与现有培训考试衔接。

首期地点固定为海珠区，学员页面直接展示地址、交通、联系电话，无须先选分校。后台保留一条场地资料，不开展多机构、多分校运营。企业和班组只是报名组织，不是租户、权限角色或现有部门，不恢复已退场的部门 CRUD。

预约板块覆盖项目与收费、场地和排期、个人购买预约、团队预约、预约记录、改期取消、退款对账、到场核销、限制名单、通知与统计。不开建设计医疗套餐、医生、病历、保险结算；证书、支付营销和完整教务班级体系也不在本次范围。

### 2.2 用户角色与数据范围

| 角色 | 主要操作 | 数据边界 |
|---|---|---|
| 学员 | 购买、付款、查看可约时段、预约、改期取消、退款申请、查看通知及核销码 | 仅本人订单、资格和预约 |
| 企业／班组联系人 | 提交名单、确认安排、接收团队通知 | 首期由机构代办；后续自助必须绑定组织授权，不能凭组织 ID 查全员 |
| 预约管理员 | 配项目/排期、代办团队、处理预约与名单 | 由现有按钮权限授权 |
| 财务人员 | 确认线下款、审核退款、查对账差异 | 按财务权限，不默认拥有试题答案或实名材料读取权 |
| 核销人员 | 核对到场身份、逐人签到、看当天名单 | 最少必要信息；核销不等于交卷 |

账号沿用 sys_user。联系人可有业务档案但不必自动生成账号；企业导入不能把共享手机号当作不同学员的唯一账号，也不能绕开现有实名流程。

#### 2.4.2 PC 管理端

新增“预约管理”菜单，包含项目设置、时段排班、预约记录、团队预约、到场核销；财务可独立拥有订单退款与对账入口。限制名单、通知记录、预约统计由对应按钮控制。

排班页按日/周查看，每行显示总名额、已约、余量、个人/团队分布与开放状态。团队详情先给导入模板，同时允许立即上传；预检错误定位到行，确认前不写预约。预约详情展示订单→资格→预约→核销→考试关联，不把所有状态压成一个“已完成”。

### 2.5 核心规则

#### 2.5.1 排期与名额

- 时段为实际起止时间，`start_at < end_at`；预约截止不晚于开始时间。具体提前多久由运营配置。
- 同一物理场地首期禁止重叠时段，避免两个项目分别卖满同一批座位；如未来确有独立教室，再引入真实资源并分别排班。
- `剩余名额 = capacity_count - reserved_count`。已确认、已核销、已缺席名额均保留该场次占用事实；取消才释放。历史利用率另外按有效预约与核销人数算。
- 减少容量不得低于已占名额。满额不能靠修改前端数字放行；增加容量需权限和审计。
- 发布时校验场地、项目、试卷及排期冲突；隐藏/停用项目不删除旧订单和预约。

#### 2.5.2 个人付款与资格

一个订单明细购买一个项目的一次到场资格，资格绑定本人、项目版本和有效期。金额用整数分，服务端计算。支付成功才生效，前端成功页和人工截图不能作为到账依据。

资格在有效期内可以预约一次；提前取消可恢复可用资格，改期复用原资格。建议到场核销后消耗资格，缺席进入待处理，不能自动免费重约，也不自动退费。购买的“一次到场”与试卷的多次作答分别展示；补考是否需重新付费属于收费政策，不能由考试失败事件自动扣费。

#### 2.5.3 团队预约

企业可以包含班组，班组归属于一个企业；也可有独立班组组织。联系人维护组织关系，学员归属作为本批次报名快照，不覆盖现有来源 institution/external 或培训类别。

流程为“建批次→导入名单→预检→确认报价→付款确认→逐人资格→选时段→确认预约”。同一企业可跨时段拆分，剩余未安排人员明确显示。默认同一提交批次全部成功或全部失败，不能只扣一部分名额却提示全部成功；管理员可以显式先选择部分成员提交。

名单校验：姓名/手机号必要性、账号匹配、重复成员、培训类别、项目适用范围、同人重复预约及同时间冲突。证件信息仅在确需实名时走原有受控流程，普通 Excel 不默认收身份证原图或完整证件号。不允许凭手机号覆盖已有账号资料。

**团队支付建议**：首期统一预付，机构代办可登记线下对公到账（需财务授权与凭证审计）。月结、定金和先占位后补名单作为待确认扩展，不默认允许。团队人员不能在本人 H5 把企业款申请退到个人账户；取消/改期由管理员协调，团队付款方提出退款。

#### 2.5.4 退改、缺席与限制

建议将“自主取消/改期截止时间、免费改期次数、资格有效期、缺席处置”配置化并随订单冻结。草案不指定未经确认的小时数或收费比例；未配置有效政策的项目禁止开售。

取消释放名额但不等于退款。退款冻结对应可用资格，财务审核后原路退款；拒绝退款解除冻结。已核销/已开考原则上不自助退，机构原因停场进入专门处置。缺席不自动拉黑；限制名单由授权人员确认原因、期限并允许解除，查询及提交时都校验有效限制。

#### 2.5.5 预约与学习考试

建议预约关联的项目明确“到场培训/到场考试”，展示已有学习要求。付款与预约不绕过原学习时长、实名、类别来源、发布状态或考试次数限制。

是否把预约作为开考硬门槛是业务待确认项：建议仅对显式设置 `requires_booking` 的培训考试启用，不影响其他考试或 legacy 制度卷。建议该模式要求有效预约、本人核销及开考窗口；具体窗口独立配置，不能把时段结束误当成自动交卷时间。

### 2.6 待业务确认清单

| 决策 | 本草案建议 | 对结果的影响 |
|---|---|---|
| 预约购买的服务 | 一次到场培训考试，列清课程/考试和费用包含项 | 决定补考与复约收费 |
| 支付渠道 | 接入机构已有商户渠道；开发前确定 H5/微信可用范围 | 决定真实支付联调与资质 |
| 团队结算 | 统一预付，支持财务确认对公到账 | 若需月结，需增加授信与逾期规则 |
| 退改与缺席 | 截止前可取消恢复资格，退款另走审核；缺席人工处理 | 决定金额、有效期与消费者展示文案 |
| 考试衔接 | 指定考试启用核销及时间门槛，旧考试保持现行规则 | 决定开考事务与上线切换 |
| 时段容量 | 单场地统一总容量，不开放跨项目重叠排期 | 若能并行上课，需核实教室资源 |

这些事项不妨碍审阅模块设计，但正式开售和生产配置前必须确认；其余工程细节按本册第 3—7 章建议执行。

## 3. 系统架构与集成边界（建议）

```text
学员 H5                      PC 管理端
   |                            |
   +------ 现有认证/按钮权限 -----+
                |
       预约服务（新模块）
       | 项目/排期/个人/团队/核销
       +----- 订单与支付适配（新模块）---- 支付渠道
       +----- 通知任务（新模块）-------- 通知渠道
       +----- 现有学员、课程、培训考试
                |
       MySQL 权威事实 / Redis 临时缓存
```

建议采用当前 NestJS、TypeORM、MySQL 技术栈实现业务规则，不直接移植参考系统 C#、医疗视图或微信患者身份。参考系统的“模板→周规则→日期资源→具体班段”可转为“时段模板→按周排期→某日时段”；首期允许直接批量生成日期时段，不要求照搬医院排班审核层级。

现行入口依据：`server/src/modules/exams/training-exams.controller.ts:30—103` 调用 AttemptService、SubmissionService 和 ExamHistoryService；`server/src/modules/exams/attempt.service.ts:275—444` 先恢复进行中记录，再校验实名、发布状态、类别、次数和学习要求，创建冻结题单。预约接入须保持这个顺序，不能把取消预约作为删除进行中考试的理由。

建议只在**新建考试尝试**前增加预约策略校验；进行中恢复和原交卷规则保持现有边界。指定考试启用预约要求后，须同时覆盖所有能创建该考试记录的入口，不能只在 H5 按钮隐藏。上线前需补全调用路径核查，本次没有声称已完成全入口改造。

项目绑定已发布试卷时记录发布版本。现有 AttemptService 在无个人 assignment 时取最新 release，在已有 assignment 时复用其冻结版本；因此不能仅传 paper_id 就声称按预约时版本开考。建议接入时显式核对预约的 release_id 与即将使用的 assignment/release，不匹配则阻断并人工改配/退改；不得悄悄换卷，也不改历史 assignment。

## 4. 数据模型与接口草案（新增建议，非现有表/API）

### 4.1 建议数据实体

以下为逻辑模型，便于评估工作量，**不是可直接执行的 DDL**。实施前补齐字段类型、索引、枚举和完整接口 DTO，并同步主设计 03/04 册、迁移、init.sql、entities。迁移编号届时按实际主线顺延，不预占或重写现有迁移。

| 建议实体 | 核心内容 | 关键约束 |
|---|---|---|
| booking_project / booking_project_version | 名称、类别、课程、paper_id/release_id、价格分、服务与退改政策快照 | 成交引用不可变版本；下架不删历史 |
| booking_venue | 固定海珠场地、地址、联系信息 | 首期单场地；具体地址由运营录入 |
| booking_slot_template / booking_schedule_rule | 起止时间、周规则、容量、开放提前量 | 可选用于批量生成；修改模板不改已生成时段 |
| booking_slot | 日期、场地、项目适用范围、起止/开放/截止、容量、占用、状态、版本 | 场地排期互斥；占用不超过容量 |
| booking_organization | 企业或班组、上级企业、联系人 | 不写入现有部门/租户模型 |
| booking_batch / booking_batch_member | 团队批次、组织、名单、逐人匹配/付款/预约结果 | 批次内成员唯一；保留导入预检回执 |
| booking_order / booking_order_item | 付款方、个人/团队、项目版本、数量、应收与实收、订单号 | 金额服务端计算；订单号唯一；明细可追到人 |
| booking_payment | 商户/渠道交易号、金额币种、支付与查单状态 | 渠道交易唯一；重复通知不重复发资格 |
| booking_entitlement | 本人、订单明细、项目、有效期、可用/占用/消耗/退款冻结 | 单份资格同一时刻至多一条有效预约 |
| booking_record | 本人、资格、slot_id、批次、时间地点项目快照、预约状态 | 本人时间冲突事务内检查；历史不物理删 |
| booking_refund | 付款方、订单明细、金额、原因、审批与渠道结果 | 处理中+成功金额不超过实收；原付款路径 |
| booking_checkin | 预约、核销人员/时间、撤销原因、凭证摘要 | 每预约一个有效核销；凭证不可推算且不带身份证 |
| booking_restriction | 本人、原因、起止、操作者、解除记录 | 有效期在服务端判断；不扩成全系统封禁 |
| booking_event / booking_outbox | 操作流水、幂等请求摘要、事务消息、通知投递结果 | 金额/名额变更可追溯；任务重复投递安全 |

沿用主设计 BIGINT ID 对外转字符串、snake_case、金额整数分、东八区 DATETIME(3)、无外键、服务端维护引用完整性的约定。索引至少覆盖本人记录、时段名单、订单明细、组织批次、渠道交易唯一与幂等键。跨时段重叠不能只靠唯一索引，需要串行化本人预约写入。

### 4.2 接口分组草案

路径均建议置于现有 `/api/v1` 前缀下；下表不是参考系统接口，也未在当前项目实现。所有普通响应沿用 `{code,message,data}`，DTO 走 DtoValidationPipe；支付回调按供应商协议响应，不强行套业务信封。

| 建议接口 | 用途与校验 |
|---|---|
| `GET /booking/projects`、`GET /booking/slots` | 可售项目、只读可约日期与余量；查询不占位 |
| `POST /booking/orders`、`GET /booking/orders/:id` | 创建本人购买订单、查权威支付状态 |
| `POST /booking/orders/:id/payments` | 发起支付，不接受客户端自定金额 |
| `POST /booking/payment-notifications/:provider` | 验签、商户、交易、金额币种校验、幂等入账 |
| `GET /booking/entitlements` | 本人可用、占用、退款冻结资格 |
| `POST /booking/records`、`GET /booking/records` | 提交资格+时段、查询本人记录 |
| `POST /booking/records/:id/reschedule` | 原子改期；expected_version + request_id |
| `POST /booking/records/:id/cancel` | 状态校验、取消原因、释放名额、资格恢复 |
| `POST /booking/refunds`、`GET /booking/refunds/:id` | 付款方申请/查询退款，团队款不向成员退 |
| `/admin/booking/projects`、`/admin/booking/slots` | 项目与排期增改查、批量生成、关闭、容量调整 |
| `/admin/booking/organizations`、`/admin/booking/batches` | 企业班组、名单预检/确认、批量预约与逐人处置 |
| `POST /admin/booking/orders/:id/confirm-transfer` | 财务确认对公到账；凭证、原因与幂等 |
| `POST /admin/booking/records/:id/checkin` | 核销；本人身份及有效凭证验证 |
| `/admin/booking/refunds`、`/admin/booking/restrictions` | 退款审批查询、限制/解除 |
| `GET /admin/booking/statistics` | 时段、团队、到场及收退款只读聚合 |

写操作使用持久 request_id 与请求摘要：同键同内容返回原结果，同键异内容拒绝。查询仅本人；管理端按按钮权限；组织自助若实施则另校验联系人与组织成员关系。错误码应从现有错误码注册表分配，草案不编造已存在的数字。

### 4.3 名额与多人提交的一致性

个人预约在同一事务锁定本人预约写入锚点、资格和时段，检查付款、限制、有效期、重复和重叠，再执行条件扣减、创建预约、占用资格、写流水及 outbox。时段名额可采用条件更新：仅当 `reserved_count + N <= capacity_count` 且时段仍开放才增加；受影响行数不是 1 就失败回滚。团队 N 为本次实际确认成员数，不是表单人数。

团队锁按成员 ID 和时段 ID 固定顺序获取；任何成员失败默认整批回滚。改期先验证目标并在同一事务中完成新位占用、旧位释放、原记录变更；新时段满额时旧预约不丢。不能先取消再另请求重约。

取消先锁记录并检查当前状态，只有首次合法转换才释放一次名额；重复请求返回原结果。退款冻结和预约占用竞争同一资格锁，退款中不允许重新预约。所有外部支付、退款、通知请求在本地事务外发送，采用持久任务与结果查询收敛，不能长时间占数据库锁等网络。

## 5. 关键流程与状态设计（建议）

### 5.1 个人先付款再预约

```text
项目说明/余量预览 → 确认价格与政策 → 创建订单 → 发起付款
                                          |
                          回调验签/主动查单确认到账
                                          |
                               发放本人预约资格
                                          |
                          选日期时段 → 事务校验并占位
                                          |
                          预约成功 → 提醒 → 到场核销
                                          |
                          原学习/考试资格检查 → 原考试
```

支付成功而没有合适时段：资格保持可用，展示有效期、可约余量与联系客服/退款入口，不虚构预约成功。支付回调丢失：服务端查单后补发资格；重复回调不重复发放。支付成功页面不能代替服务端到账确认。

### 5.2 团队统一安排

```text
机构建企业/班组批次 → 下载模板/上传名单 → 预检与账号匹配
       → 确认项目/人数/报价 → 企业统一付款/财务确认到账
       → 逐人发放资格 → 选择本次成员和时段 → 原子批量预约
       → 逐人通知与核销 → 原学习/考试 → 团队汇总
```

导入预检不写账号和预约。创建学员须走现有学员管理授权服务，不能静默改现有账号。变更名单要区分未付款、已付未预约、已预约、已核销阶段；已核销成员不得被替换。首期建议只允许同一付款批次内未使用名额经管理员撤销重配，必须保留前后成员与金额流水，不直接改历史预约 user_id。

成员取消不自动取消整个团队。部分退款以订单明细为单位核对未消耗资格，退款仍回企业原付款路径。线上款调用渠道原路退款；线下对公转账由财务审核、付款复核，退至经核验的原付款企业账户，再登记退款流水与到账凭证，不调用在线渠道退款 API。前端不得任意指定收款账户。预付后长期未安排的成员在批次中单列，不视为预约成功。

### 5.3 机构停场与改期

关闭某时段先阻断新预约，再列出全部受影响人员、付款方和进行中考试。已有预约不得批量静默删除。管理员选择经确认的替代时段，或取消并恢复资格/发起退款；原记录保留原因及关联新安排。对已经开始的考试仅处理到场业务，不重置考试或自动交卷。

通知失败不回滚已经成功的预约，但必须进入待处理清单；联系人知悉不能替代每位成员当前预约记录的更新。

### 5.4 状态分别记录

| 对象 | 建议状态与转换 |
|---|---|
| 订单付款 | pending → paid；pending → closed；关闭后收到晚到付款先查渠道事实再补发或退款处置 |
| 单笔支付 | initiated → processing → succeeded / failed；不确定保持 processing 并查单 |
| 资格 | available → reserved → consumed；提前取消 reserved → available；available → refund_frozen → refunded，拒绝退款恢复 available；reserved → no_show_pending → consumed / available；过期由服务端判定 |
| 预约 | confirmed → checked_in / canceled / no_show；改期保留事件并更新版本；核销撤销需授权且未开考，同事务恢复预约 confirmed、资格 consumed → reserved |
| 退款 | requested → approved → processing → succeeded；requested → rejected；processing 不确定时先查单，不盲目重复退款 |
| 时段 | draft → open → closed / finished；closed 保留预约和处置进度 |
| 考试 | 沿用原考试状态；预约不自行增加“及格/不及格”或改写分数 |

核销时资格消耗；缺席后的资格进入 no_show_pending 冻结待处理，管理员根据已公示政策决定消耗或恢复。资格已占用于有效预约时，即使有效期后来届满也不自动取消该预约；有效期只限制新的预约/改期，具体例外须在政策中说明。预约 canceled 不是 refund succeeded；checked_in 不是考试通过。

### 5.5 超时与补偿任务

任务覆盖待支付关单前查单、支付结果补查、退款结果补查、未来排期生成、预约提醒、缺席标记、限制到期、消息重试和容量对账。任务进度和幂等依据落 MySQL，Redis 丢失不影响预约事实。名额与有效预约计数不一致时报警并按明细核对，不能不留痕覆盖计数。

## 6. 安全、统计与运营口径（建议）

- 继续使用现有登录会话、Redis 吊销及按钮权限；不移植微信患者关联和医疗卡号身份。核销人员只看最少身份信息，二维码不含证件号或长期访问令牌。
- 团队名单、手机号、付款凭证、导出均鉴权和审计。导入限制大小/行数、校验文件内容；导出防电子表格公式注入；测试不使用真实证件或支付密钥。
- 支付/退款回调验签、防重放、校验商户归属与实收金额；密钥运行期注入。订单归属不能由客户端 user_id 决定；退款不得接受任意收款账户。
- 核销凭证是可撤销的短期随机凭证，改期/取消后旧码失效；扫码操作须后端鉴权、核对预约状态并留痕。
- 预约数按预约成功事实统计；改期不增加购买人数；当前有效预约剔除取消。到场率 = 同一统计期间已结束且未取消预约中的已核销人数 / 同期已结束且未取消预约人数，分母为零显示“—”；缺席在时段结束后按规则收口。
- 时段使用率 = 当前有效占用人数 / 容量；历史统计记录容量变更依据。个人/团队按预约来源分组，不能把团队一批算成一个人。
- 实收、退款中、已退款分别展示；净收 = 已确认实收 - 成功退款，申请退款不提前冲减。考试通过率沿用原考试统计口径，仅做预约关联，不因多次预约重复计分。

## 7. 验收场景与实施顺序（建议）

### 7.1 可验收结果

| 场景 | 预期结果 |
|---|---|
| 未付款直接预约、伪造前端付款成功 | 后端拒绝；无预约、无名额扣减 |
| 个人付款成功但时段满额 | 保留可用资格，提示重选或申请退款，不显示预约成功 |
| 30 个名额同时提交 50 人 | 最多成功 30 人，DB 预约/资格/计数一致，无负余量 |
| 余量 5，团队一次提交 6 人 | 整批失败且零扣减；可显式选 5 人重新提交 |
| 不同时段有时间重叠，同人并发预约 | 至多创建一条符合规则的预约，不能靠不同请求绕过 |
| 重复预约/支付回调/取消/扫码 | 返回已存在结果，不重复扣位、发资格、退位或核销 |
| 改期目标满额/断网重试 | 原预约保留，重试按幂等回执收敛 |
| 取消与退款/再预约同时发生 | 资格状态唯一、无双重占用、不重复退款 |
| 团队部分成员取消 | 只释放对应成员名额，其他预约保持；退款回付款方 |
| 团队名单错误、重复、已有账号 | 预检逐行报告，不覆盖原账号，不提前创建预约 |
| 时段减少容量/机构停场 | 不低于已占容量；停场有受影响清单、处置与通知记录 |
| 付款回调丢失、重复、晚到，渠道退款超时 | 查单与补偿收敛，不能重复收费或凭本地关单丢弃实收 |
| 名额表缓存丢失、任务重启 | 从 DB 恢复；有效预约不丢；消息安全重试 |
| 预约后项目涨价/修改政策/重新发布试卷 | 原订单按快照；开考版本核对，不偷偷换卷或覆盖历史 |
| 未实名/学习不足/次数已用尽 | 沿用原拒绝规则，付款不绕过，失败不新消耗考试次数 |
| 已开始考试后取消/停场/时段结束 | 不删考试，不自动提交评分；按原 deadline 和交卷契约处理 |
| 跨用户/跨组织查询、猜核销码、伪造回调 | 拒绝并留审计；不泄露名单、订单或实名资料 |
| 财务确认到账/退款/核销撤销 | 需独立权限、原因与可追溯记录 |

### 7.2 建议实施顺序与验证边界

1. 先确认第 2.6 节的服务、收费、退改和开考门槛，形成批准版本；文档中的建议不自动生效。
2. 完成项目、场地时段、订单资格、个人预约及幂等/并发闭环。
3. 接入团队名单、统一结算、批量占位、核销与原考试衔接。
4. 补齐退款对账、机构停场、限制名单、通知、统计；正式运营前完成 P0 全链路，不能以“后续做退款”为由先卖课收费。
5. 数据迁移/构建/API 自动验证、PC/H5 操作、真实支付渠道、真实手机、部署验收分别登记；本次只交付源码核对和设计文档，没有执行上述运行验收。
