## 已确认决定

以下 D01—D38 保留用户确认时的原文与上下文；其中“尚未实现/待设计”等是当时状态，不是当前实施结论。例如 D06 的根构建脚本已于 Task 15/Gate I 落地，现状以下文实施事实和 Gate J 收口记录为准。

### D01：交付优先级与平台

- 首版交付 H5，按微信小程序兼容要求组织代码。
- 后续小程序只考虑微信；App 不是当前确定交付目标，留待后续评估。
- 确认依据：“重点做好h5和小程序”；回答是否仅微信时说“是的，只考虑微信”。
- 不因此推定微信登录、微信审核发布或 App 打包已经进入首版范围。

### D02：学员端技术栈

- uni-app + Vue 3 + TypeScript + Wot UI v2 + Pinia。
- 采用传统 uni-app 路线，不把 uni-app x 作为当前实施目标。
- Wot 提供基础组件，业务组件承接题目、答题卡、课程等界面，外观参考 `gemini.pen`。
- PC 管理端继续使用 Vue 3 + Element Plus。
- 确认依据：用户对上述选型说“上面的你的建议我都同意”，后续继续确认已汇总架构。

### D03：工程与后端关系

- 独立 `mobile/` 学员端工程，与现有 `web/` 管理端并列。
- 两个前端共用现有 NestJS 后端及业务数据。
- 学员端共用页面与业务逻辑，平台差异集中适配；不直接把 PC 工程改造成 uni-app。
- 确认依据：对独立工程和共用后端建议表示同意，之后按此继续讨论部署。

### D04：首版登录入口

- H5 使用手机号验证码登录。
- 小程序初期沿用该业务登录方式；真正实施小程序时再优化微信专属登录与授权。
- 确认原话：“先采用h5的手机验证码，到时候真的做到小程序，我再优化”。
- 不新增已确认的微信一键登录、自动关联规则或微信身份数据模型。

### D05：源码分开、同域合包部署

- `web/` 和 `mobile/` 源码分开，发布时合成一个目录，部署一次同时发布 PC 与 H5。
- 仓库根 `dist/` 放 PC 产物，`dist/mobile/` 放学员 H5 产物。
- 网站入口为 `/` 与 `/mobile/`，共用 `/api/v1/` 后端接口。
- H5 资源与路由基础路径为 `/mobile/`，首版使用 Hash 路由，允许地址带 `#`。
- 确认依据：“放在pc端的包的mobile里面”“部署pc端的时候，等于部署了h5端”；对 `#` 回答“可以接受啊”。
- 用户随后要求最终 `dist/` 与 `web/`、`mobile/` 同级，覆盖早先 `web/dist/` 方案。

### D06：Node.js 统一构建入口

- 保留现有 npm；仅为统一打包，不迁移 pnpm workspace。
- Node.js 脚本调用各工程编译，负责检查成功与组装发布目录。
- 支持分别构建 PC、H5，也支持组合构建。
- 约定命令：`node scripts/build.mjs web`、`node scripts/build.mjs h5`、`node scripts/build.mjs web h5`。
- 确认原话：“用nodejs脚本去做一个命令打包比较好……可以单独，剋组合”；随后“好，继续讨论”。

### D07：统一构建的产物保护

- 单独构建 `web` 保留 `dist/mobile/`；单独构建 `h5` 保留 PC 产物。

- 可并行编译，合并由统一脚本管理，避免一端清目录覆盖另一端。

### D08：PC/H5 前端状态隔离

- Pinia 运行状态与持久化存储按端区分；实际存储 key 使用 `pc`、`mobile` 前缀。

- 退出时只清理对应端的数据，草稿的退出保留规则另按需求基线确定。
- 确认原话：“H5和PC的各种登录状态最好能区分开”“只需要在前面加前缀就可以了”。

### D12：短时断网仍可继续答题

- 考试中短时断网不阻止本地继续选择或修改答案；断网本身不应打断作答。
- 确认原话：“正常来说，断网不影响他答题才对的。”
- 原服务端截止时间照常推进，不能因断网延长；该期限边界承接既有需求基线。
- 截止后仍未成功提交的处理见 D15，不能凭本地草稿补交。
- 本地答案保存时机与存储 API 已按 D29 确认。

### D13：首版本地记录答案、最终统一交卷

- 进入考试时已取得全部试题，首版不采用实时或持续向服务端同步答案的方案。
- 答题中记录每道题的选择，答案先在前端状态中维护，并按 FR-H5-25 保存为本地草稿，最终统一交卷。
- Pinia 内存状态不等于已经持久化的草稿；本地写入按 D29，草稿缺失或损坏的恢复规则按 D30。
- 确认上下文：用户纠正实时服务端同步思路，要求总体按简单、可走通闭环设计，重点防止学员误退出考试。
- 该方向替代上一轮推荐的“服务端持续草稿同步/有限补交宽限”路径；有限补交宽限未获确认。
- D12 的短时断网继续答题及原服务端截止时间不延长仍有效；截止后未成功提交的处理按 D15。

### D14：防止误退出考试，保留明确确认后的离开能力

- 首版采用防误退出，不要求绝对锁死页面。
- 答题页不提供普通返回入口和底部导航；页面内离开、浏览器返回或小程序返回尽可能先拦截并强提示，默认继续答题。
- 用户明确确认后仍可离开；原考试期限继续，本地草稿仅供截止前的同一作答恢复使用。
- 浏览器强制关闭和系统回收无法绝对阻止，由本地草稿兜底；D12、D13 继续有效。
- 确认原话：“剋”（主代理结合上下文按“可以”理解，确认上一轮防误退出提议）。
- 具体弹窗文案、拦截 API 及平台实现方式尚未确定；不将“尽可能拦截”描述为所有情况下均可阻止。

### D15：逾期未成功提交，由后端终结为超时/失败

- 服务端截止时间已过且未成功提交时，后端终结该作答为超时/失败，不能再交卷。
- 确认原话：“超时没有提交结果，肯定后端就记录失败了啊。不可能还能交卷。”
- 前端重进只能查询并展示服务端权威结果，禁止再用本地草稿补交或修改。
- 确认服务端终态后，清理或失效对应本地草稿；截止前重进仍可按 D14 恢复。
- 仅学员主动提交才可交卷，必须由服务端在截止前成功受理；主动触发和成功判定分别见 D16、D17。
- 明确作废主代理上一轮“超期回来用最后本地草稿交卷”的建议；不是新的待决选项。

### D16：仅学员主动确认交卷，到期不自动提交

- 交卷只能由学员主动点击并确认触发；倒计时结束时前端锁定编辑，不发送自动交卷。
- 未在截止前成功主动提交的作答，按 D15 由后端终结为超时/失败；截止后只能查结果，不能补交。
- 确认原话：“自动交卷成功 → 后端评分我们怎么会自动交卷的，他自己触发才行啊”。
- 本决定覆盖需求当前 FR-H5-26、FR-H5-27、UC-H5-05、C-H5-04、§8.7 中“到期自动提交”的条款；完整设计时必须回写需求。
- 本轮仅更新决策记录，不修改需求原文；主动提交临界请求的业务判定按 D17。
- 明确作废主代理刚才“自动交卷成功”的描述，以及 D15 原有到期自动交卷表述。

### D17：以服务端截止前成功受理为交卷成功标准

- 只有服务端在 deadline 前成功受理主动交卷才算已交卷；前端点击、确认或请求发出本身均不构成成功。
- 提交失败时，若仍未截止则保留本地草稿并允许重试；截止后按 D15 终结为超时/失败，不再重试交卷或补交。
- 确认上下文：用户确认以服务端截止前成功受理为准；即使已点击提交，网络失败且到点未成功受理仍判超时/失败。
- D12 的“断网不影响本地答题”不等于断网直到截止仍能交卷；成功状态仍以服务端为准。

### D18：视频断网沿用播放器的缓冲行为

- 首版视频断网沿用原生 `video` / uni-app 视频组件的缓冲、loading 行为，不增加离线播放、复杂重试队列或额外弱网状态机。
- 确认原话：“正常看视频断网，视频那边就会漏，一直会loading，这个还需要有什么特别吗”。
- 保留需求最低边界：缓冲、停滞不计入有效学习时长；最终加载失败提供简单可重试反馈。
- 失败、断网不覆盖服务端已确认进度；网络恢复后按播放器正常机制继续或重试。
- 服务端学习计时仍是必需；本决定只收敛视频断网的产品处理范围。
- 视频组件事件 API 与协议映射留待技术设计和联调；心跳周期、容差和完成阈值按 D19 复用既有协议。

### D19：移动端复用 05 册既有视频学习协议

- H5、微信小程序直接复用 `docs/design/05-模块设计.md` §5.4.8 的视频会话协议，不另造学习计时规则。
- 默认 30 秒心跳，上报递增 `seq`、`position_ms` 和播放状态；前端只报告状态与位置，服务端权威计算。
- 仅合法连续 `playing` 区间计时；`paused`、`buffering`、`background` 不计时，非 playing→playing 的首拍只重置锚点。
- 服务端按真实间隔、45 秒封顶与位置前进量确认：`credited_ms=min(server_elapsed,45000,forward_position)`。
- 前进量超过服务端 `elapsed + 2 秒` 时，该段不计入且不推进已确认断点；去重覆盖达到 95% 才完成，重复播放不重复增加覆盖。
- 确认上下文：用户确认复用 05 册现行规则；这些参数是既有协议，并非本轮新发明。
- 最终设计须同步修订 00 册仍将“上报周期、时间容差、完成阈值”写为待确认的过时表述；本轮只更新记录，不改 00/05 正文。

### D20：结构化 JSON 题库与三种客观题的只读渲染

- 题库、考试数据以服务端结构化 JSON 为权威，学员端接收只读题目数组，按设计稿展示并收集选择。
- 题型严格限定 `single`、`multiple`、`judgment`，分别对应单选、多选、判断；题干与选项支持普通文本、受控图片。
- 不扩展主观题、图片作答、答题上传、公式等额外题型或表达能力；“答题上传”限制不影响独立的实名材料上传需求。
- 考试下发继续不含正确答案、解析；正确答案仅由后端评分使用。
- 确认上下文：用户提供参考题库并明确后端保存 JSON、返回前端题目数组，移动端按设计稿仅支持单选、多选、判断。
- 样本没有独立多选题章节，不影响产品明确支持多选题；多选支持来自产品设计，不能伪称来自该样本。

### D21：三种题型统一使用本地答案模型

- 本地答案统一为 `Record<itemId, optionId[]>`；`single`、`judgment` 最多选一项，`multiple` 可选多项。
- 交卷按 D33 原样保持稳定的题目项、选项标识，不转换为展示下标，也不因题型拆成三套答案状态。
- 确认上下文：用户确认主代理提出的统一作答状态建议。

### D22：按设计稿落实答题页交互与布局

- 顶部“退出”是 D14 的受保护动作，必须先提示确认，不是直接返回；居中显示倒计时，临近截止以红色提示，按 D16 不自动交卷。
- 顶部右侧“交卷”为学员主动提交入口，遵守 D16、D17 的确认与成功判定规则。
- 页面显示进度条、已答数量、草稿保存时间；题目区域包含题号/总数、题型标签、分值、题干及选项。
