# 测试报错记录

## 记录规则

- 只有用户明确要求“记录”时，才新增或更新报错条目；日常排查不自动记录。
- 每条记录包含：错误、错误原因、修复方法。
- 排查中提到与另一个项目的区别时，将已核实的区别写入“错误原因”；没有提到时不增加该部分。
- 原因尚未确认时标注“待确认”；修复方法区分建议方案与已实施、已验证的结果。
- 不记录密码、密钥、Cookie、令牌、完整签名链接或不必要的个人资料。

以下条目均按用户明确要求记录；未被要求的问题不自动补录。

## 2026-10-28｜H5头像直传COS时跨域预检失败

### 错误

- 发生页面或操作：H5“个人资料”页，选择图片并上传头像。
- 页面来源：`http://127.0.0.1:5175`。
- 浏览器报错：`Response to preflight request doesn't pass access control check: No 'Access-Control-Allow-Origin' header is present on the requested resource`，随后 COS `PUT` 请求显示 `net::ERR_FAILED`。
- 影响：头像无法完成直传。这是头像上传错误，不是身份证、人脸识别结果。
- 证据：用户提供的浏览器控制台日志；日志中的签名参数、临时凭据和具体对象键不在此保存。

### 错误原因

修复前配置为 COS 存储，后端 `/media/limits` 仅按存储类型返回 `upload_mode=direct`。H5先向后端申请上传会话与授权，再用浏览器向 COS 临时对象执行跨域 PUT。该请求包含 `Content-Type`、`x-cos-acl` 等请求头，需要先进行 OPTIONS 预检；本次预检响应缺少允许当前来源的 `Access-Control-Allow-Origin`，浏览器阻止了上传。

已确认的是预检失败及响应头缺失；尚未读取实际桶 CORS 规则，具体是来源、方法、请求头不匹配，还是配置未生效，仍需在桶配置中核对。上传会话和授权由后端管理，不会消除浏览器直传所需的 COS CORS 配置。

与另一个项目 gooodwork 的区别：

- gooodwork 后端支持独立的 `MEDIA_UPLOAD_MODE=proxy|server|backend`；特定开发、测试配置也会默认选择中转。
- gooodwork 前端在开发模式（排除 test）发现上传地址与页面不同源时，主动走后端中转；直传遇到特定的上传网络错误时，也会回退中转，取消操作和明确的 COS HTTP 错误不统一回退。
- 修复前，培训项目的 H5 头像上传按后端 `upload_mode` 执行；COS 模式下选择直传，发生 CORS/网络错误后提示失败，没有上述中转回退机制。下述修复已补齐独立模式选择及限定的网络错误回退。
- 因而另一个项目在本地上传成功，可能实际走的是中转，不能据此认定它的 COS 直传不受跨域限制。其实际运行时采用哪条路径，本次未抓取请求验证。
- 源码依据：本项目 `server/src/modules/media/media.service.ts` 的 `limits()`、`mobile/src/api/media.ts` 的 `uploadAvatar()`、`mobile/src/platform/media-upload.h5.ts` 的 `uploadImageDirect()`；另一个项目 `D:/goodwork/develop/server/interfaces/http/composition/http_settings_wiring.py` 的 `should_use_proxy_upload()`，以及 `D:/goodwork/develop/client/src/services/mediaUpload.ts` 的 `uploadMediaFile()`、`shouldUseDevelopmentProxy()`、`isDirectUploadNetworkError()`。

### 修复方法

方案一，继续使用直传：在 COS 桶中保留现有规则并追加精确页面来源 `http://127.0.0.1:5175`（不带 `/mobile/` 路径），允许 `GET/HEAD/PUT`，允许项目使用的 `Authorization`、`Content-Type`、`Content-MD5`、`Range`、`x-cos-acl`、`x-cos-security-token`、`x-cos-sdk-retry` 请求头，暴露 `ETag`、`Content-Range`、`Content-Length`、`Accept-Ranges`。手机 HTTPS 测试地址需另外追加对应的精确来源，不覆盖共享桶原有规则。

方案二（本次已实施），参考 gooodwork 的模式选择和限定回退，复用本项目已有的受控中转链路：

- 增加独立的 `MEDIA_UPLOAD_MODE=auto|proxy|server|backend|direct|presigned`，非法配置使启动失败。默认 auto 在 development/test 使用中转，其余环境 COS 使用直传；local 存储始终中转。`proxy/server/backend` 强制中转，`direct/presigned` 请求直传。上传方式不改变存储类型，选择中转仍可存入 COS。
- H5 中转复用 `POST /media/upload`，沿用用户鉴权、用途授权、文件大小/格式探测、服务端 SHA-256、正式私有 COS 发布与内容回读；未引入另一个项目的 trusted_local 扫描旁路，也未放宽实名检查。
- 直传仅在 COS PUT 的 TypeError 网络/CORS 拒绝或无可见状态码时回退一次中转；原 staging 会话走既有取消/清理协议。取消、会话切换、明确 COS HTTP 错误、读取本地图片失败及完成确认异常不回退，避免重复发布或跨账号上传。
- 本地默认中转不依赖 H5 直传的 Web Crypto 能力。显式直传仍要求相应安全能力及 COS CORS 配置；COS 下载短链的跨域要求另行保留。
- 生效方式：手动重启后端，使新编译代码与上传模式生效，刷新 H5 后重试。可在根 `.env` 显式设置 `MEDIA_UPLOAD_MODE=proxy`；未设置时，本地 development 已默认中转。本次没有改动用户现有运行服务或 COS 桶配置。

- 实施状态：已在 `weifabao` 分支工作区完成，未提交。
- 验证结果：修复前新增配置与 CORS 回退测试可复现失败，修复后通过；学员端 66 个文件 / 661 项单元测试及类型检查通过；3 项 Chrome 浏览器回归通过（缺少 Web Crypto 时中转并保存头像、COS 网络失败后仅回退一次、明确 403 不回退）；服务端上传配置及 COS 中转发布针对性测试 20 项通过；服务端编译与统一 H5 生产构建通过。
- 验证边界：浏览器请求和 COS 使用隔离 mock，后端 COS 发布使用内存存储 fixture，未写入真实云对象或用户数据库；尚未完成手机真机、真实 COS 上传验收。服务端全量回归为 1555 通过、15 失败、2 跳过，另有 Redis 集成套件启动失败；失败的文件权限、目录 fsync、视频工具执行及 Redis 二进制问题已在独立 HEAD 原始源码快照复现，不能宣称全量通过。本次随后新增的 1 项 COS 中转发布用例已单独验证通过。
