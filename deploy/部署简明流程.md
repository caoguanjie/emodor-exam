# 部署简明流程（运维人员与 AI 共用）

适用：单台服务器、Docker Compose 部署本项目。默认端口 **8080**，不占用服务器的 80。所有命令在项目根目录执行。真实账号和密钥单独交付，不随 Git 代码更新。

## 一、开始前先确认

填写本次部署信息，未知项先核实，不猜测：

| 项目 | 本次填写 |
| --- | --- |
| 服务器、登录用户、项目目录 | 待填写 |
| 首次部署 / 更新已有系统 / 只补配置 | 待填写 |
| 要发布的版本或提交编号 | 待填写 |
| 访问地址（默认 http://服务器地址:8080） | 待填写 |
| 配置负责人、验收负责人 | 待填写 |
| 已有系统的备份位置与恢复办法 | 待填写；首次空库可注明不适用 |

需要 Docker、Docker Compose，以及用于配置检查的 Node.js 22 或以上版本。确认 8080 空闲；需要外部访问时确认防火墙已放行。正式域名、HTTPS 和宿主 Nginx 的设置另行确认，本流程不自动改动它们。

```bash
docker --version && docker compose version && node --version
git status --short
git rev-parse HEAD
```

发现本地未提交改动时先查明归属，不能覆盖。已有系统先备份数据库、文件数据和 `.env`，记录旧版本；备份应能用于恢复。不要把备份内容或密钥贴进聊天、日志和仓库。

## 二、首次部署

### 1. 准备配置

取得指定版本代码后，创建配置文件。已有文件会保留：

```bash
test -e .env || (umask 077; cp deploy/.env.example .env)
```

按模板注释填写以下内容：

| 配置 | 如何准备 |
| --- | --- |
| 数据库账号和密码 | 使用非 root 业务账号，密码不能为空 |
| 系统密钥 | 只在首次空环境生成；按模板各自生成，不共用 |
| 管理员初始密码 | 首次初始化时填写，首次登录后改密 |
| 短信、身份证识别、人脸核验 | 从负责人取得真实配置，并开启对应开关 |
| COS | 填写正式桶和访问配置；密钥只给后端 |
| 对外端口 | 保持 `HTTP_PORT=8080` |

电脑上已经填好的短信和实名配置，可以按[补齐配置说明](supplier-env.md)单独导出、传递和合并。**不要用电脑上的整份 `.env` 覆盖服务器配置。**

### 2. 检查，再启动

```bash
node scripts/supplier-env.mjs check --file .env &&
docker compose --env-file .env config --quiet &&
docker compose --env-file .env up -d --build
```

出现报错就停在当前步骤，按提示处理。不要跳过检查，也不要运行不带 `--quiet` 的配置展示命令把密码输出出来。

### 3. 创建管理员

先执行 `docker compose ps`，确认 API 显示 healthy。随后执行一次：

```bash
docker compose --env-file .env exec api node dist/seed.js
```

新数据库会自动装载初始表结构；已有数据库不会因为再次启动就重新初始化。

## 三、更新已有系统

1. 记录旧版本，确认备份和恢复办法。
2. 检查服务器是否有未提交改动，取得本次指定版本。不要盲目更新到“最新”。
3. **保留原 `.env` 和全部数据卷。** 新增配置按提示补齐，不能重新生成已有系统密钥。
4. 确认本次是否需要数据库升级。如果需要，先取得并执行该版本专门的升级与恢复步骤；本简明流程不替代数据库升级方案。不能重新导入 `init.sql`，不能改写已执行迁移。
5. 在上述条件满足后，执行第二节的“检查，再启动”，然后执行下方验收。日常更新不需要重新创建管理员。

只修改短信、实名等后端配置时，用以下命令代替重新构建：

```bash
node scripts/supplier-env.mjs check --file .env &&
docker compose --env-file .env config --quiet &&
docker compose --env-file .env up -d --no-deps --force-recreate api
```

单纯 `restart` 不会加载新环境变量。修改 COS 公共地址等前端构建配置时，需要重新构建，不能只重启后端。

## 四、怎样才算部署成功

先检查容器和后端：

```bash
docker compose ps
docker compose exec -T api wget -qO- http://127.0.0.1:3000/api/v1/health
```

四个容器应正常运行，API 应显示 healthy。外部访问 `/api/v1/health` 返回 404 是预期行为。

再由验收人员实际操作：

- 打开网站首页和 `/mobile/`。
- 管理员用图形验证码登录；首次登录完成改密。
- 学员实际接收短信并登录。
- 用授权的测试人员完成实名认证。
- 查看图片、播放视频，确认 COS 资源可以读取。

配置检查通过只说明“填写完整”，不说明短信、实名服务一定能用。没有做的步骤明确写“未验证”。不要为了测试批量发送短信或反复提交真实身份材料。

## 五、遇到问题怎么处理

| 问题 | 处理方式 |
| --- | --- |
| 提示缺少配置 | 找配置负责人补齐提示的字段，不编造值 |
| 8080 被占用 | 确认占用服务；协商其他端口，不停止不明服务 |
| API 不健康 | 在受控终端检查 API 日志；对外反馈先脱敏 |
| 合并提示已有不同密钥 | 停止，确认哪个账号应使用，不强行覆盖 |
| 更新后异常 | 保留现场，按该版本恢复方案处理；数据库变更后不能只退代码 |

禁止用删除数据库、删除数据卷、`docker compose down -v` 或重新生成密钥来“试着修复”。

## 六、人和 AI 都按这个格式交付结果

```text
部署类型：
服务器与目录：
发布版本：
访问地址：
配置检查：通过 / 未通过
容器状态：
已实际验证：
尚未验证：
备份与恢复记录位置：
遗留问题及负责人：
```

AI 执行时也必须逐步确认结果：没有服务器授权只做本地工作；信息缺失先核实；命令失败不继续依赖它的步骤；不展示密钥；不把“写好了流程”说成“部署成功”。
