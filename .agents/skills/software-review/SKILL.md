# 软件工程审查

先阅读项目实际代码与配置，再判断清单各项的适用性。交付有证据、按风险排序的审查结果，帮助用户决定先修什么。默认只读，不实施修复。

## 原始清单

开始审查时完整读取 [英文原始清单](references/checklist.md)，包括最后的工程团队职责部分。英文内容按用户原文保留；不要翻译、改写、删减或重排该参考文件。执行说明与报告默认使用简体中文。

清单是检查线索，不是必须建设的功能列表。结合当前产品、交付阶段、数据敏感度、部署方式、合同与实际使用场景判断，不能为了逐项打勾扩大产品范围。

## 范围与边界

- 读取当前适用的 AGENTS.md、README、依赖清单与锁文件、架构/数据设计、入口配置，识别产品与关键数据流；设计文档中的承诺不等于代码已实现或运行已验证。
- 优先使用项目指定的代码探索工具。图索引不完整、过期或没有结果时，核对当前源码并说明覆盖限制；不能把搜索无结果直接判成能力缺失。
- 不修改业务代码、配置、依赖、数据或部署，不提交、推送或自动修复。用户后续确认某项修复后，按其批准范围另行实施。
- 默认在对话中交付报告。只有用户要求保存时才写报告文件，并遵循项目的报告目录约定。
- 可运行不改变业务状态的诊断。执行测试前检查副作用；需要写入时使用已获授权的隔离临时环境，不能对开发库或生产库运行会重建数据的测试。主动渗透、压测、外部写入及真实供应商付费调用需要相应授权。
- 不读取受用户排除的文件，不输出真实凭据、令牌或个人数据。查到泄露线索时报告脱敏位置、类型与暴露范围；不把密钥原文复制进报告、提示词或日志。

## 审查流程

### 1. 判断每项是否适用

先形成简短产品画像：用户角色、单机构/多租户、登录方式、核心业务、支付、敏感数据、AI/第三方接口、部署与可用性要求。常规信息从代码与配置推断，并标明依据；只有缺失信息会实质改变结论时才提问，同时继续不依赖答案的检查。

为每个英文条目建立逐项台账，分别记录适用性、检查状态、证据或缺口。保留原文短引或原文行号，方便回查，不能只检查熟悉的几个领域。

| 适用性 | 处理 |
| --- | --- |
| 适用 | 检查实际实现、配置与可获得的运行证据 |
| 不适用 | 写明产品依据后跳过，不建议新增对应功能 |
| 无法确认是否适用 | 说明缺少的业务、合同或部署信息；不能当成不适用 |

例如，无支付业务不检查订阅、税费、退款与 PCI；没有邮件登录不以邮箱加号或重置邮件功能缺失报错。单机构产品可跳过租户隔离，但仍须检查用户之间的数据授权。SSO、SAML、SCIM、MFA、SOC 2、HIPAA、GDPR、跨地域部署等按实际风险与适用条件判断，不能一概强制，也不能仅凭产品名称排除。

清单中的技术方案要按其保护目标评估：具备可靠恢复方案不一定需要软删除；可靠的前向修复不一定需要可逆的破坏性迁移；金额也可由正确配置的精确十进制类型承载。确认现有方案能否满足业务，不把某种实现方式当成唯一合格答案。英文原文保持不变。

### 2. 检查实现并保存证据

优先检查数据泄露、越权、不可恢复的数据损坏、资金或 AI 费用失控、服务中断风险，再检查可维护性和体验。独立领域可按当前授权与工具能力并行审查；各子任务沿用同一只读范围与证据标准，由主审复核合并。

沿实际执行路径核查：入口 → 校验/鉴权 → 业务逻辑 → 数据/文件/外部服务 → 返回与日志。局部缺少检查时继续核对上游守卫、中间件、数据库策略和部署保护，避免遗漏已有控制。

检查结果采用以下状态：

| 检查状态 | 必须具备的依据 |
| --- | --- |
| 已确认问题 | 具体文件/配置、有效执行路径、触发条件和可解释的后果；注明源码确认或安全复现 |
| 已检查，当前范围未发现问题 | 写清检查了什么及其证据等级，不声称全系统安全 |
| 无法确认 | 写清缺少什么、已查到什么，以及最小补充验证方式 |

文件证据使用当前文件路径与准确行号，并标出关键函数/配置项。历史报告、测试源码、设计承诺和注释只能证明其自身内容；构建成功不等于业务验证，测试通过不等于生产配置生效。

只见 README 的备份说明，不能确认备份或恢复成功；只见内部 HTTP 监听，不能断言公网没有 TLS；没有访问生产环境，不能断言没有告警、值班、密钥轮换或访问审查。依赖漏洞需要核对锁定版本、当前权威公告或实际扫描结果及受影响条件，不能凭包名或年龄认定有漏洞。

法规、认证与组织条目只报告当前可验证的工程证据和缺口；适用性或要求需要外部核实时查询当前权威来源，不凭代码宣称合规或取得认证。最后的团队职责清单用于检查责任归属、文档、交接和运行证据，不要求为每个职位名称另招一人。

### 3. 复核与风险排序

将发现对应回具体清单条目，合并同一根因，检查反证，区分已确认缺陷与待核实事项。风险按影响范围、数据敏感度、发生可能性、触发前提和恢复难度判断；严重程度与证据确定性分别记录。

| 严重程度 | 参考判据 |
| --- | --- |
| P0 紧急 | 已确认可造成大范围敏感数据泄露、重大损失、不可恢复的数据破坏或核心服务瘫痪，且触发门槛极低或已发生 |
| P1 高 | 已确认的严重越权、关键数据完整性或可用性缺陷，有明确可达触发路径，应优先修复 |
| P2 中 | 影响受限或需特定条件触发的可靠性、安全、业务正确性问题 |
| P3 低 | 有具体影响的维护或体验问题，风险较低 |

优先给出最多 10 个已确认且最值得修复的问题。少于 10 个就如实给出实际数量，不能用“无法确认”、不适用功能、风格偏好或重复根因凑数。其他已确认问题列在其后；高影响但证据不足的事项单独列为“优先核实”，不伪装成缺陷，也不隐藏。

## 报告格式

先说最重要的结论与优先修复项，再给检查边界。每项发现采用下面的紧凑格式：

```text
1. [P1 高][源码确认] 具体问题标题
风险与触发：谁在什么条件下能做什么，会影响什么数据或业务。
证据：文件路径:行号、关键符号/配置，以及已核对的调用或授权链。
建议修复方向：与现有架构一致的最小改动方向；此次不实施。
验收方式：用哪个针对性检查证明问题已解决。
```

主体按以下顺序交付：

1. 最值得修复的问题：最多 10 项，按严重程度排序，引用实际证据。
2. 其他已确认问题（如有），以及单独的优先核实事项：明确写“无法确认”和所需证据。
3. 检查覆盖与逐项台账：按领域压缩展示，仍能逐项对应原始清单；不适用项可合并列出依据，不给建设建议。
4. 验证边界：实际读过的范围、执行的命令与结果、未执行的运行/生产/真机/供应商检查。若覆盖不完整，明确称为部分审查。

报告收尾停在审查结果，等待用户选择修复项。不要直接进入修复、提交或部署流程。
